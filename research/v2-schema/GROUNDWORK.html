Coexistence Groundwork

Four pieces of additive 1.x work that let two schema generations answer questions in one install — arrived at by removing every mechanism that needed someone to be careful.

What this is

v2 replaces the star schema with a single event table. That change is worthless if the reporting layer cannot serve both generations at once, because no data is migrated — v1 holds the history permanently and v2 accumulates from cutover forward. This document plans the work that makes that coexistence possible. None of it is v2 code. All of it ships in 1.x releases, each standing on its own, and three of the four pieces are improvements even if v2 never happens.

The principle that fell out

Every version-aware mechanism considered for this got discarded in favour of something the codebase already had. The sequence is worth recording, because it is the reason the plan is small:

ProposedFailed becauseReplaced by
Route by date periodthere is no boundary instant — cutover is per-feature, dual-write overlaps, switch-off is an admin action, the queue is asyncthe profile
An install-wide version settingwith no migration, a flip blanks every historical reportthe profile
A required version on every query62 report configs, the REST API and the UI would each grow a fieldthe profile supplies it from siteId
Filter versions at the entity-pool sortfixes one consumer of ten; the picker had already offered the wrong definitionscope the catalog
Partition the catalog by versionthreads a version concept through every accessor, and such concepts leakscope by entity

What survived is the entity. It is in every registration already, understood everywhere already, and it implies the generation without naming it. So the word “version” ends up confined to the profile record and the migration machinery — the only place generational schema changes are actually relevant.

The through-line: prefer structure that makes the wrong answer unreachable over discipline that remembers to exclude it. Each replacement above removed a place where something had to be careful.

Part One

The work

In dependency order. Each is testable against v1 alone, before a second generation exists to mask a mistake.

1The dimension catalog becomes entity-keyed Decided

The prerequisite everything else stands on. registerDimension() loops $entity_names but writes two different shapes:

if ($denormalized) {
    $this->denormalizedDimensions[$dim_name][$entity] = $dim;   // entity-keyed
} else {
    $this->dimensions[$dim_name] = $dim;                        // name-keyed — last write wins
}

The normalized branch overwrites itself on every iteration, so only the last entity survives. And _loadDimensions() compounds it with a flat array_merge across modules. A second generation registering pageTitle would replace the first at load time — gone before any read-side scoping could apply, which is why this must land before item 2 rather than alongside it.

Measured across 103 registrations: 58 denormalized (already entity-keyed, unaffected), 41 normalized against a single entity (the overwrite is a no-op), and 3 normalized against all seven $fact_table_entities — month, userName, priorVisitCount.

Change: $this->dimensions[$dim_name][$entity], matching denormalizedDimensions, which already has the correct shape. Metrics need nothing — $this->metrics[$name][] = $map already accumulates a list per name, which is why the registry has always been able to hold visits twice (base.session/id and base.request/session_id).

Blast radius: the registration loop, the _loadDimensions() merge, and getDimension() — which has exactly one caller, ResultSetManager:970.

Proof: with one generation registered the change must be behaviour-preserving, so every existing report renders identically. That is a characterization run, and the harness exists — tests/ReportCharacterizationHarness.php, 433 lines with snapshot/observe/normalise.

Traced: userName is the one, and it is registered wrongly Measured

An earlier draft named three suspects from static analysis — month, userName, priorVisitCount. At runtime only one dimension was losing entities: userName, which keeps 1 of 7. The other two parse as multi-entity but register denormalized; the static count mis-read their argument positions. The recovered total is 6 entries, not the ~18 estimated.

And the loss was hiding a defect. userName is registered normalized against seven fact entities that all carry user_name denormalized on the row. Normalized resolution joins a dimension table through a foreign key, and its foreign_key_name is empty — so it builds an alias ending _via_ and joins whichever entity was registered last (base.commerce_line_item_fact) rather than the one being queried.

The fix is one flag, denormalized = true, exactly as date is registered against the same list; it then lands in denormalizedDimensions[$name][$entity], which is where it belonged. Note the value is written both ways — denormalized onto fact rows, and to owa_visitor alongside user_email, which SessionHandlers updates on change — so the denormalized reading is the correct one for these entities.

Reachable but unexercised: no shipped report uses userName, yet getAllDimensions() offers it, so it is selectable in the custom-report picker. That is why it has gone unnoticed. Deliberately not fixed in the characterization PR — a behaviour change does not belong in a behaviour-preserving commit, and it needs its own test.

2Catalog accessors take an entity scope Decided

The catalog is keyed by name, and the failure is at enumeration, not resolution. getAllMetrics() and getAllDimensions() return the flat name-keyed map to ten consumers:

ConsumerUse
ResultSetManager :930, :937, :2364internal resolution
CustomReports :1371, :1378custom report definition
CustomReportEdit :220, :226, :243, :270, :282the picker UI and its validation

The picker is built from array_keys( getAllMetrics() ). Array keys are unique, so with two generations registered it offers one visits that silently means two different things, and the validation loops beside it are equally blind. Selection never gets the chance to be wrong, because the wrong definition was offered and accepted as valid upstream of it. This is why filtering inside getMetricEntities() was rejected: it fixes one consumer.

Change: the accessors take an entity scope, supplied by the profile. Nothing downstream filters, because the other generation is not in scope — the picker lists one generation's names with no change to CustomReportEdit, validation follows, and ResultSetManager needs nothing at all: its summary-level sort simply runs inside the scope it is handed.

Value independent of v2: getAllMetrics() today returns everything regardless of whether it is queryable in the current context. An entity-scoped picker is more correct with one generation, not just two.

Modules do not declare a generation Decided

A module registers across entities, exactly as Base already does — visits is registered twice today, against base.session/id and base.request/session_id. The v2 registration is a third call in the same file, in the same module, against the event entity. There is no per-module generation, so _loadMetrics() and _loadDimensions() need no grouping: they keep merging modules flat, and the accessors filter that merged map by the entity scope. The single choke point is preserved because every consumer goes through an accessor.

A third-party module registering only against v1 entities is unaffected and needs no change: it simply will not appear in a v2 profile's scope, automatically, because its entity is not in scope. When such a module wants to support v2 it adds a registration against the event entity — the porting story is one more registration, not a version declaration or a rewrite, and a module can serve both generations at once without knowing generations exist.

But that registration must be safeguarded by the module's schema version, or it will advertise a dimension whose column does not exist on installs that have not reached the update which created it. The machinery is already there: Core/Module.php carries $required_schema_version and getRequiredSchemaVersion(), and the applied version is persisted per module as a schema_version setting. Because §4.1 keeps one numbered sequence rather than a v1/v2 pair, the check is a numeric comparison — no compatibility matrix, which is precisely why that decision was made. A module adding v2 registrations raises its required version to the sequence number that introduced the entity.

The safeguard has to run in both directions

The forward case is an install whose schema predates the v2 entity. The mirror case is more likely and easier to miss: §4.1 makes a dropped v1 a supported state, so a module registering against base.session may be offering dimensions backed by a table the administrator deliberately removed.

So scoping filters for two distinct reasons at the same accessor — not in this profile (the entity scope of this item) and not in this install (schema version and entity existence). They are separate conditions and conflating them will read as one bug and be two.

This also makes the $fact_table_entities hazard below the principal way to get this wrong, rather than an incidental one: with everything registered from one module, appending the v2 entity to the shared array is the tempting shortcut. v2 registrations are separate calls with their own columns.

Calculated metrics have no entity

They carry child_metrics and a formula instead, so scoping must include a calculated metric when all of its children resolve within the scope, and exclude it otherwise. It falls out of the existing recursion — getMetricEntities() already merges children's entities — but it is the one case where scoping is not a direct property test. Getting it wrong silently drops bounceRate and its siblings from the picker rather than erroring, so it needs an explicit test rather than an assumption.

3Site identity decoupled from the domain Decided

A site's identifier is a pure function of its domain:

Site::generateSiteId( $domain ) { return md5( $domain ); }

So two profiles for one website are impossible by construction, not by policy. Three places derive it — Site::generateSiteId(), an inline md5($domain) at SiteManager.php:44 that bypasses the method, and InstallManager.php:95 — and one re-derives it at runtime in the permission path, ServiceUser.php:283. That last one is the edge that needs care and tests; note that a site's allowed-user grant set is full-replace, which is an easy place to revoke people silently while refactoring nearby.

Change: stop deriving new identifiers and treat the column as opaque. The domain becomes an attribute of a profile rather than its identity.

Never rewrite existing site_id values

Every identifier in the wild is md5(domain) and every fact row references it. Decoupling identity from derivation does not require reissuing identities already handed out — stop computing new ones, leave existing ones alone, and the change is genuinely additive with no data migration.

Value independent of v2: the derivation currently prevents tracking two configurations of one domain, renaming a domain without orphaning its data, and expressing one property spanning several domains. All three are fixed by the same change.

4Profiles Decided

Vocabulary settled. A site stays the tracked website; a profile is the new thing measuring it; site_family becomes the grouping. “Property” is avoided deliberately — it carries a GA meaning close enough to mislead and not quite the same. This needed settling first because it surfaces in the UI, the REST API and the schema at once.

One tracked website, several profiles; a profile declares its generation and supplies the entity scope of item 2. The whole experience fans out from it — a v2 profile shows v2 navigation, v2 reports, and queries the v2 REST endpoint. This is the path GA took to GA4.

It dissolves the problems rather than solving them: version selection is never inferred, spanning two generations in one result set is structurally impossible rather than a rule somebody must remember, history needs no migration because the v1 profile keeps its data and its reports, and cutover is per-site opt-in whose rollback is “use the other profile”.

Two things are already in place. site_family exists as a column on owa_site, is settable at creation, and is written but never read anywhere — a dormant slot, so the grouping can be defined freshly rather than migrated. And the per-site session store (owa_s_<siteId>) already gives two profiles on one domain independent session cookies, which is both correct and exactly GA's _ga_<property>.

No client change. §3.1 is Decided: one tracker, server-side fan-out, and nothing about the page changes on cutover day. The site → profiles mapping is server-side, so the page never learns profiles exist. Two trackers were rejected there because they split a site's data by which snippet happened to be deployed — stepping v1's history exactly when a site upgrades, destroying the thing v1 is being kept for.

5Metrics become configuration Open

Two things, and only one of them is work. An earlier draft argued this had to come before v2's metrics were authored, or they would be written as classes and converted later -- the same work twice. That was wrong: nothing forces v2's metrics to be classes.

WhatCost
5aA policy: new metrics are registered as configuration. registerMetricDefinition() already works and 6 metrics use it todayNone. Needs no machinery and no sequencing. Adopt it and the doubled work cannot happen, because v2's metrics are config from the first one written
5bConverting v1's existing 22 class metrics Real but optional. Pure cleanup of code that already works, on no critical path, schedulable whenever — or never

So 5a should be adopted immediately and is not really an item at all, while 5b is different in kind from 1–4: those are prerequisites v2 cannot happen without, and this is housekeeping. Separating them removes the only argument for scheduling the conversion early.

Measured ConfigurableMetric already supports count, distinct_count, sum and calculated, but only 6 metrics are registered through it against 22 class references, and calculated has no registrations at all. The classes are declarations wearing class clothing — BounceRate is six setters and a formula string, and no metric class in the tree contains SQL — so the conversion is mechanical, exactly as the report controllers were.

Why it is no longer load-bearing. An earlier draft had this on the critical path for coexistence. It is not: the registry is keyed by entity, so v2 registers additional implementations under existing names whether those implementations are classes or config entries. Nothing about two generations coexisting depends on the format.

Not included: the formula evaluator. ResultSetManager::evalFormula() runs @ eval() on a PHP string, which is tolerable only while every formula ships in the repo — and a config file in the repo is exactly as trusted as a class in the repo, so moving the 8 shipped formulas does not move the trust boundary. The parser is the prerequisite for a user-authored metric builder, a separate feature, and a plain four-operator grammar would not even cover today's set since round(actions / visits, 1) needs function application.

In v2 the remaining classes disappear, so 5b is 1.x-only housekeeping

Of the seven metric classes left after the conversion, three are the goal classes, one is repeatVisitors, one is unregistered and one is ConfigurableMetric itself. Every one of them is gone in v2 (EVENTS.html §7.14): the numbered goal slots retire in favour of named key events with a parameterised metric, repeatVisitors retires into the newVsReturning dimension, and per-key- event reporting becomes one metric plus one dimension.

So the classes that resist configuration are not a gap to close — they are artefacts of numbered slots and stored booleans, which v2 removes for unrelated reasons. That makes 5b housekeeping for the 1.x line rather than groundwork for v2, and lowers its priority further.

Position: 5a now, as a standing rule. 5b unscheduled — it competes with work that actually blocks, and its cost does not grow if it waits, because 5a stops the class metrics multiplying in the meantime.

Part Three

Order and proof

Why this order

  1. 1 before 2 — the overwrite happens at registration. Until the catalog can hold two definitions under one name, there is nothing for scoping to select between.
  2. 2 before 4 — the profile's job is to supply a scope. Build the thing that consumes a scope before the thing that produces one.
  3. 3 before 4 — md5(domain) makes a second profile per website impossible, so profiles cannot be built on top of it.
  4. All four before any v2 schema work — building v2 tables before the container they live in is backwards, and both of the blockers found here were invisible until coexistence was attempted. Assume there are more.

How each is proved

The standing rule applies: coverage precedes development, bug fixes start with a failing test, behaviour-preserving work starts with a characterization suite, and every pin is mutation-checked at creation. Concretely here:

WorkProof
1 · entity-keyed dimensionscharacterization: one generation registered, every existing report byte-identical. Mutation-check by registering a second definition and asserting both survive
2 · scoped accessorsa metric registered against an out-of-scope entity must not appear in the picker — and a calculated metric whose children are all in scope must. Separately: a module whose required_schema_version exceeds the install's must not register, and neither must one whose entity's table has been dropped
3 · site identityexisting installs unchanged; a new site gets a non-derived id; two sites on one domain become possible
4 · profilestwo profiles on one website resolve to different catalogs and different session cookies from one tracker

Three standing traps apply to all of it: an order-dependent test that passes only because an earlier file warmed a registry (CI runs an isolation sweep); a vacuous assertion, where a double-quoted PHP needle containing $this-> interpolates away and passes unconditionally; and configless CI, which has no database and skips ~506 tests that pass locally — reproduce with composer test:configless, not test:scratch.

Open before building

  • Linked or independent? Whether a v1 and v2 profile for one website present as related in the UI (“the old version of this property”) or as two entries that happen to share a domain. GA chose linked, and it is how people found their way across.
  • Are month, userName and priorVisitCount broken today? Unresolved, and cheap to answer once item 1 makes the surviving entity explicit.
