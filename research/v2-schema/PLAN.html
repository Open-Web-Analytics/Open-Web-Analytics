Part One

What v2 is

One table for every event, and the consequences that follow from it.

1.1The shape Decided

Every tracked interaction becomes one row in one table, GA4-style, replacing ten parallel fact tables and their dimension satellites. Ids are content-derived, so a write is a single insert with no lookups: no session upsert, no dimension check-and-create.

ModelPer tracked pageviewEvents/s
1.x star1 insert + 1 session upsert + 5 dimension checks = 7 statements79
v2 event table1 insert202

Measured Disk is a wash — within ±2%, because 1.x already denormalises 58 dimensions onto its facts. The win is not storage. It is throughput, one definition per metric instead of nine commerce metrics existing twice, and the deletion of an entire class of dimension-FK bugs this release cycle has been spent fixing.

The star keeps exactly one real advantage: post-hoc enrichment is 589× cheaper — rewriting one dimension row versus 565k event rows. That advantage is a row-store artefact and inverts on a columnar engine, and it has been explicitly traded away.

1.2What it deletes

Against the live registry: 78 metrics × 100 dimensions = 5,493 valid API pairs. Under v2, 4,443 (81%) work unchanged, 770 (14%) reference the eleven *InVisit dimensions which have zero references anywhere outside their own registration, and 280 (5%) need an exit page served by an is_exit flag. Nothing is genuinely lost.

Also retired: owa_session's 121 columns (45 of them goal columns) and nine derived date-part columns per fact row. The dead owa_exit entity is already gone — removed from 1.x in #1048 with its registration and its setting. Its table is deliberately left in place: dropping it is a destructive migration and a separate decision from deleting dead code. The name also moved to the legacy class-name test's RETIRED list, which asserts it is gone rather than merely dropping it — a real backward-compat break, taken deliberately.

The risk inverts. 1.x's entity boundaries prevent non-additive metric combinations — the resolver intersects entity sets, so bounceRate × pagePath is correctly refused today. A single table has no such boundary, so v2's registry must enforce explicitly what the schema currently enforces implicitly, or it newly permits nonsense.

1.3Sessions Decided

Sessions are not a table, and they are never counted from a marker event. Session totals come from an incrementally-maintained rollup built by a scheduler job, plus two pieces of client-carried state. (Marker events still exist — see §1.4 — but for what they carry, not for what they count.)

  • Engagement time — engagement_msec rides every outgoing event, GA-style: the time accrued on the current page since the last report, so envelope attribution is automatically correct and loss granularity is one increment, not one page. The hide-time user_engagement event carries only the residue since the last event — fired on any hide at any size; the 10 s threshold gates only the read-time classification, never the send, or it would bake itself into collection — with a content-derived id (hash(session_id + page_ref + seq)): beaconed at hide, then riding the session's next request as parameters — never a separate catch-up beacon — with the server materializing the row, duplicates collapsing at the table. Engaged is SUM(engagement_msec) across the session vs the threshold. Final-page dwell keeps the one irreducible lossy attempt, and is the thing 1.x structurally cannot measure at all.
  • Engaged is derived, not stored — classification at read time: SUM(delta) ≥ threshold OR pageviews ≥ 2 OR key event. An earlier draft carried a sticky client-set flag; it was removed — the pageview and key-event disjuncts are already loss-tolerant rows, threshold-crossing single-page sessions emit delta-carrying scroll events anyway, and in the worst case the flag rode the same lossy terminal beacon as the delta. No stored classification means nothing to disagree with.
  • Bounce means “not engaged” Decided — the single-pageview definition is retired. Measured: on a photo/blog install it marks 73.6% of sessions as bounces regardless of dwell, because 1.x cannot see final-page time — the exact thing engagement deltas measure. v1 history keeps the old definition in its own UI, so no trend steps in either system. Engaged is derived at read time from deltas, pageviews and key events — the sole authority, with no stored flag to disagree with (measured: 201 ms/year for the two-level shape). Engaged as a dimension is punted for v2.0 — the question installs actually ask, “which URLs have the most engagement”, is a one-pass SUM(msec) GROUP BY page_ref over the user_engagement rows, no classification needed. The punt is free to reverse: nothing is stored, so the dimension is a later query-builder feature (measured at 210 ms/year derived) with no schema change. The threshold is per-site, default 10 s, and retroactively tunable — events are immutable, only the lens changes — with a UI annotation at any change date, since historical bounce numbers move with it. Parity expectation, declared in advance: v2 bounce ≤ v1 bounce, and a v2 number above v1's is a defect, not an intended difference.

The design rule this produced: never make a record's existence depend on a single packet. A marker event rides on one beacon, so losing it erases the session while its other events still count. A sticky flag rides on every event, so losing one costs nothing. Values may degrade; records must not vanish. This rule governs several decisions below.

Emit the markers; never count from them. They exist for grain, not merely for payload. A metric and a dimension combine only where a row exists at their shared grain — which is the entire job owa_session's 121 columns do in 1.x, and why removing the session-grain table would make “sessions by landing page” not slow but unavailable. They are also the natural thing to mark as a key event, and they carry the attribution the client knows at that instant.

What they must not be is the basis of a count. GA4 emits session_start yet counts sessions by estimating distinct session ids, precisely because the marker goes missing (consent mode, app lifecycle). v2 counts from the rollup for the same reason, so a lost marker degrades that session's attribution and erases nothing. fsts stays on every event as the redundant floor for new-visitor.

One authority per metric — the trap this creates

If session totals come from the rollup while session breakdowns come from marker events, the two disagree whenever a marker is lost and the breakdown stops summing to the total. Both numbers are defensible, neither is wrong alone, and a user who notices stops trusting the product. So the rollup is the authority for session counts and their breakdowns, which means it carries the session's dimensional context — taken from the session's own events — plus a parameter map for custom variables.

That map matters more than it looks. 1.x spends ten columns (cv1_name…cv5_value) implementing exactly five custom-variable slots. The fixed slots are not a preference — they are what a fixed-width session row forces. On a parameter map the limit disappears, which is the unregistered custom-variable segmentation v2 wants.

The rollup's column list is a rebuild away, not a ceiling. Because it is derived from retained events, adding a session dimension later costs one rebuild — 50.4 s over the full corpus — and applies retroactively to all existing data with no change to collection. That is post-hoc enrichment recovered: the star's one measured advantage in this research (589×) was rewriting a dimension without touching facts, and a derived rollup restores exactly that at the session grain.

Two storage layers — the session table proved unnecessary

An earlier draft kept a session-grain derived table (~30 columns, owa_session's grain reborn). It did not survive review: the v2 session primitives already make every session metric a single-pass aggregate over the fact table. Deltas are additive, so engagement time is SUM(delta) by anything; the engaged flag is sticky, so engaged sessions are a DISTINCT IF; and session-scoped values (source, campaign, landing page) are stamped on every event — a decision made for attribution that turns out to govern query shape. Measured: “sessions by landing page” as a first-event join costs 3.1 s over a year; as a plain group-by over sticky values, 215 ms. The session's context is embedded in its event rows, so the event table is the session-grain table. (This is also why owa_session genuinely is needed in 1.x — its events carry none of this.)

The markers are the breakdown fast path. With session_start in the stream, an interactive breakdown counts marker rows instead of deduplicating session ids — measured via 1.x's is_entry_page proxy: 92 ms vs 373 ms over a year, 218 ms vs 1,855 ms over three. The expensive DISTINCT is confined to the rollup job, bounded to its trailing window. A lost marker undercounts the breakdown and lands in (unknown). Duplicate markers (tab races, queue redelivery) are structurally impossible: the marker's event id is content-derived — hash(site_id + session_id + 'session_start') — so racing writers produce the same row and the second insert is a duplicate-key no-op, with no coordination and across subdomains, where the Web Locks API (origin-scoped) could not reach. A negative remainder is therefore a pure defect signal. The derived session table demotes to an optional materialization: derived state an install can add later with one rebuild if breakdown latency outgrows these shapes, a cache with a trigger condition rather than architecture.

Where a total and a breakdown meet on one screen, the total is authoritative and the API closes the gap — a synthetic row with dimension value (unknown) and the remainder as its metric value, which is simply true: sessions the total can see and the breakdown cannot attribute. The invariant “breakdowns sum to totals” is enforced at the API envelope rather than assumed from storage, and v1 already has the seam — result sets carry aggregates beside the dimensional rows. Two rules keep it honest: the row appears only for a positive remainder and is labelled (unknown), never blended into (not set); and a negative remainder is never clamped — breakdown exceeding total means a defect, and absorbing it would silently convert the parity harness's clearest bug signal into invisible correction.

Measured — the cost depends on how rich the stream is

1.x averages 2.10 events per session and 1.15 sessions per visitor, measured across two live installs. At that density the two markers would add roughly 89% to event volume, which is what made a flat rejection look reasonable.

But that density is an artefact of 1.x tracking almost nothing but pageviews. With the automatic events above — scroll, engagement, clicks, form interactions — a v2 session is more like 6–8 events, and the same two markers cost 25–30%. The marker overhead is inversely proportional to stream richness, so it falls as v2 does its job.

Recordings are not events. A domstream chunk becomes an attachment to a page_view, with the payload stored outside the row. Promoting chunks — or worse, their samples — to events would swamp the table: one measured corpus held 229,663 chunks carrying 5,767,986 pointer and scroll samples.

1.5Visitor identity Decided

The one dimension that cannot be content-derived — everything else in v2 hashes from its own value, but a visitor is arbitrary and must be assigned, carried and trusted.

Defect carried forward from 1.x

The visitor id looks 63 bits wide because it lands in a BIGINT. It is a 10-digit unix timestamp followed by 6 and 3 random digits, so inside any one second the space is 10⁹ — about 30 bits.

Expected collisions per year: 1.4 at 10 new visitors/sec, 156 at 100/sec, 15,752 at 1,000/sec. Each one silently and permanently merges two people.

Not a competitive gap — GA's _ga uses the same construction with one more bit. Correction: the entropy cannot be improved. The construction uses 60.6 of the 63 bits a signed BIGINT allows, and re-dividing the budget is provably worthless — coarsening the time bucket by k multiplies ids-per-bucket by k (pairs by k²), divides bucket count by k, and grows the random space by k, so k cancels; measured across second/minute/hour/day granularity the collisions per year are identical. The rate depends only on the total budget and arrival rate: ~0.8/year at 10 new visitors/sec. An accepted, quantified limit, not an open defect. The discarded salt was removed instead (PR #1017) — it could not be honoured for the same reason.

  • is_new_visitor stops being a marker and becomes derivable from the first-seen timestamp already carried on every event — the same rule that governs sessions.
  • Known users resolve at collection time only. Events collected before someone identified themselves stay anonymous forever. Same answer as goals and bot reclassification, for the same reason.
  • Cross-device requires a site-supplied user id or does not happen. No fingerprinting, no IP-and-user-agent heuristics — a probabilistic join produces a number nobody can check.

1.6Freshness and the API Decided

Two freshness tiers, and they separate helpfully. Cost tracks window width, not table size — so a thirty-minute window is trivial against raw events while a year is not. The rollup buys breadth, not recency.

ViewReadsFreshness
Realtime — “what is happening now”raw events, short windowimmediate
Historical — “last month by source”rolluplast job run

So the freshest number in the system is the most naively computed one, and “is my tracking working?” — the question that must never be stale — never touches a summary.

Realtime is one screen, not a mode on every report Decided

1.x expresses realtime as a Live View toggle on every report, and what that does is re-run the historical query more often. Each widget owns a setInterval calling getNewResultSet() — its full query, over the full period. On the traffic report that is nine widgets, so Live View across thirty days issues nine full-period aggregations every fifteen seconds, thirty-six queries a minute, to learn about whatever arrived in the last fifteen.

The cost scales with period width × widget count and not at all with how much changed, which is the tell: it is asking a historical question to get a realtime answer. The two tiers above exist precisely because those are different questions with different costs.

So realtime becomes a single dedicated screen — a short window over raw events, answering “what is happening now” and “is my tracking working”. That is the question the table above says must never be stale, and on a narrow window it is cheap by construction: one query, one partition, no summary touched. It is also what GA ships, and it removes the per-report auto-refresh control along with the per-widget polling behind it.

What this does not fix, and should not pretend to. Historical reports remain stale for the current day, because they read the rollup and the rollup runs on a schedule. The answer is composition rather than polling — a period metric is rollup(closed days) + raw(today), where closed days never change and so cache indefinitely, and only today's slice is volatile and bounded to one partition. That makes every report current without any refresh loop, and it is worth doing on its own merits. Recorded here as the follow-on, not folded into this decision.

Measured — the trap this creates

Partitioning is on yyyymmdd, so the obvious way to write “last 30 minutes” does not prune, and is unselective enough that the optimiser abandons the timestamp index too:

The date bound belongs in the query builder, derived from the time bound — never left to whoever writes the report. This trap exists in 1.x today.

Eventual consistency is a rollup property, not a scheduling one. A rollup that advances a watermark can never converge: an event arriving after the watermark passes its own timestamp is not late, it is lost. So the rollup recomputes a trailing window idempotently. The window is the lateness horizon, and it is the number a test asserts against.

The API is the contract for both UIs. Metric and dimension discovery already exists — resultSet.relatedDimensions is what feeds the existing explorer widget's pickers — so v2 formalises it rather than inventing it. Freshness belongs in the response envelope beside the row count, because it is a property of a result set, not of the installation.

1.7The UI layer Decided

  • Reporting: client-rendered against the API. Charts and the grid rest on abandoned jQuery plugins (flot, jqgrid), which have to be replaced regardless.
  • Admin: stays server-rendered. It is forms and tables; a SPA buys nothing.
  • Reports become JSON. Most existing reports are one shape wearing different labels, and the bespoke remainder are largely dashboards — so a generic widget format with grid layout descriptors covers both, and can be retrofitted into 1.x additively.
  • Realtime is its own screen, not a refresh toggle on every report — see §1.6. One narrow view over raw events, which retires the per-widget polling that made Live View cost nine full-period aggregations every fifteen seconds.
  • Both reporting UIs run side by side for as long as wanted, sharing one session. A separate login for each would make comparison tedious enough that nobody does it — which turns the overlap period into a rubber stamp.
  • The charted metric is chosen by the reader, not by the report. Shipped in 1.x — clicking a metric box redraws the trend on that metric, and the boxes mark which one is charted. This paragraph used to end “there is no click handler on a metric box anywhere in the reporting JS”; there is one now, and chartMetric already means what the next paragraph says it should. Kept here because what v2 inherits is the reasoning, not the diagnosis: the result set already carried every series, so the only thing missing was a way to ask.

    This changes what the key means, which is why it belongs here rather than in the format: chartMetric stops being the charted metric and becomes the one charted first. Its absence keeps its current meaning — draw no chart — because a report that wants no trend is a different statement from one that has not chosen a starting series.

1.8Privacy and retention

  • Anonymise by default. The implementation exists; the default is simply wrong for a privacy-positioned product.
  • Installation-wide retention, enforced by a scheduled job, with a real default rather than “forever” — deliberately not per site, see §4.5.
  • An erasure command — forget visitor=<id> — reaching events, recording payloads and rollups, and tested, because an erasure path that silently misses a table is worse than none.
  • Retention and erasure share mechanics and must not share a code path. One is time-based and bulk; the other is subject-based and exact.

The single table cuts both ways here: erasure by visitor_id becomes one delete in one place, but denormalisation means an email in a URL query string now sits on every event that saw it. Erasure has to scan, not look up.

1.10The tables Decided

The column-admission rule (revised): a field is a column if its name is known at release time and it is scalar; params (JSON) is reserved for what cannot be a column — site-defined keys unknown at release time (unregistered custom variables; the alternatives are user-controlled DDL, a forbidden registration step, or a forbidden EAV join) and nested arrays (commerce items, which cost 1.x a separate fact table and a join). Params buys nothing else: the wide prototype measured storage as a wash, JSON extraction is slower than a column, and MySQL 8 INSTANT ADD COLUMN removes the ALTER cost for release-known fields. Columnar stores agree more strongly — wide and sparse is their native shape, and their JSON shredding covers the dynamic keys (one param key, one type, enforced at ingest). owa_event lands at 40 columns against owa_request's 58 + owa_session's 121.

Indexes as measured in the prototype: PK (id, yyyymmdd), site_date, site_type_date, session, visitor; partitioned by RANGE on yyyymmdd under the existing rotate job. Deliberately absent, each per a settled decision: any engaged flag, is_new_visitor, entry/exit flags, eight date parts, all dimension FKs — and bot rows entirely, refused at ingest.

The midnight rule — re-derived after server materialization, still necessary. Dedup rides PK (id, yyyymmdd) (a partitioned table cannot have a unique key omitting the partition column), and two cases still hand a second attempt a fresh receipt date: the engagement residue (beacon and retry are independent arrivals) and racing tabs at session start. Idempotent events therefore derive yyyymmdd from the timestamp embedded in session_id — deterministic on every attempt; the entropy fix must keep the guid's time prefix. Pinned alongside: ts is stamped once at edge receipt and travels with the queue item, which is what keeps at-least-once redelivery off this list.

owa_rollup_day — grain (site_id, yyyymmdd) and nothing else: events, pageviews, sessions (the reconciliation authority), engaged_sessions (threshold applied at build; a change rebuilds, ~50 s measured, UI-annotated), visitors, new_visitors, engagement_msec, key_events, revenue, and built_at — the as-of value the API freshness envelope reports. Bounce rate is 1 − engaged_sessions/sessions and earns no column.

Two logical stores. The application tables (sites, users, config, goals, job state) require a SQL store — MySQL-class, transactional, never abstracted away. The reporting tables (owa_event, owa_rollup_day, the payload store) default to the same connection but accept a separate store via a second DSN — a dedicated MySQL or the columnar path. The rule that makes the split real: no reporting query ever joins an application table — site_id arrives as a literal, key events are stamped at ingest — so the two stores are never assumed co-located. Ingest and the rollup job write only the reporting store; site deletion becomes two operations, with orphaned events invisible to queries and reaped by retention. Derived state lives beside what it derives from: owa_rollup_day and any later materialization go in the reporting store, whichever engine that is — rebuildable from that store alone, so the store stays self-contained and a backend migration is “copy events, rebuild summaries”. The scheduler's job state stays in the application store; job state is not job output. The rollup's replace-whole-day-rows maintenance is also the batch shape columnar engines handle well.

owa_event_payload — recording chunks as attachments: (event_id, yyyymmdd, payload), partitioned on the same scheme so payload retention is the same partition drop, on a shorter window than events since nothing is derived from payloads.

Part Two

Derived dimensions declare a kind, not SQL Decided

Some new dimensions are functions of columns rather than columns — sourceMedium and firstSourceMedium concatenate two, and newVsReturning maps one (EVENTS.html §7.7, §7.12). The tempting shortcut is to let each carry its own SQL, which works until the reporting store is not MySQL — and §1.10 deliberately holds that door open behind a second DSN. Then a store move rewrites every derived dimension by hand.

The dialect layer does not cover this today: MysqlDialect abstracts DDL and introspection — partitioning, keys, indexes, session sql_mode — and has no expression surface, nor an interface for a second implementation to satisfy.

So a dimension declares its kind and the dialect renders it, and the reason that is cheap rather than a mini-language is that the column-admission rule keeps the set small and closed. Everything proposed so far needs three: concat, map and datePart. That makes a store migration O(kinds), not O(dimensions) — three renderers to write once, rather than a bill that grows quietly every time somebody adds a dimension.

Worth settling before the first one is built. Once dimensions carry SQL strings, converting them means recovering intent from expressions, which is precisely where the report controllers were before they became configuration — and the narrowing that made that safe was the same move: names from a known list, never code (§1.7).

Metrics too — but replace the formula evaluator first Open

The same argument one layer over, where it is half-built already: ConfigurableMetric supports count, distinct_count, sum and calculated, but only 6 metrics are registered through it against 22 class references, and the calculated type has no registrations at all. The classes are declarations in class clothing — BounceRate is six setters and a formula string, and no metric class contains SQL — so the conversion is mechanical, exactly as the report controllers were.

The payoff is bigger than for dimensions, because only base metrics touch the store at all: three aggregate kinds, three renderers. Calculated metrics are arithmetic over other metrics' results and need no SQL whatsoever, so they port for free. Six renderers total covers both surfaces (EVENTS.html §7.13).

The conversion is additive; the evaluator is not part of it. Formulas are run through ResultSetManager::evalFormula(), which @ eval()s a PHP string — but moving a shipped metric from a class to a config entry does not move the trust boundary. All 8 formulas in the tree are repo-authored and stay repo-authored, so nothing in ResultSetManager needs to change. The parser is the prerequisite for a user-authored metric builder, a separate later feature — and a plain four-operator grammar would not even cover today's set, since round(actions / visits, 1) needs function application. Separately and on its own terms: the @ means a malformed formula falls through to 0, so a broken metric reads as a real zero.

The version selector already exists — it is the entity Measured

The open question behind all of the above was whether renovating v1's metrics and dimensions is genuinely additive for v2, or whether it drags a rewrite of the query layer behind it. It is additive, and by a wider margin than expected: ResultSetManager is retained unchanged in v2 — it already holds the combination logic and the selection of summary tables over fact tables — and the one thing it appears not to know, which definition set to use, turns out to be something it already resolves.

Metric lookup is keyed by entity, not by name:

$this->metricObjectsByEntityMap[ $this->baseEntity->getName() ][ $metric_name ]

registerMetric() stores a list per name ($this->metrics[$metric_name][] = $map), and the registerMetricDefinition() docblock makes it the contract: “the entity to use when calculating this metric — you must register the same metric for each entity that it can be calculated on.” One name, several implementations, chosen by the entity the query lands on. That is precisely the mechanism that already lets visits come from owa_session or from a summary table, and v2 is just another entity in that pool — no version flag, no namespaced metric names, and no rewriting of report configs at cutover.

This is not a new pattern; visits is registered twice today.

'name' => 'visits',  'entity' => 'base.session',  'column' => 'id'
'name' => 'visits',  'entity' => 'base.request',  'column' => 'session_id'

Same name, same label, same metric_type; different entity and different column, because the concept is expressed differently in each table. Nothing is called sessionVisits or requestVisits. v2 adds a third registration and renames nothing — the entity-keyed lookup is what avoids a naming scheme, since name-only resolution would force v2Visits and a rewrite of every report config. The name is the concept; the entity is where it is computed. Version is a query scope, like siteId and period — visits already means different numbers per site and per date range without that being part of its name.

Calculated metrics inherit it for free. Children resolve through the same map, so a formula never names a store and the version rides in on the children. Six of the eight formulas in the tree become v2-correct without being touched.

The one genuine change is where the base entity is picked. Today the candidate entities are sorted by getSummaryLevel() and the highest wins; drop v2's event entity into that pool and the version gets decided by summary-level niceness, which is an arbitrary basis for that particular choice. The fix is a filter on the entity pool before the niceness sort — version by context first, summary level within it — not a new resolution path. And the version need not be tagged onto metrics at all: the entity already implies it, so it is one property on the entity plus one filter in the manager.

Version context must be required, not defaulted

The deeper reason is an invariant, not a usability worry. The two visits registrations above are semantically equivalent — a distinct count of session ids answers the same question from either table — and that equivalence is exactly what makes automatic summary-level selection safe: every candidate answers identically, so take the cheapest. v1 and v2 visits are not equivalent (§3.3), so putting them in one pool violates the assumption the selector was built on.

Hence a partition, not a preference: within a version the candidates are equivalent and automatic selection stays correct; across versions they never are, and selection must not be able to cross. And hence a missing version context is an error, not a default — a default is precisely a silent crossing, showing v1 numbers to a reader who believes they are looking at v2.

Note this is the mechanism being additive, not the numbers being equal (§3.3). The property worth having is that the architecture accommodates the divergence honestly: visits meaning something different per version is directly expressible, rather than being papered over by a shared name.

1.12“(not set)” is a presentation choice, never a stored value Decided

Measured 16 tracking properties in modules/Base/Module.php declare 'default_value' => '(not set)'. Because those properties are required, the string is written to the fact row on every event that does not carry a real value — user_name among them, so on a default install every row carries the literal text.

This is the §1.12 problem in a different costume. A magic string is not absence; it is a value that merely looks like absence, and the difference shows up everywhere downstream. It groups as its own bucket, so a pie over the dimension draws a “(not set)” slice indistinguishable from a real category. It sorts among real values. It cannot be told apart from a visitor who genuinely typed that. And the codebase already knows it is lying: Visitor.php checks != '(not set)' before using a name, and TrackingEventHelpers does the same for REMOTE_HOST and search_terms — three separate places reconstructing an absence the schema threw away.

v2 stores absence as NULL and decides the label at render time. The reporting layer already formats values; “show nothing as (not set)” is a formatter's job, one place, changeable without touching data, and translatable. Baking it into the row makes a display string permanent and unrecoverable — the one thing §1.10 says facts must never be.

Follows the same rule as the boolean columns below it: the store records what happened, the presentation layer decides how to say it. Note this narrows what a nullable column means rather than widening it — NULL becomes unambiguously “not provided”, which is only useful if the write path never also writes a sentinel meaning the same thing.

1.12Boolean columns carry three values Open

A two-state fact must not be storable as three. In 1.x the boolean fact columns are nullable with no default, so is_repeat_visitor holds 1, 0 and NULL — and every one of those is a distinct GROUP BY bucket. A pie over the dimension draws two separate slices that both format as “No”, which is how this was found.

The cause in 1.x was a derivation that returned true for one branch and fell off the end for the other (setRepeatVisitorFlag, unchanged since 2015). That specific bug is fixed, but the shape is the problem: nothing in the schema, the entity layer or the ingestion pipeline stops a write path leaving NULL in a column that has only two meanings.

Update, 28 Aug — fixing the derivation was not enough, and the reason generalises. Rows written before that fix still hold NULL, so the third bucket survives in the data whatever the writer does now: the pie was still drawing two slices labelled “New” on a live install, months after the derivation was corrected. The client half had to change too — the chart now sums by label rather than emitting one slice per row, because a valueLabels map that folds two values onto one name is a statement that they mean the same thing, and a renderer that still draws them apart contradicts it. Two things for v2 follow: NOT NULL DEFAULT 0 fixes new writes and nothing else, so a schema that has ever permitted the third value needs a migration to close it; and any renderer that groups by a labelled value must fold labels, not rows.

For v2:

  • Declare booleans NOT NULL DEFAULT 0. The storage should refuse the third value rather than rely on every writer remembering. 1.x cannot retrofit this cheaply — it is an ALTER over every install’s session and fact tables — which is exactly why it belongs in a schema that is being defined rather than migrated.
  • Give the type a formatter, not each report. A boolean dimension should render as Yes/No wherever it is shown, from its declared type. 1.x now does this, and the same seam should exist in v2 rather than every widget re-solving it.
  • Let a report rename the values. Yes/No is the correct default and a poor label for a specific question — “New/Repeat” reads better on a visitor-type chart. 1.x added a per-widget valueLabels map for this; keep the split, with the type supplying the default and the report overriding it.
  • Decide NULL’s meaning where it is genuinely unknown. Some flags really do have an unknown state. Those want an explicit three-state type, not an accidental one.

Open question: whether 1.x should backfill the existing NULLs or normalise at read time. Reporting currently cannot express a normalised column — the dimension registry prefixes a table alias onto whatever it is given, so COALESCE(...) is not expressible as a dimension today.

Additive work in 1.x

What ships now, reduces risk, and is inherited by v2 rather than redone.

2.1Why this matters more than it looks

Every item here is proved against real traffic before v2 depends on it, and each one narrows what the rewrite has to get right on the first attempt. The evidence that this is the correct posture is recent: converting one id width across two installations took five pull requests, a storage upgrade and most of a day, with tracking dropped in the window where the flag and the data disagreed. A total schema change is not that problem scaled up — it is a different and much worse problem, and the way to survive it is to arrive with most of the pieces already running.

Because the server fans a single tracker's events out to both pipelines, the wire format no longer has to satisfy v1 — compatibility is a server-side translation. 2.5Order of operations Decided

Sequenced on three rules: bugs whose cost accrues daily go first, because every day of delay is data you cannot recover; foundations before the things built on them; and the expensive irreversible work last, when the most is known.

Standing precondition — coverage before development

No phase item starts until the behavior it touches is pinned by tests, in the form the work demands. Bug fixes begin with a failing test demonstrating the defect — the test is the bug report. Behavior-preserving work (PDO, cookie consolidation, Util.js, CORS) begins with a characterization suite of current behavior — cookie bytes in both formats, emitted beacons per event type, generated SQL text, endpoint headers — because “same behavior, different plumbing” has no other definition of broke something. Expect the pins to be most of the job; the swap under them is the small half. Every pin is mutation-checked at creation (break the behavior, watch it fail, restore) — a vacuous pin certifies the refactor didn't break what it broke.

Part Three

Migration

Coexistence, not conversion. No 1.x data is ever converted.

3.1One tracker, two pipelines Decided

A single tracker describes each event richly enough that both pipelines can consume it. The server fans one received event out to both — v1's handlers write the star, v2's write the event table — and at parity the fan-out to v1 is switched off. Nothing about the page changes on that day.

Two trackers would have split each site's data by which snippet happened to be deployed, so v1's history would step or stop the moment a site upgraded — destroying the value of the thing being kept.

3.2Early cutover, per feature Decided

Fan-out is per event type, not global. A feature skips the dual-write period entirely when both hold:

  1. v1 has no history worth preserving for it — nothing to strand, no oracle to compare against
  2. keeping it dual-written would mean renovating v1 storage to carry data only v2 can use

Domstreams qualify on both. Everything v2 changes about them is storage-shaped: a recording becomes an attachment rather than a parallel fact row, the payload moves outside the row, the encoding becomes delta tuples plus gzip (~30× measured). Dual-writing leaves only bad options — either the new capture has nowhere to land, or owa_domstream is renovated to accept a format v1 will never report on. Heatmaps follow, being built on the same capture.

3.3The parity harness — two instruments, not one Decided

Both pipelines consume identical events, so v1 can serve as an oracle — but only below the session boundary, and an earlier draft of this section did not say so. The correction matters enough to state first, because it changes what this harness is for.

v1 is not an oracle for anything session-scoped

This section already made the argument for attribution — parity there “would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right.” That reasoning is not special to attribution. v2 keeps the event and changes the session, so it applies to everything the session model touches.

And the divergence propagates. Per-site session stores give site B its own session where v1 shared one; sessions are created only by page-view events; the store is withheld until sendAccepted. So visits is a different number by design — and visits is the denominator of 6 of the 8 formulas in the tree. Bounce rate, pages/visit, actions/visit and revenue/visit all diverge without anything about their own definitions changing. Separately, 18 of 34 metric classes bind to base.session directly.

Which means the “intended differences” list below is not five enumerable items, it is most of the surface — and the warning attached to it turns on itself. An exclusion list that large is not an exclusion list; it is the majority case, and a real regression hides comfortably inside it.

So what was described as one harness is two instruments, and they must not share a verdict:

It is integrity empty, and every model change carrying a stated, tested expected behaviour. Collapsing those into one number is exactly what would let an expected difference shelter a real one.

Attribution has a warm-up — it cannot be cut over cold

Today attribution is decided in the browser. setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the decided result — source_id, medium, campaign_id — not the observation that produced it.

Two consequences for the sequence. Existing history is not a usable touchpoint log, so the server-side model cannot be validated by replaying it — parity against v1 attribution would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right. And original is a sliding 60-day window, not first-touch-ever, so a server-side implementation produces nothing trustworthy until it has observed 60 days of traffic.

Therefore recording raw touchpoints is itself an additive 1.x item, and an early one — earlier than the switch-over it serves. Start it and the warm-up runs in the background while other phases proceed; start it at cutover and it becomes a 60-day hold on the one part of v2 that cannot be hurried.

3.4Profiles carry the version Proposed

Everything above resolves the version at query time, and every automatic signal for doing so fails. A date boundary cannot work: §3.2 makes cutover per-feature so there is no single instant, dual-write means both stores hold the same period, the switch-off is an administrator's action rather than a release date, and the queue is asynchronous so an event accepted before a switch can land after it. Coverage watermarks fail for the same reason — during overlap both stores answer, and the data cannot say which is authoritative. An install-wide setting fails differently: since no data is migrated, v1 holds the history permanently (§3.5 keeps v1 reporting precisely for that), so a global flip would blank every historical report.

The proposal is to stop resolving it at query time and carry it in the data model instead. Decouple the tracked website from the profile that measures it: one website may have several profiles, and a profile declares its version. The whole experience fans out from the profile — a v2 profile shows v2 navigation, v2 reports, and queries the v2 REST endpoint. This is the path GA took to GA4, and it dissolves rather than solves the open questions:

QuestionHow the profile answers it
Which version does a query use?The profile's. Never inferred, timed, or defaulted

CutoverPer-site opt-in, no big-bang flip. Rollback is “use the other profile”

What it requires — and it is smaller than it sounds Measured

site_id is md5($domain) (Site::generateSiteId(), and inline at SiteManager.php:44), so two profiles for one domain are impossible by construction. Only three call sites derive it, and just one re-derives at runtime — ServiceUser.php:283, in the permission path, which is the edge needing care and tests.

Two things are already in place. site_family exists as a column on owa_site and is written but never read anywhere — a dormant grouping slot, so “tracked website” can be defined freshly rather than migrated. And the per-site session store (owa_s_<siteId>) already gives two profiles on one domain independent session cookies, which is both correct and exactly GA's _ga_<property>.

Do not rewrite existing site_id values

Every site_id in the wild is md5(domain) and every fact row references it. The change is to stop deriving new ones and treat the column as opaque — existing identities keep their values and existing data is untouched. Decoupling identity from derivation does not require reissuing the identities already handed out.

No second tracking tag, and no second tracker. An earlier draft of this section argued for one; that contradicted §3.1, which is Decided and whose reasoning still holds — two trackers split a site's data by which snippet happened to be deployed, so v1's history steps or stops the moment a site upgrades, destroying the thing v1 is being kept for. The fidelity argument was also backwards: the tracker is extended in Phase 3, so it already emits v2-rich events and the server degrades them for v1 — not v1-poor events upgraded for v2. There is no fidelity gap to protect against.

So the profile model requires no client change whatsoever: one tag, one event, and the server writes each received event into every profile configured for that website. The site → profiles mapping is server-side, so the page never learns that profiles exist, and §3.1's promise holds — nothing about the page changes on cutover day.

Independent of v2, md5(domain) already prevents tracking two configurations of one domain, renaming a domain without orphaning its data, and expressing one property across several domains. The decoupling is additive 1.x work with standalone value.

What the profile does not do is spare ResultSetManager. It settles where the version comes from, not how the manager acts on it, so the entity-pool change of §1.11 survives intact and is still the work: resolve the version from the profile behind siteId, filter candidate entities to that version before arsort($niceness), and error when none resolves. setSiteId() today only records a query param and a constraint rather than loading the site, so there is a little plumbing from siteId to a version — but nothing new threads through the REST API or the report configs, which is precisely what the profile model buys: an unambiguous input already present in every query.

Nothing feeds the manager a “v2 list” Measured

A fair question is what supplies ResultSetManager with the v2 metric and dimension sets. The answer is that no new channel is needed. getMetricEntities() asks the service singleton for every registered implementation of a requested name, instantiates each, and keys it by its own entity:

$classes = $s->getMetricClasses($metric_name);   // every implementation
foreach ($classes as $map) {
    $m = metricFactory($map['class'], $map['params']);
    $this->metricObjectsByEntityMap[ $m->getEntityName() ][ $metric_name ] = $m;
}

So a v2 registration appears alongside the v1 one automatically. Dimensions behave identically — registerDimension() loops $entity_names into one entry per entity, and lookup is denormalizedDimensions[$name][$entity]. The v2 set is just more registrations carrying the v2 entity, or more config entries once §1.11 lands. This is the same reason report configs need no version field.

Which relocates the filter. Because implementations are built before anything is selected, the version filter belongs in getMetricEntities() — skip a class whose entity is the wrong version, so wrong-version objects are never constructed — rather than at the niceness sort, where they already exist. And the recursion into child metrics means filtering children constrains their calculated parents for free.

Scope the catalog by entity, not by version Decided

Refinement of the section below. Partitioning by version works but spreads a version concept through every accessor, and concepts like that leak until they are everywhere. Keying off the entity achieves the same isolation using something already present in every registration and already understood across the codebase: a profile determines a candidate entity set, the accessors scope to it, and the word “version” survives only in the profile record and the migration machinery — which is the one place generational schema changes are actually relevant.

It is still a single choke point rather than scattered filtering: every consumer goes through the accessor, so there is one place to be right instead of ten. And it improves the API independently of v2 — getAllMetrics() today returns everything regardless of whether it is queryable in the current context, so an entity-scoped picker is more correct even with one generation.

An earlier note suggested partitioning might subsume it; under entity-scoped accessors it is the foundation, because the overwrite happens at registration, before any read scoping can apply — both registerDimension() and _loadDimensions() write flat name-keyed. Calculated metrics have no entity

They carry child_metrics and a formula instead, so an entity-scoped getAllMetrics() must include a calculated metric when all of its children resolve within the scope and exclude it otherwise. This falls out of recursion naturally, but it is the one case where scoping is not a direct property test — and getting it wrong silently drops bounceRate and its siblings from the picker rather than erroring.

Superseded: partition by version Measured

Kept for the measurement, which still stands; the entity-scoped approach above is preferred.

The paragraphs above proposed registering the v2 set into the existing registry and discriminating downstream — a filter in getMetricEntities(). That is wrong, and the reason is enumeration rather than resolution. getAllMetrics() and getAllDimensions() return the flat, name-keyed map, and they are consumed in ten places:

ConsumerUse
ResultSetManager :930, :937, :2364internal resolution
CustomReports.php :1371, :1378custom report definition
CustomReportEdit.php :220, :226, :243, :270, :282the metric/dimension picker UI and its validation

The picker is built from array_keys( getAllMetrics() ). Array keys are unique, so with both sets registered it offers one visits that silently means two different things, and the validation loops beside it are equally version-blind. Selection never gets the chance to be wrong, because the wrong definition was already offered and accepted as valid. A filter at one consumer fixes one consumer.

So partition at the aggregation points instead. There are exactly two, and they are the only places module registries merge into the service:

_loadMetrics()    : $this->metrics    = array_merge_recursive( $this->metrics, $module->metrics );

Group by version there rather than flattening, and resolve accessors within a version. Nothing downstream filters anything, because the other version is not in scope: the picker lists one version's names with no change to CustomReportEdit, validation follows automatically, ResultSetManager needs no niceness-sort filter, and the name-collision blocker below dissolves — separate partitions cannot overwrite one another, so keying $this->dimensions by entity may prove unnecessary.

The distinction is scoping the registry once versus remembering to discriminate at ten consumers. Open: the service is a boot-time singleton, built before a query knows its profile, so either every accessor takes a version or the version becomes request-scoped ambient state. The explicit parameter is safer — ten call sites is tractable, and it keeps the version visible at each consumer rather than hidden in ambient state, which is the same silent-wrong-answer failure in a different costume.

BLOCKER: the normalized dimension registry is name-keyed, so v2 would overwrite v1

The claim above that dimensions behave like metrics is only true for denormalized ones. registerDimension() loops $entity_names but writes to two different shapes:

if ($denormalized) {
    $this->denormalizedDimensions[$dim_name][$entity] = $dim;   // entity-keyed
} else {
    $this->dimensions[$dim_name] = $dim;                        // NAME-keyed — last write wins
}

Measured of 103 registrations: 58 denormalized (safe), 41 normalized against a single entity (the overwrite is a no-op), and 3 normalized against all seven $fact_table_entities — month, userName, priorVisitCount.

This blocks v2 for all 44 normalized dimensions. v1 registers pageTitle against its dimension table, v2 registers pageTitle against the event table, and the second write replaces the first — the v1 definition is gone from the registry before any entity filter could run. No downstream selection can recover it, and renaming is not an option.

Fix: key $this->dimensions by entity, matching denormalizedDimensions, which already has the right shape. getDimension() has exactly one caller (ResultSetManager:970), so the change is that call site plus the registration loop. This is a prerequisite in 1.x: the registry must be able to hold two definitions under one name before a second set can exist at all.

Unverified, worth a trace: the 3 normalized multi-entity registrations keep only the last of seven entities, and $dim['entity'] then drives the JOIN (entityFactory(), getForeignKeyColumn(), $db->join()). date is registered against the same list with denormalized = true while month beside it is not, which looks like an oversight rather than a distinction. Not claimed as a live defect until traced.

Do not add the v2 entity to $fact_table_entities

Dimensions are registered against a shared array: registerDimension('date', $fact_table_entities, 'yyyymmdd', …). Appending the v2 entity to that one variable would make every dimension claim to work on v2 while still naming v1's columns — a one-line change producing broadly wrong SQL, and the obvious-looking way to “add v2 support”. v2 needs its own registrations with its own columns, exactly as metrics do.

Open: the vocabulary (site / profile / property / site_family) wants settling before anything is built, since it will surface in the UI, the API and the schema at once.

3.5Cutover sequence

  1. Ship the additive work in 1.x releases, each standing on its own
  2. v2 creates its tables alongside; the single tracker's events fan out to both pipelines, except for features on the early-cutover list
  3. Run both for an overlap period, comparing the two UIs over the same events — which is what makes it a test rather than an impression
  4. When satisfied, switch off the fan-out to v1 and keep v1 reporting for history
  5. When the history is no longer wanted, a command drops the 20 parallel tables, leaving the shared admin tables untouched

No step is irreversible until the last one, and the last one is the administrator's decision rather than an upgrade's side effect.

Part Four

Supporting decisions

Settled questions that would otherwise resurface mid-build.

4.1Schema versioning Decided

One schema version, one numbered update sequence. An update may touch v1 tables, v2 tables or both. v1 and v2 are not two schemas that coexist; they are one schema containing both shapes — which removes the version pair, and with it any compatibility matrix or cross-sequence ordering question.

This is smaller than it sounds, because the mechanism already works this way: only Base has ever had updates, install() builds tables from entity registration and never replays updates, and the apply loop already sorts numerically, stops at first failure and resumes.

The sharp edge

A dropped v1 is a supported state, so every update written afterwards must tolerate those tables being absent — not just ones that mean to touch them. The apply loop stops at the first failure, so one update assuming owa_session exists blocks every later update for those installs, and isUpdateRequired() then wedges them out of the admin over a table they deliberately removed.

Worth a helper on the update base class rather than a documented convention — the failure lands on the update written eighteen months from now.

Measured A fresh install creates both shapes: 19 empty tables cost 27.0 MB, nearly all per-partition tablespace overhead on 15 partitioned fact tables. Cheap enough to accept, and it keeps a fresh install able to serve a v1 beacon without being migrated forward into v1 first.

4.2Scheduling Decided

The scheduler shipped in 1.11 — one crontab line, jobs dispatched from it, per-job overlap locking, level-triggered so a missed occurrence runs once rather than backfilling. v2 needs no new machinery, only a registration.

The convergence rule it already imposes on registered jobs is the same property the rollup needs, arrived at from the other direction: a watermark rollup would be both non-convergent and not eventually consistent. One defect, two symptoms.

New in v2: the scheduler stops being optional. 1.x runs correctly with no cron entry; v2's rollup does not. That belongs in install verification, not in how the software is shipped.

4.3Packaging Decided

Unchanged. Same tarball, same Release Packager workflow, same wizard. No Composer requirement for end users, no build step at install time, no new runtime dependency. The distribution model is the reason a self-hosted tool gets installed at all, and a rewrite is exactly when one is tempted to modernise it into something needing a toolchain on the target machine. The schema changing is not a reason for the delivery mechanism to change.

4.4Testing Decided

The two harnesses of §3.3 are the primary tests — pipeline integrity generated and exhaustive, model characterization hand-written and small. Neither alone is “the” test, and reporting them as one is the failure mode that section describes. Around it: 77 test files and 509 methods today, of which only 8 files are named for star-schema artefacts — most of the suite tests CLI commands, settings, auth, validation, the queue and the scheduler, and ports unchanged. What genuinely expires is the part testing the star's mechanics.

Three hazards, the first two already known here:

  • Order-dependent tests — CI already runs an isolation sweep executing each file alone. More valuable during a rewrite, not less
  • Vacuous assertions — double-quoted PHP needles containing $this-> interpolate away and pass unconditionally. A rewrite writes many tests quickly, which is the condition that produced these the first time. Worth a lint
  • Silently narrowing coverage — a test deleted because it tested the star, never replaced, leaves no trace. A green suite that is green because it asks less

Claims in this plan that are worth nothing untested: the rollup folds in a late event on the next run; an event beyond the horizon does not, but still lands in the event table; running the rollup twice changes nothing; a throwing v2 handler fails neither the v1 write nor the request; the update sequence runs clean with v1 dropped; and generated realtime SQL carries a closed partition-key range — asserted on the SQL, since a timing assertion on a small fixture would pass either way.

4.5Multi-site

The area needing least work: a single event table handles tenancy naturally, site_id is a column, isolation is a WHERE, and it already leads the composite indexes. Permissions are already per-site.

Two things change. site_id becomes more load-bearing — it scopes page identity as hash(site_id + uri) — so it must be immutable. And site_family is written by site creation and read nowhere; it was built for a UI that never shipped, and should be dropped rather than ported.

Retention stays installation-wide, not per site. A partition of the shared event table holds every site’s rows, so varying retention by site could not be a partition drop — it would need a row-level DELETE sweeping every partition, leaving fragmentation behind and competing with live writes. Uniform retention is a metadata-only partition drop, effectively instant, and already implemented. The single table makes the simpler policy the cheap one.
