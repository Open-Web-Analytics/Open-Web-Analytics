IArchitecture

1.1The shape Decided

Every tracked interaction becomes one row in one table, replacing ten parallel fact tables and their dimension satellites. A write is a single insert with no lookups — no session upsert, no dimension check-and-create — and the ids of events that must collapse on redelivery are derived from their own content rather than assigned. The one exception is a new visitor's first session, which also writes the visitor store (§2.9).

1.2Sessions Decided

A session is not a table and not a row. Session context is stamped on every event, so a session is counted from the denormalised table — as a distinct count of (visitor_id, session_id), not of session_id alone. The session id embeds its creation timestamp (§2.1), so two visitors starting in the same second can share one; pairing it with the visitor id makes the count depend only on visitor-id uniqueness, which §1.4 bounds. A rollup, if one is ever added, precomputes the same thing rather than becoming a second authority.

A session starts on a page view, and restarts when attribution changes. Only page-view events create one; a session spanning midnight is split; the store is withheld until sendAccepted; and a new set of attribution tags starts a new session — so the tracker has to notice a mid-session tag change and restart cleanly.

Marker events (§1.3) exist for what they carry, not for what they count.

1.2.1Engagement is measured in deltas

engagement_msec rides every outgoing event: the time accrued on the current page since the last report. Losing a beacon then costs one increment rather than one page.

The hide-time user_engagement event carries the residue since the last event, and fires on any hide at any size — the threshold gates read-time classification, never the send, or it would bake itself into collection. It is delivered once, at hide; losing that beacon costs that increment like any other. Two tabs of one session each send their own residue and both are real — not a duplicate to collapse, since they differ in ts (A.1.32).

Final-page dwell is the one irreducible lossy attempt, and the thing 1.x cannot measure at all.

1.2.2Engaged is derived at read time, never stored

A session is engaged if any of three things is true. No sticky client-set flag is stored, so there is no classification for the derivation to disagree with.

DisjunctWhy it is loss-tolerant

1.2.3Bounce means not engaged

A bounce is a session that is not engaged, by those three disjuncts. The single-pageview definition is retired: it measures beacon count rather than attention. v1 history keeps the old definition in its own UI, so neither system's trend steps.

  • The threshold is per-site, defaults to 10 seconds, and is retroactively tunable — events are immutable and only the lens changes — with a UI annotation at any change date, since historical bounce numbers move with it.
  • Parity expectation, declared in advance: v2 bounce ≤ v1 bounce. A v2 number above v1's is a defect, not an intended difference.
  • Engaged as a dimension is deferred past v2.0. What installs actually ask — which URLs have the most engagement — is a one-pass SUM(msec) GROUP BY pagePath with no classification in it. Nothing is stored, so adding it later is a query-builder feature rather than a schema change.

1.2.4A record's existence never depends on one packet

Values may degrade. Records must not vanish. Anything carried on a single beacon goes with that beacon, which is why a session's identity and context ride every event instead — the session stays countable, and attributable, from any of its rows. The markers are raised server-side in the same atomic write as the beacon carrying their flags, so a marker cannot be lost while its own page view survives — but the beacon itself can be, and then the session has no marker row (§2.13). A delta or a stamped value rides every event, so losing one costs nothing or a single increment. Where a value can go on either shape, it goes on every event.

1.3Events and markers Decided

The event set is tabulated in §2.2.

Two of those events are markers, and no browser sends them. session_start and first_visit are materialised by the server from state already riding the session's first page_view request, so they cost nothing on the wire.

1.3.1What the markers are for

A marker gives a session or a visitor one row of its own. Nothing in this design reads that row yet: totals are a distinct count of (visitor_id, session_id) over event rows, breakdowns group by a stamped column, and acquisition is written by any event of a visitor's first session (§2.9). The marker's value is that it makes a session countable as a row rather than a distinct, which is the cheaper shape over a wide window, and that it is the natural thing to name as a goal event (§1.3.3).

It cannot be duplicated: the id is content-derived, so two racing writers produce the same row and the second insert collapses at the table. It can be lost, with the beacon that raised it — see below.

1.3.2Goal events are author-named events Decided

1.x had twenty numbered goal slots. v2 has none: an author names a goal event and gives it an event type and a condition, and when the condition matches the server materialises an additional row whose event_type is that name — the marker mechanism again, pointed at a condition the author wrote. Three rules come with it:

  • the materialised row is never counted as an ordinary event;
  • the triggering event stays an ordinary page_view with is_goal_event = 0, since flagging both would double-count and blur which row is the conversion;
  • the event_type vocabulary therefore stops being closed — intended, but stated so nobody discovers it by naming a goal event page_view.

They are called goal events, because a 1.x installation has goals and the people using it say goals. The numbered slots are already gone in 1.x, so v2 inherits authored goal events rather than introducing them — counting, per-goal metrics and the once-per-session clamp are §2.20.

1.4Visitor identity Decided

A visitor is arbitrary: it must be assigned, carried and trusted, where a page or a referrer is just a value a report groups by. That makes it the one identity v2 has to mint, and the only one it can get wrong.

  • The entropy limit is accepted, not fixed. The id is a unix timestamp plus 9 random digits. The budget is nearly all spent — 60.6 of a signed BIGINT's 63 bits — but it is spent on the timestamp, so within any one second only about 30 bits of it separate two visitors. It cannot be improved: re-dividing the budget provably cancels, because coarsening the time bucket by k multiplies ids per bucket by k and grows the random space by the same k. The rate is ~0.8 collisions/year at 10 new visitors/sec, and each one silently merges two people. The discarded salt was removed rather than honoured (PR #1017).
  • is_new_visitor becomes derivable from the first-seen timestamp carried on every event, rather than being a marker.
  • Known users resolve at collection time only. Events collected before someone identified themselves stay anonymous forever — the same answer as goals and bot reclassification.
  • Cross-device requires a site-supplied user id or does not happen. No fingerprinting and no IP-and-user-agent heuristics: a probabilistic join produces a number nobody can check.

1.5The storage layers Decided

LayerGrainStoreServes
Rawevent, as receivedrow store — it takes one insert per beaconrealtime, and the record of what was observed
Denormalisedevent, enrichedrow or columnar — written only in bulk, by the passevery report; the table queries actually hit
Rollup Deferredwould be day × traffic sourcefollows the denormalised tableNot built, and deliberately not specified. A rollup is derived from the layer above by definition, so it can be added with one job and one backfill — no collection change, no migration, nothing to re-derive. Measured against this corpus it saves nothing yet: a month is 106 ms straight from events, and only an all-time query is slow enough to want it (appendix). Build it when a measured query is too slow, and let that measurement choose the key

The fact table stops being primary. Events land in raw exactly as they arrived. A pass reads that and writes a denormalised fact table with session- and user-scoped values materialised onto every row. Queries hit the denormalised table; raw is the record of what was observed.

The two layers have opposite write patterns, so they need not share a store. Raw takes one insert per beacon, which a row store handles and a columnar engine does not. The denormalised table is never written a row at a time — the pass builds a whole partition into staging and swaps it — which is the load pattern a columnar store wants. So the design has to admit a second data source for the analytics table, with its own loading path: bulk load, partition replace, no row-level updates (§2.1).

The whole scheme rests on a derived table being rebuildable. You never UPDATE a fact row, you regenerate a partition — so no-retroactive-fact-updates survives intact and stops being a constraint that forces values onto the wire. The pass is §2.7; the partition cycle is §2.8.

1.5.3What to carry and what to derive

The rule is not “carry what cannot be derived”: first-seen and session count are both readily derivable and are carried anyway. It is about what kind of thing the value is:

KindTreatmentWhy
Counters and anchors the client already maintainsCarryvid, sid, session count, first-seen, last-hit. The client computed them for its own session decision, so sending them costs a few bytes and saves an expensive per-visitor ordered scan. Correct in raw immediately, with no pass
Resolutions needing server-side dataDeriveSource and medium from the referrer and tags, geography from the address, device from the user agent. The client cannot know these without shipping OWA's tables to the browser
Decisions and modelsDerive, never carryattribs is wrong to carry not because it is reconstructible but because it is a verdict. A model frozen in a cookie cannot be revisited when the model changes

By that rule nps and fsts stay, and attribs goes.

1.5.4The visitor store

v2 keeps one visitor-grain table, for a single value that cannot ride an event: acquisition — the source, medium, campaign, ad and search terms of the visit that created the visitor. It originates in a first session that may be years old, and no later beacon carries it. Everything else about a visitor rides every event already.

  • It holds acquisition written once and never updated, plus last_seen, which exists only to drive the TTL. Column by column it is §2.9.
  • A row expires after N months of inactivity, default 14 — a sliding inactivity window, which is the shape every other vendor uses and roughly where two of them independently land. The default sits deliberately just above the longest cookie that can reach it, Chrome's 400-day cap on any first-party cookie. Below it, a visitor can return carrying an id whose store row has gone; above it, the cookie always dies first.
  • Expiring a row does not rewrite history. Rows already denormalised keep the acquisition stamped on them; only the ability to attribute future events is lost.
  • An expired visitor comes back as a new one, with real attribution. Their cookie is gone too, so is_new_visitor_created fires, a fresh first_visit is raised, and acquisition is resolved from that visit — a referrer-less arrival resolving to direct like any other (§2.6.2), not to the sentinel. They are a new visitor who happens to be the same person, and nothing connects the two — which is the honest answer, since nothing can.
  • Acquisition never falls back to the earliest retained event, which would change the answer every time the window slid forward. Where the pass genuinely cannot resolve it, it writes the sentinel.

The vendor survey and measured lifespans are A.1; the argument that nearly removed this table is A.2.

1.5.5What it costs

Raw plus denormalised roughly doubles event storage before the rollup, recoverable by pruning raw — at the cost of re-derivability past that horizon.

1.6Freshness and the API Decided

Two freshness tiers, and the boundary is where the data physically is. Realtime reads raw, which is immediate. Everything attributed reads the denormalised table, which is as of the last pass. Cost tracks window width rather than table size, so a thirty-minute window is trivial against raw events while an all-time one is not — that is the query a rollup would eventually serve, and it is deferred until one is slow enough to justify it (§2.1).

ViewReadsFreshness
Realtime — “what is happening now”raw events, short windowimmediate
Historical — “last month by source”the denormalised tableas of the last pass

Realtime is a single dedicated screen over a short window of raw events, replacing 1.x's per-report Live View toggle and the per-widget polling behind it.

1.6.1Eventual consistency is a property of the derived table, not of the schedule

A derived table that advances a watermark can never converge: an event arriving after the watermark passes its own timestamp is not late, it is lost. So the pass rebuilds a trailing window idempotently. The window is the lateness horizon, and it is the number a test asserts against.

1.6.2The API is the contract for both UIs

Metric and dimension discovery already exists — resultSet.relatedDimensions feeds the existing explorer widget's pickers — so v2 formalises it rather than inventing it. Freshness belongs in the response envelope beside the row count, because it is a property of a result set rather than of the installation.

1.7The UI layer Decided

  • Reporting is client-rendered against the API. Charts and the grid rest on abandoned jQuery plugins (flot, jqgrid) which have to be replaced regardless.
  • Admin stays server-rendered. It is forms and tables; a SPA buys nothing.
  • Both reporting UIs run side by side for as long as wanted, sharing one session, the v2 one under its own path (§2.23). A separate login for each would make comparison tedious enough that nobody does it, turning the overlap period into a rubber stamp.

1.8Privacy and retention Decided

Retention stays installation-wide and is a partition drop, not a row-level sweep (§2.17). No erasure tooling is specified here.

The single table cuts both ways for erasure: by visitor_id it is one delete in one place, but denormalisation means an email in a URL query string now sits on every event that saw it, so erasure has to scan rather than look up.

1.9One pipeline, and v1’s data migrated into it Decided

v2 collects; v1 does not run beside it. There is no fan-out, no dual write and no overlap period. v2’s tables are built, v1’s history is migrated into them, collection switches over, and v1’s tables are dropped when nobody wants them any more (§2.25).

This is available because v1 is already an event log. owa_request is one row per tracked interaction with foreign keys into ten dimension tables, so denormalising it is a join — the same shape the pass performs, reading a star instead of a flat table. The migrator is §2.21.

What running both would have bought was an oracle, and migration buys a better one. Two live pipelines are compared across nondeterministic timing and cost throughput to do it (A.1.13). Re-deriving migrated rows and comparing against v1’s own reports is the same comparison over fixed input, with no production cost (§2.22).

What it does not buy is an oracle for collection. Every migrated row was collected by v1’s tracker, so the pass and the reporting layer get tested and the new tracker does not — engagement deltas, the session model, consent and the new event types ship against e2e coverage and nothing else. The alternative is to run v2 collection on one site for a window purely as a test and discard the data, which is the fan-out as an instrument rather than as an architecture.

2.1Table layouts Decided

Every field whose name the release knows gets its own column. params (JSON) holds only what cannot be one: site-defined keys unknown at release time (unregistered custom variables) and nested arrays (commerce items, which cost 1.x a separate fact table and a join). Nothing else goes in it: the wide prototype measured storage as a wash, JSON extraction is slower than a column, and MySQL 8 INSTANT ADD COLUMN removes the ALTER cost for release-known fields. Columnar stores agree more strongly — wide and sparse is their native shape, and their JSON shredding covers the dynamic keys (one param key, one type, enforced at ingest). The two layouts below land at 37 and 52 columns against owa_request's 58 + owa_session's 121.

Which layer a column belongs to follows one cut: a column belongs to raw if it is an observation or a mechanical resolution, and to the denormalised table if a pass has to derive it. That is the same cut §1.5 applies to the wire, one layer down.

Raw holds the evidence; the denormalised table holds the reading. The tagged_* columns are what the landing URL carried, written as collected, with referer_url beside them. The pass turns the pair into source and medium — the tag if there was one, otherwise the referrer classified.

Only the landing event carries tags. The landing URL rides the landing beacon and no other (§2.10), so ingest parses the tags out of that event’s page_location and every later raw row of the session holds NULL in tagged_*. The pass reads the session’s first event anyway, for the landing page, so carrying the reading across the session adds no read. session_referer is not in that position: it is session-scoped tracker state and does ride every beacon, so the referring host is on every raw row.

The verdict is never written where it cannot be corrected. Not in the cookie — that is the objection §1.5.3 raises against carrying attribs — and not in raw either. It goes in the derived layer, which exists to be rebuilt, so a fixed classifier re-reads history instead of leaving it wrong.

The cost falls on realtime, narrowly: a live query over raw shows the referring host on any row and the tagged campaign on the landing row, but not the classified channel, and not the landing page for a row later in the session — both are the pass’s (§1.5).

No landing_url column in raw. 2.1.2How an event id is derived

Every event id is derived from the event, by one formula, with no exceptions:

id = wideStringGuid( site_id + visitor_id + session_id + ts + event_name )

Nothing is minted. The edge stamps ts and queues the beacon (§2.1.3); ingest expands it and derives an id per event from inputs that are all on the queue item. A redelivery therefore derives the same ids and collapses at PK (id, yyyymmdd) — which is the whole reason the id is content-derived rather than assigned.

The expansion needs no ordering and no counter. One beacon yields at most one event of any given name — page_view, session_start, first_visit — so event_name separates them whatever order they are built in. That invariant is what the formula rests on: if a beacon ever carries two events of one name, the fix is a per-event ts, not a discriminator bolted onto the key.

The resolution of ts is the uniqueness guarantee. Two events collide only when one visitor and session produce two beacons at the same ts carrying the same event name. At second resolution that is reachable; at microsecond resolution it is not. owa_request.msec is broken in 1.x and deferred to v2 for sub-second ordering (A.1.11) — this is the second reason to fix it, and it sets the unit.

Signed BIGINT, not BIGINT UNSIGNED — changed when the table was built. OWA runs with a permissive sql_mode, under which a negative value written to an UNSIGNED column is silently clamped to 0 rather than refused. v1 has negative visitor ids — PR #1118 exists because of them — so migrating those in would merge strangers into visitor 0, with no error anywhere. The headroom was never needed: wideStringGuid() tops out at 63 bits by construction and a microsecond timestamp is nowhere near it.

The hash is 1.x’s, unchanged. Lib::wideStringGuid(): sha1 of the lowercased string, first 16 hex characters, split into two 32-bit halves with the top bit of the high half masked off, giving 63 bits and always positive. The two halves keep every intermediate inside the integer range: all 16 characters through hexdec() produce a float, which loses precision and whose cast to int is undefined in PHP. Several nodes derive ids for the same content and have to agree on it.

Uniqueness is required within a partition, not globally: the primary key is (id, yyyymmdd), so two events a week apart may share an id with no effect. Note also what this is not — 1.x derives dimension ids from content and mints fact row ids randomly (Lib::generateRandomUid()). v2 derives the fact id too, because a fact that arrives twice is the same fact; two facts that differ in any input differ in their id.

2.1.3Notes on both

Indexes as measured in the prototype: PK (id, yyyymmdd), site_date, site_type_date, session, visitor; partitioned by RANGE on yyyymmdd under the existing rotate job. Deliberately absent, each per a settled decision: any engaged flag, is_new_visitor, entry/exit flags, eight date parts, all dimension FKs — and bot rows entirely, refused at ingest.

Two logical stores. The application tables (sites, users, config, goals, job state) require a SQL store — MySQL-class, transactional, never abstracted away. Raw requires a row store — it takes one insert per beacon, the one thing a columnar engine is bad at. The denormalised table accepts a separate store via a second DSN, a dedicated MySQL or a columnar engine, because the pass never writes it a row at a time: it builds a partition into staging and swaps. Such a source brings its own loading path — bulk load, partition replace, no row-level updates — which is what the pass already does on MySQL. The rule that makes the split real: no reporting query ever joins an application table — site_id arrives as a literal, goal events are stamped at ingest — so the two stores are never assumed co-located. Ingest writes raw; the pass writes the analytics store; site deletion becomes two operations, with orphaned events invisible to queries and reaped by retention. Derived state lives beside what it derives from: any later materialization goes in the reporting store, whichever engine that is — rebuildable from that store alone, so the store stays self-contained and a backend migration is “copy events, rebuild summaries”. The scheduler's job state stays in the application store; job state is not job output. Replacing a whole partition is also the batch shape a columnar engine handles well.

owa_event_payload — recording chunks as attachments: (event_id, yyyymmdd, payload), partitioned on the same scheme so payload retention is the same partition drop, on a shorter window than events since nothing is derived from payloads.

Two things change status rather than behaviour. The scheduler stops being optional — 1.x runs correctly with no cron entry and v2's pass does not, which belongs in install verification rather than in how the software is shipped. And partition-rotate stops being housekeeping: under the two-stage partition cycle a stalled rotation erodes the lead until rows reach pmax, breaking the invariant everything else rests on. It wants an alarm, not a log line. There have been two scheduler-adjacent stalls already.

2.5.1Choosing the interval

The interval and the partition granularity are one decision, not two. Each run rebuilds however much of the current partition exists, so at */15 that is 96 rebuilds a day: on a monthly partition the last of them rewrites a month, and the cost climbs through the month. On a daily partition it rewrites at most a day, flat. A sub-hourly cadence is affordable on daily partitions and not on anything coarser — which is why daily was added to PARTITION_CUTS in PR #1113, additively: nothing adopts it on its own.

Two cadences fall out. A frequent run on the current partition, which sets the attributed-freshness tier; and a less frequent run across the rest of the late-arrival window, which is where a late first_visit is actually picked up.

One constraint from the shipped scheduler: the lock is keyed on the job name, so a single name serialises every partition that job touches. Rebuilding the window in parallel would need per-partition job names.

2.6Ingest Decided

One beacon becomes several events, and the expansion happens at ingest rather than in the pass. The client sends one page_view carrying flags; the server raises session_start and first_visit from them into the raw log.

The test for which side a derivation falls on: a pure function of one beacon goes in at ingest (raising first_visit from is_new_visitor_created); anything needing other events goes in the pass (acquisition source, session finalisation). Expanding in the pass instead would make it synthesise as well as enrich, so it would have to be idempotent about creation across every rebuild, and first_visit would be invisible to realtime, which reads raw.

2.6.1The expansion is one atomic write

Every row one beacon becomes is written together or not at all. A page_view that landed without its session_start is not something a later pass can repair: the flag was on the beacon that half-wrote, so re-reading raw reproduces the same partial state. The guarantee has to be made where the rows are created.

1.x does not do this. Db::beginTransaction() exists and the fact tables are InnoDB, but the only callers are the schema-update CLI — each create() on the ingest path stands alone. Nothing depended on it while one beacon meant one row. State the requirement as one atomic write of everything a beacon becomes rather than as “a transaction”: on MySQL it is a transaction, and on ClickHouse a single multi-row INSERT lands as one part, which satisfies it equally.

2.6.2The flags, and why acquisition keys off one

Ingest records the tagged values and stops there. Whatever the landing URL carried — source, medium, campaign, ad, term — is written onto the landing event as tagged_*, beside the referer_url it arrived with. That is transcription, and it sits here next to the geo and device lookups.

The reading is the pass’s, and the model is the report’s. Whether a referring host counts as organic search, a social network or a plain referral is a table that grows and gets corrected, so the pass resolves it into source and medium on the denormalised row (§2.1) — correcting the table is then a reprocess over retained raw (§1.5.2), not an edit. Above that, original versus last touch and the window either is measured over is a choice the reporting layer makes over stored values and touchpoints (§2.22). Neither reaches ingest.

OWA has the flags already, with three different lifetimes:

Keyed off the flag, no other event can change the answer: the failure mode is absent then present, never wrong then corrected. What remains is out-of-order arrival, and those rows are in the same or later days, so the blast radius is bounded by lateness rather than by retention.

2.7The denormalisation pass Decided

One function, run once per partition: read every raw row in partition P, write the same rows enriched into a staging table, swap staging into P. It creates nothing, deletes nothing and updates nothing in place, so rows in equals rows out always holds, and any count mismatch is a bug.

Every column it fills is one of three things:

  • Observed — already in raw from the beacon. Copied across.
  • Resolved at ingest — a deterministic lookup, like geography from the address. Already done, which is why realtime can report on it.
  • Copied by the pass — a value resolved elsewhere that has to appear on rows other than the one it was resolved on: the landing page onto every event of its session, a visitor's acquisition onto every session they have.
  • Computed by the pass — a value needing a set of rows rather than one, like engagement time or bounce, and not knowable until the session closes.

Scope decides only how far the pass reaches for a derived value: the row, the session's other rows, or an event from years ago.

So the pass needs a visitor store to look acquisition up in (§2.9), and it cannot finalise a session whose last event has not arrived, which the late-arrival window bounds.

2.7.1One statement and a swap

There are two inserters in the whole design: ingest and this pass. Ingest writes the raw events a beacon becomes, and the visitor row on a first session (§2.9). The pass writes the denormalised rows. Nothing else inserts anything.

So a run is one statement and a swap:

  1. Build. INSERT INTO staging SELECT … — every raw row in the partition, stamped: the landing page from the session's first event, acquisition read from the visitor store, and the terminal values computed inline over the session's own rows.
  2. Swap. EXCHANGE PARTITION.

Terminal session values stay NULL until the session closes, and are filled on a later rebuild. They are a predicate inside the build. The alternative is an explicit session cap in the window, and it is not needed: session_length is an idle timeout rather than a duration cap, so a session with a hit every 25 minutes runs indefinitely, and no finite window can wait for it to close. §2.11 already makes “not final yet” and “no value” the same NULL.

  • The swap is the commit. Staging is built whole and is invisible until the exchange, so a run that dies during the build leaves the live table as it was and the next run simply rebuilds.
  • It runs entirely in the database. No row passes through PHP, and the same shape works on a columnar engine. The terminal values use window functions, so v2 requires MySQL 8.0 — the repo declares no minimum server version today.
  • One statement is not what makes it atomic — the swap is. Staging is invisible until the exchange however many statements filled it, so the build may be split where splitting is faster, and the guarantee is unchanged.
  • Nothing outlives a failed run except the visitor store, which ingest wrote and the pass only reads.

2.7.3The swap forbids an instant column Measured

2.8The partition cycle Decided

A rebuild replaces a whole partition, so the partition scheme sets the unit of work: the rebuild window wants fine partitions and everything older wants coarse ones. That is one lead of mixed granularity, maintained by three operations, and only the last costs anything.

  • The split is forced. extendPartitions() fills PARTITION_MONTHS_AHEAD (12 months) at whatever granularity the table already uses, so a table taken wholly to quarter-month carries ~48 partitions of lead instead of 12, against a PARTITION_COUNT_LIMIT of 400. Fine-graining the whole table would spend the budget on empty future months.
  • pmax must never receive a row. Everything else here is tuning; this one is required for the scheme to work. Extending the lead costs in proportion to what sits in the catch-all — 1.52s to create 31 partitions when it is empty.
  • One job, and merge before carve. These are separate ALTER statements, but they belong in one run under one lock, as PartitionRotateCli already works. Merging first frees roughly a month of partitions before the carve consumes one, so a run peaks near its starting count; a run that dies between the two leaves the table below where it started rather than over budget.
  • Rotation becomes a dependency of ingest correctness, not housekeeping. A stalled rotation erodes the lead until rows reach pmax. It wants an alarm rather than a log line; there have been two scheduler-adjacent stalls already.

2.8.1One lead, two granularities Decided

There are not three tiers. There is one lead, twelve months of it, and its granularity varies along it. An ordinary fact table holds a single granularity across the whole lead. The cube holds a mix: daily for the first two months, the table’s own granularity for the other ten. Calling those separate tiers implied separate leads and separate budgets, and both implications are false — the budget check is one number for one table.

How much of the lead is daily is not a setting, and that is the decision. §2.5.1 says the interval and the granularity are one decision rather than two — so exposing the front granularity beside the cadence lets an install pick a monthly front and a quarter-hourly run, which is 96 rebuilds a day each rewriting up to a month. Nothing would report that; it would simply get slower through the month and stall near the end of it. Fixing it at daily makes the incoherent pair unrepresentable instead of merely discouraged. It is also a floor: an install that lowered it below the rebuild window would silently stop late events being folded in.

Only the cube’s lead is part daily. Raw never needs it (A.1.8): its retention is a DROP PARTITION and it is never rebuilt, so it pays no merge and gains nothing from being finer at the front. v1’s fact tables have no rebuild to make cheaper. Carving every fact table would spend the open-file budget for nothing.

REVISIT THIS WHEN v1’s FACT TABLES ARE DROPPED. The mixed lead is the right shape while v1 is still here, and that is a transition constraint rather than a property of the design. The per-table budget is the server’s spare open-file slots divided by the reserve and by the number of partitioned fact tables — ten today, eight of them v1’s. Measured on the dev box: 2916 spare gives 145 per table now and 737 once only owa_event_raw and owa_event remain. The mixed lead needs 73 of that; a cube pegged daily throughout needs 366. Both fit comfortably at 737.

At which point pegging the cube daily is the simpler system and should replace this: it deletes the carve, the merge, the skip range that keeps partition-reorganize off the daily front, the last-span guard and the daily refusal. The costs are measured and negligible — EXCHANGE PARTITION goes from 77ms at 72 partitions to 115ms at 365, the partition listing from 8ms to 51ms, and the extra lead extension is a few seconds of REORGANIZE against an empty pmax spread over a year. The ~350 extra partitions are empty future days, and nothing rebuilds a future partition.

What forbids doing it NOW is sequencing. With the budget at 145, a daily cube needs 366 for its lead alone — so it is not the carve that gets refused but extendTableLead(), which means no lead and writes reaching the catch-all. That is worse than anything the mixed lead does. Making the daily depth adapt to the budget to bridge the gap is more machinery, not less. So: this shape until v1 goes, then delete it.

2.8.2The carve waits for the merge Decided

This coupling is the whole of it, and getting it wrong is what made the first version cost 40% more partitions than it needed. Bound the carve by a month horizon and it fires on the 1st, while the merge cannot fire until the window has cleared the previous period’s last day — about the 8th. For that week the daily part is three months wide, and the open-file budget has to be sized for a peak near 103 partitions to hold what only ever needs 60.

Gating the carve on the daily part being shallower than two months couples them: the merge gives the partitions back and the carve takes them, in the same run, once per period. Driven day by day for a year against the real code:

Measured as months of coverage, not as a count of partitions. The daily part extends backwards as well as forwards — elapsed days stay daily until their period merges — so it is the span from its first daily partition to its last that has to be two months, not the distance ahead of today. A flat count of 60 does the same job on average and gets February wrong: after a 31-day month merges, 31 + 28 is 59, and the gate lets a third month through.

The cycle is the table’s own period, not the calendar month. With a quarter-month granularity the window clears a quarter, that quarter merges back to one partition, and the carve extends the daily part in the same run. A period is merged only when its daily partitions tile it completely — a partial merge would produce a span overlapping the days still separate, which the server refuses.

The partition taking writes is carved despite holding rows. Normally a partition with rows is left alone, because reorganizing it rewrites every one of them. But if today falls inside a coarse partition then the daily part has fallen behind — an install upgrading into it, or a run missed long enough for it to run out — and every rebuild until that period ends rewrites a whole period. Carving costs that rewrite once; leaving it costs the same rewrite on every run. Only that one: a past period holding rows is not being written to and merges shortly anyway.

2.8.3What the other commands must not do to it Decided

A daily partition is an ordinary fine period, and that is enough to break two of the three partition commands. Both were found by driving the real code against a cube-shaped table rather than reading it.

partition-reorganize merged the daily front away. Every filter in repartitionTable() admits a one-day partition, so granularity=monthly collapsed two months of them into two, rewriting every live row — and the next partition-rotate rewrote them again putting them back. That is the merge-and-re-carve churn the merge/carve disjointness was built to prevent, arriving from outside the cycle. It also reported the wrong budget (56 partitions for a table that would hold 74 once rotate restored the front), and it accepted granularity=daily, which takes the whole lead daily and makes the next rotate extend a year of lead at daily.

So repartitionTable() takes a skip range and plans each contiguous run on its own — one target across the hole would merge partitions from either side of it and swallow the front. The command passes the cube’s live daily coverage as that range, reports it, and refuses daily for the cube. An explicit from=/to= still overrides, for an operator who means it: the protection is a default, not a prohibition.

The cube is created in shape, not given its front by a later rotate. Db::createTable() built a monthly lead unconditionally, so a fresh install and the upgrade both produced a cube with no daily front — every rebuild rewriting a whole month until the first rotate ran, and on an installation whose scheduler was never set up, for as long as the month lasted. An entity may now declare the lead it needs, and the cube asks for 61 daily plus 11 monthly, contiguous, ending at the ordinary lead boundary with a monthly last span so the granularity inference still reads monthly. The first rotate then carves nothing and merges nothing. An entity cannot exceed PARTITION_COUNT_LIMIT on its own say-so; over it, the table is created monthly and the run says so.

One declaration, and only half of it is declared. Three things shape a table’s partitions and each had its own idea of what a fact table looks like, which is why two of them were wrong the same way. The shape is now stated once, on the ENTITY — Event::getDailyLeadMonths() — and every command reads it. It has to live there: Db::createTable() sits below the controllers and cannot reach them, so a description kept anywhere else is one the creation path cannot consult. Building the ranges is Db::makeLeadRanges(): the entity states a requirement, the database layer renders it.

Measured consequence: move the cube to quarter-month and the merge releases a QUARTER of the daily front rather than a month — the cycle follows the inference, and turning in smaller steps rewrites less per merge. Coverage stays two months either way, because what the merge releases the next carve claims.

partition-init was never affected: it refuses any table that is already partitioned, and the cube is always created partitioned. One job each — init sets a table up, rotate keeps it in shape, reorganize changes the granularity of the part it owns.

The exhausted lead recovers in one run. Nothing daily, rows landing in a coarse partition — a missed run, or an installation upgrading into this. One partition-rotate carves the whole two months back, including the partition taking writes, and a second run does nothing, so the recovery cannot re-rewrite what it has just written.

One lead means one budget, and the daily part is the half that loses. partition-rotate computes the per-table budget once and passes the same number to the lead extension, the compaction and the carve; all three measure total partitions on that table. The lead extension runs first and its dozen coarse partitions always fit, so it is the sixty daily ones the budget refuses — leaving a table with a lead at a granularity that makes every rebuild period-sized. The run now says which half was dropped. The opposite priority is arguable, since the far lead only has to exist before writes reach it while the daily part governs rebuild cost on every run, and is not decided here.

Three month-counts govern partitioning in 1.x and only one is about granularity: PARTITION_CUTS is the granularity itself and is not a month count; PARTITION_DETAIL_MONTHS (36) is how long a period keeps it before compaction; PARTITION_MONTHS_AHEAD (12) is the lead. Granularity is never stored — it is inferred per table from the existing layout, read from the LAST span, and only partition-reorganize changes it. That inference is why the carve must never touch the furthest-future span: carve it and the cube infers daily, and the next rotate extends twelve months of lead at daily — ~365 partitions, silently. daily was added in PR #1113.

2.9The visitor store Decided

This is not a fact table. It is a lookup with one job: stamping first attribution. It holds acquisition — source, medium, campaign, ad, search terms as collected — write-once from the visitor's first session, plus last_seen, which exists only to drive the TTL. Nothing else.

A visitor with no known acquisition has no row. A row carrying nothing to stamp would answer no question. So the store is not a census of visitors: it holds the ones whose first attribution is known, and the pass writes the sentinel where the row is absent (§2.12).

Placeholder rows would also break the write rule below. It is insert-if-absent, so a row written with nothing in it would be found present when the real first_visit arrived late on a queue drain or a rebuild, and would block the real value permanently, silently. Keeping the row absent leaves that path open.

The row is written at ingest, in the same transaction as the event, and the pass only reads it. The tagged values are recorded at ingest (§2.6.2), so the acquisition exists by the time the event is written — there is nothing for a later step to derive, and no harvest.

Any event of the visitor’s first session can write it, not only the one that raised first_visit. A session cannot change its attribution part-way, since new tags start a new session (§1.2), so every event of that session resolves the same acquisition; is_new_visitor or prior_sessions=0 says which session it is. Insert-if-absent means whichever lands first writes the row and the rest are no-ops.

So losing one beacon does not cost the acquisition. It does not reopen the correction problem §2.6.2 guards against: every candidate resolves the same answer, so the failure stays absent then present and never wrong then corrected.

Raw is what is authoritative here. It either holds a first_visit for that visitor or it does not. The store mirrors that, and the sentinel on a denormalised row is derived from the store missing — so of the three, only raw is a record; the other two are readings of it. A disagreement is therefore not a judgement call: rebuild the store from raw.

That holds only as far as raw is retained. Past that horizon raw no longer carries the first_visit, and the store is the sole record of an acquisition rather than a lookup over one — which is exactly the decoupling it exists for (§1.5.4), and the point beyond which it can no longer be rebuilt.

A value that rides every event does not belong here. nps is a counter the client maintains and sends on every beacon, so “how many sessions has this visitor had” is MAX(nps) in a group-by rather than a lookup — the same argument that removed the session table (§1.5.1). Only values that cannot be on the event, because they originate in one event that may be years old, earn a row.

Ingest makes exactly one keyed write, and only for a visitor’s first session. That is the one departure from the pure-append path §1.1 describes, and it is bounded: on the measured install the visitor store holds 6,761 rows against 445,055 requests. Every other event is still a straight insert with no lookup.

last_seen does not add a second one. Three things hold that:

  • the pass advances it, not ingest — one set-based UPDATE over the visitors seen in the partition being rebuilt;
  • it stores a period, not a timestamp, so it changes at most once per visitor per month and the common case is a write that changes nothing;
  • GREATEST(last_seen, <partition max>) is monotonic, so rebuilding a partition twice is a no-op and the column cannot go backwards when partitions are rebuilt out of order.

The write rule is insert-if-absent, never update, so a rerun cannot corrupt it: every event eligible to write the row resolves the same acquisition, so a second write can only carry the value already there. The rule applies to the acquisition columns, not to the row — last_seen is the maintenance exception above. A full rebuild from raw must break ties deterministically, ordering by (timestamp, event_id) rather than timestamp alone, or two rebuilds can disagree.

Two things here are open — the rebuild set, and what partitioning on yyyymmdd alone costs a multi-site install. Both are in §3.1.

2.9.1Do not partition it

Partitioning on last_seen is refused by MySQL, not merely expensive. Every unique key on a partitioned table must contain all partitioning columns, so the key becomes (visitor_id, last_seen_period) and uniqueness on visitor_id alone becomes unenforceable, and insert-if-absent depends on it. A visitor could hold two acquisition rows in two partitions with nothing to say which is right. The cost objections are real too: last_seen is mutable, so MySQL physically moves the row between partitions whenever it crosses a boundary, and a lookup by visitor_id with no period in hand dives into every partition.

Partitioning on first-seen would fix both costs and still buy nothing. The first-seen period is a pure function of visitor_id, so the column is immutable and every lookup can prune to one partition. But expiry is by inactivity, and a first-seen partition holds a mix of long-dead and still-active visitors, so it can never be dropped whole — and expiry is the only reason to partition this table.

So do not partition it, and expire with a plain DELETE. Under a TTL this holds active visitors only: 6,761 on the measured install against 445,055 request rows. A site a hundred times busier is still under a million rows, where a monthly DELETE … WHERE last_seen < cutoff against an index is unremarkable.

The cost falls on realtime, and it is narrow: a raw row from later in the session carries neither the landing URL nor the tags parsed out of it, so a live query cannot show the landing page or the campaign for it. session_referer does ride every beacon, so the referring host reads live; the classified channel does not.

2.11Absence is stored as NULL Decided

A magic string is not absence; it is a value that merely looks like absence, and the difference shows up everywhere downstream. It groups as its own bucket, so a pie over the dimension draws a “(not set)” slice indistinguishable from a real category. It sorts among real values. It cannot be told apart from a visitor who genuinely typed that. And the codebase already knows it is lying: Visitor.php checks != '(not set)' before using a name, and TrackingEventHelpers does the same for REMOTE_HOST and search_terms — three separate places reconstructing an absence the schema threw away.

v2 stores absence as NULL and decides the label at render time. The reporting layer already formats values; “show nothing as (not set)” is a formatter's job, one place, changeable without touching data, and translatable. Baking it into the row makes a display string permanent and unrecoverable — the one thing §2.1 says facts must never be.

Follows the same rule as the boolean columns below it: the store records what happened, the presentation layer decides how to say it. Note this narrows what a nullable column means rather than widening it — NULL becomes unambiguously “not provided”, which is only useful if the write path never also writes a sentinel meaning the same thing.

2.12Boolean columns carry three values Decided

A nullable boolean holds three values, and GROUP BY gives each its own bucket. In 1.x the boolean fact columns are nullable with no default, so is_repeat_visitor holds 1, 0 and NULL — and a pie over the dimension draws two separate slices that both format as “No”. Nothing in the schema, the entity layer or the ingestion pipeline stops a write path leaving NULL in a column with two meanings.

For v2:

  • Declare booleans NOT NULL DEFAULT 0. The storage should refuse the third value rather than rely on every writer remembering. 1.x cannot retrofit this cheaply — it is an ALTER over every install's session and fact tables — which is why it belongs in a schema being defined rather than migrated.
  • Give the type a formatter, not each report. A boolean dimension renders as Yes/No from its declared type, wherever it is shown.
  • Let a report rename the values. “New/Repeat” reads better than Yes/No on a visitor-type chart. The type supplies the default; the report overrides it.
  • A flag with a real unknown state gets an explicit three-state type, not an accidental one.
  • A value the pass could not produce gets a sentinel, and that is not a contradiction. The objection above is to a sentinel standing in for an observation, where it cannot be told apart from a value someone supplied. “Unresolved” is not an observation: the pass generates it, and no visitor can produce it. So NULL keeps one meaning — the beacon carried nothing — and the sentinel carries the other, the pass could not work it out. The formatter renders the first (not set) and the second (unknown), at the same edge, in the same place.
  • The sentinel has to be un-typeable. source and medium are not purely server-derived: resolveMedium() returns strtolower(trim($tagged)) straight from the URL when a visit is tagged, so all five attribution columns can carry visitor text. A readable token like “(unknown)” would therefore be forgeable, which is the confusion this section exists to remove. It is a reserved control byte, and the pass strips control bytes from observed values — which a VARCHAR wants anyway.

    The mechanism to copy is a grammar, not a token. GA reserves the prefixes firebase_, google_ and ga_ for event and parameter names, and requires a name to start with a letter and hold only letters, digits and underscores, so (not set) falls outside the alphabet a name may use. It does not do the same for dimension values: nothing stops a site sending utm_source=(not set), and the parenthesis convention rests on real values rarely containing one. That is tolerable there because a forged placeholder mislabels one row of the site's own report. It is not tolerable here, because our sentinel asserts the pipeline failed to resolve this — a claim about our processing, which the thing being processed should not be able to make. Restricting what an observed value may contain is the same move GA makes for names, applied to values.

Two things this cost 1.x, worth carrying forward: NOT NULL DEFAULT 0 fixes new writes and nothing else, so a schema that has ever permitted the third value needs a migration to close it; and a renderer grouping by a labelled value must fold labels rather than rows, or a map that folds two values onto one name still draws them apart. Whether 1.x backfills its existing NULLs or normalises at read time is open — the dimension registry prefixes a table alias onto whatever it is given, so COALESCE(...) is not expressible as a dimension today.

2.13.1Computing a total and a breakdown

A total and a breakdown are computed differently, which sets two rules:

Breakdowns therefore sum to their totals, and nothing has to reconcile them. A session the pass could not attribute is not missing from the grid, and it does not inflate (not set) either: the pass writes a sentinel where it failed, so that session groups under (unknown) (§2.12). Both are ordinary buckets, both sum, and neither is a remainder computed by subtraction.

A lost first beacon takes its marker with it — the client commits the session on sendAccepted, which fires when sendBeacon queues rather than delivers — so a session can exist with no session_start row. Neither number above notices: the tagged values are recorded at ingest on every event, and the visitor row is written by any event of a first session. What goes with the beacon is the landing page, which rides only that one (§2.10).

A reconciliation row would be needed only if a breakdown were computed from a different source than its total — counting marker rows as a fast path, or reading a rollup (§1.5). Both are out of the current design. One rule from that reasoning is worth keeping: a breakdown exceeding its total is a defect and is never clamped. It means an event-grain dimension has been crossed with a session metric, which §2.13's scope algebra labels rather than hides.

2.13.2Two queries, one generation

A report asks for a total and a breakdown, and ResultSetManager issues them as two queries — computeAggregates() then computeDimensionalRows(). The pass can swap a partition between them, and then the two numbers describe different data.

Both queries return MAX(built_at) alongside their result. If the two values differ, a swap landed between them and the pair is re-run.

SELECT COUNT(DISTINCT visitor_id, session_id), MAX(built_at) FROM owa_event WHERE …
SELECT source, medium, COUNT(DISTINCT visitor_id, session_id), MAX(built_at)
  FROM owa_event WHERE … GROUP BY source, medium
  • It needs no transaction, which matters because there is not one to use. MySQL would give this for free under REPEATABLE READ, but the swap is EXCHANGE PARTITION — DDL, which MVCC does not cover — and ClickHouse's transactions are experimental and absent from its cloud. Carrying the generation in the row works on both.
  • It costs no extra reads. The check rides queries already being issued, so there is no marker table and no second round trip.
  • It detects rather than prevents. Pinning by predicate would not work: the swap replaces the partition, so filtering built_at ≤ X after one returns nothing rather than the old rows. Retaining both generations would prevent it, and costs a second copy of every partition under rebuild.
  • Most reports never reach the check. Only a period overlapping the rebuild window can see a swap at all (§2.5.1); a closed period reads partitions nothing will rewrite.

How often a swap actually lands between the two queries is unmeasured. Reports are sub-second and the pass touches one partition at a time, so it should be rare — but the failure is silent, so it wants a number before anyone relies on the retry being cheap.

2.14Schema versioning Decided

One schema version, one numbered update sequence. An update may touch v1 tables, v2 tables or both. v1 and v2 are not two schemas that coexist; they are one schema containing both shapes — which removes the version pair, and with it any compatibility matrix or cross-sequence ordering question.

The mechanism already works this way: only Base has ever had updates, install() builds tables from entity registration and never replays updates, and the apply loop already sorts numerically, stops at first failure and resumes.

The sharp edge

A dropped v1 is a supported state, so every update written afterwards must tolerate those tables being absent — not just ones that mean to touch them. The apply loop stops at the first failure, so one update assuming owa_session exists blocks every later update for those installs, and isUpdateRequired() then wedges them out of the admin over a table they deliberately removed.

Worth a helper on the update base class rather than a documented convention — the failure lands on the update written eighteen months from now.

2.15Packaging Decided

Unchanged. Same tarball, same Release Packager workflow, same wizard. No Composer requirement for end users, no build step at install time, no new runtime dependency. The distribution model is the reason a self-hosted tool gets installed at all, and a rewrite is exactly when one is tempted to modernise it into something needing a toolchain on the target machine. The schema changing is not a reason for the delivery mechanism to change.

2.16Testing Decided

The two harnesses of §2.22 are the primary tests — pipeline integrity generated and exhaustive, model characterization hand-written and small. Neither alone is “the” test, and reporting them as one is the failure mode that section describes. Around it: 77 test files and 509 methods today, of which only 8 files are named for star-schema artefacts — most of the suite tests CLI commands, settings, auth, validation, the queue and the scheduler, and ports unchanged. What genuinely expires is the part testing the star's mechanics.

Three hazards, the first two already known here:

  • Order-dependent tests — CI already runs an isolation sweep executing each file alone. More valuable during a rewrite, not less
  • Vacuous assertions — double-quoted PHP needles containing $this-> interpolate away and pass unconditionally. A rewrite writes many tests quickly, which is the condition that produced these the first time. Worth a lint
  • Silently narrowing coverage — a test deleted because it tested the star, never replaced, leaves no trace. A green suite that is green because it asks less

Claims in this plan that are worth nothing untested: the pass folds in a late event on the next run; an event beyond the horizon does not, but still lands in the event table; running the pass twice changes nothing; a throwing v2 handler fails neither the v1 write nor the request; the update sequence runs clean with v1 dropped; and generated realtime SQL carries a closed partition-key range — asserted on the SQL, since a timing assertion on a small fixture would pass either way.

2.17Multi-site Decided

The area needing least work: a single event table handles tenancy naturally, site_id is a column, isolation is a WHERE, and it already leads the composite indexes. Permissions are already per-site.

Two things change. site_id becomes more load-bearing — it leads every composite index and every report's WHERE — so it must be immutable. And site_family is written by site creation and read nowhere; it was built for a UI that never shipped, and should be dropped rather than ported.

Retention stays installation-wide, not per site. A partition of the shared event table holds every site’s rows, so varying retention by site could not be a partition drop — it would need a row-level DELETE sweeping every partition, leaving fragmentation behind and competing with live writes. Uniform retention is a metadata-only partition drop, effectively instant, and already implemented. The single table makes the simpler policy the cheap one.

  • A funnel step can name a goal event, and its conditions are compiled into a row predicate matched against the facts — deliberately not a lookup of the stored conversion, which has no timestamp to order by and is stamped forward-only, so a goal event created this morning would draw an empty funnel over last month.

Everything v2 changes about them is storage-shaped: a recording becomes an attachment rather than a parallel fact row, the payload moves outside the row, and the encoding becomes delta tuples plus gzip, measured at ~30×. Migrating them means re-encoding, so they either go last or stay in owa_domstream until it is dropped with the rest.

2.22The parity harness Decided

Parity runs over migrated history, not over two live pipelines. The same rows are read twice — by v1’s reports from its own tables, and by v2’s from the migrated ones — so the input is fixed, the comparison is deterministic, and nothing is double-written in production to make it possible.

It is still two instruments, and they must not share a verdict.

2.23One reporting path, and v2 replaces v1’s metrics and dimensions Decided

There is ONE reporting path and it reads the cube. v1’s metrics and dimensions are replaced by v2 ones resolving against the Property’s cube rather than the star, and the existing report configs keep their names wherever the concept survives — only a name that does not survive is edited.

Why there is no second UI. The migrator (§2.21) denormalises v1’s tracking data into v2’s RAW store and the build fills the cubes from there, so after it runs there is no v1 history needing v1 reports. A /v2 path would be a second surface maintained for a window that closes, and every report would have to be authored twice to span it.

Supersedes the earlier decision — a separate /v2 path with both UIs side by side, DECIDED and reversed 24 Sep. What that decision got right is kept and is now free: nothing infers a version from a date, a watermark, a coverage check or an install-wide flag. There is no version to infer.

The ordering it implies. The migrator moves into the reporting arc rather than a later phase. The moment metrics read the cube, un-migrated history is unreportable — which is survivable only because v2 merges to master once reporting runs off v2, so the migrator has to land before that merge and not after it.

The compatibility surface is the NAMES, not the path. Rows in owa_custom_report are documents written by people naming metrics, dimensions and sorts (A.1.10), and they resolve through the registry at render time. A v2 metric registering under its v1 name keeps every saved report working; a rename needs an alias, not a sweep of other people’s reports.

2.23.1Entity selection STAYS; its inputs get simpler

ResultSetManager reduces the candidate entities to those that can compute every requested metric, refuses the combination if that intersection is empty, ranks what survives by getSummaryLevel() and takes the first that relates to every requested dimension.

That algorithm stays. Summary tables may be introduced later, and a summary is exactly another entity carrying a subset of the metrics at a higher summary level — this is the machinery that would pick it, and the refusal is what stops a report asking a summary for something it does not carry. Removing it because one cube answers everything today would have to be rebuilt the first time one does not.

What simplifies is the inputs, not the logic. Against a single denormalised cube the metric intersection is satisfied by construction, and the dimension check becomes “is this a column on the entity” rather than “is there a relation from this fact table to that dimension table”. 60 dimension names, instead of the 60 names spread over eight source entities that denormalizedDimensions[$name][$entity] holds now.

The cube’s table is per Property, so the entity must be BOUND before it can name one. Entity\Event is a shape and its getTableName() throws while unbound (§2.27). ResultSetManager does the binding, because it is the thing that knows the site the request names and therefore the Property; Classes\Cube\Cubes stays the only place a cube’s name is built. This is the one thing the superseded version of this section could not have said — it was written when there was a single owa_event.

2.23.2Domain aliases stay v1-only, and narrow Decided

A site may answer on more than one domain, and that list should not be made to do two further jobs.

  • It does not widen CORS. matchAllowedOrigin() matches a request's Origin against each site's domain and nothing else. Feeding alternates into that allowlist would grant cross-origin API access installs do not have today, as a side effect of moving a setting into a column.
  • An alias narrows to a variant of the same domain. Its documented purpose is collapsing www.mydomain.com and mydomain.com; a general redirect map is a much larger thing to reason about than the help text implies.

2.24Publishing the tracker Deferred

It is build, serving and admin work, which is why it is not in Phase 5 (§2.19.2) with the collection changes.

2.24.1One file, at a URL that never changes

The bundle and the config ship as one file, not two. And its URL is fixed for the life of the site, because the snippet cannot be updated — a pasted tag outlives every setting it was pasted beside. That rules out versioned filenames, which in turn rules out invalidation-by-renaming.

What makes that affordable is conditional requests. Apache already sends ETag and Last-Modified on the tracker, so a client re-checking after its freshness expires gets a 304 with no body unless a publish actually changed the file. The payload moves when there is something to move.

2.24.2Cache lifetime, and what happens without one

The header goes in the .htaccess OWA already ships, guarded like everything else in it:

<IfModule mod_headers.c>
    <If "%{REQUEST_URI} =~ m#/public/base/t/#">
        Header set Cache-Control "public, max-age=900"
    </If>
</IfModule>

Root .htaccess rather than one beside the files, because public/ is gitignored and would not ship. Today the tracker is served with no Cache-Control at all, so caching is whatever each client decides heuristically — worth fixing whether or not per-site trackers happen.

That header cannot be relied on. OWA installs onto nginx, LiteSpeed and IIS where .htaccess is inert, onto Apache without mod_headers where the guard silently skips it, and behind proxies that rewrite it. The failure is invisible: publish succeeds, the file on disk is right, and nothing reaches visitors. So publish fetches the URL it just wrote and reads the header back. Detection of the web server is the remedy, not the test — it decides which snippet to show once verification has already failed, so a server OWA has never heard of gets a clear message instead of a wrong one.

Absent a header, heuristic freshness scales with the age of Last-Modified: short right after a publish, longer as the file sits unchanged. Crude, client-dependent, and it fails in the useful direction.

2.24.3Moving it to a CDN

A site owner can name an alternate domain for the tracker, publish the file there, and control expiry with the CDN’s own tools. OWA then owns none of it, which is the point: cache headers depend on a web server OWA does not run.

Deploying to a particular CDN is a module’s job, and the hooks exist — registerEventHandler and registerFilter, the latter already used next door as tracker_tag_cmds. The module uploads and expires the object; OWA passes it the file and the site id. Config changes are rare enough that this needs no reconciliation machinery beyond that.

Two consequences to state where the domain is entered, not in documentation: OWA can no longer say when a change reaches visitors, and an unpublished or un-uploaded site 404s its tracker on every page with nothing to fall back to. Publish on site creation, and have setup fetch the URL once before calling the site configured.

2.24.4What the snippet keeps

Only what the server cannot know when it publishes. Page title, content group, user id, custom variables, and the trackPageView call. setPageType goes with the dimension it fed (§2.4). Everything else — logClicks, logPage, movementInterval, the three domstream* options, sessionLength, cookie_domain, campaignKeys, maxCustomVars, getRequestCharacterLimit, encodeProperties, the site id and the endpoints — bakes in.

Today’s tag pushes six commands, of which two are site config that lives in the page only because there was nowhere else to put it.

Three options would be publishing a control that does nothing. logMovement appears once in Tracker.js — its own declaration; bindMovementEvents() never reads it. thirdParty sets a flag no server code consumes. campaignAttributionWindow is passed to setState as an expiry that StateManager drops. trafficAttributionMode is not one of them: it is inert server-side, but Tracker.js switches on it to choose between the direct and original models, so the verdict the event carries depends on it. Decide what these are before giving any of them a screen.

Both, with the site winning. The two tiers already exist:

2.24.6What this does to the snippet-command route

PR #1098 answered the same question the other way: reach the tracker by adding snippet commands. Its own rationale is the argument against doing more of it — the snippet is rendered server-side and changes the moment PHP is upgraded, while the tracker is a long-cached static file a returning visitor may hold for days, so a new command can arrive at a tracker too old to understand it. That was found on a live install: the queue died before trackPageView and no visitor cookie was written at all.

Publishing config into the file collapses that skew, because the config and the code that reads it become one artifact with one lifetime. The command-queue fix that shipped stays worth having — an unknown command should never take the queue down — but the contortion it was protecting, emitting a command only when a value differs from its default so pasted snippets stay byte-identical, stops being necessary.

2.24.7What it costs the deploy

public/ is gitignored, so published trackers do not arrive with a pull — the same reason the runbook already requires a build. A republish becomes a deploy step, and because the bundle lives inside every per-site file, an OWA upgrade republishes all of them. webpack.config.js sets no clean, so published files under public/ survive a rebuild.

2.26Custom dimensions Decided

SUPERSEDED IN ONE RESPECT by §2.27. This section was written while there was one cube for the installation, so it places registration at installation level. With a cube per Property, registration is per PROPERTY -- which is also what GA does, and for the same reason: the level that owns the table is the level that owns the definitions. Everything else here stands unchanged.

A site-defined value becomes queryable by being REGISTERED, and registration adds a real column to the cube. Everything queryable is a dimension; there is no path that reads an unregistered key. The mechanism was settled by measurement against MySQL 8 — every number below is measured on a 72-partition table, not estimated.

2.26.1Two scopes, and only two Decided

GA offers site authors exactly two scopes for custom values — event and user — and derives session scope itself rather than letting a tag carry it. v2 does the same, which settles what the tracker exposes:

The slot number is dropped: it was v1 storage, not information.

2.26.2Registration adds the column Decided

  • Prefixed cd_, so the column set stays separable. It constrains DROP COLUMN to a pattern — de-registration takes a name from user input and issues DDL, and nothing matching ^cd_[A-Za-z0-9_]+$ can be a release column. It also makes collision with a release column impossible without a reserved-word list that would go stale every time the cube gains a column, and it lets a test still assert that the cube’s non-cd_ columns are exactly the entity’s.
  • The column name is DERIVED from the key, not equal to it. Db enforces ^[A-Za-z0-9_]+$ on every DDL path. So the registry stores key ↔ column, and uniqueness is enforced on the COLUMN, because that is what DDL collides on: JSON keys are case-sensitive where column names are not, so Plan and plan are two keys and one column.
  • A REGISTRABLE KEY IS THE TRACKER’S OWN NAME PATTERN, ^[A-Za-z][A-Za-z0-9_]{0,39}$, character for character — not “any JSON key”, which is what this section first assumed. Two things follow, and the second is the reason. A key the registration refuses is one no OWA tracker could have set, so refusing it costs nothing real. And the JSON path is then $.<key> with nothing to quote: a registration taking arbitrary keys would have had to build a path out of user text and place it inside a SQL string literal, escaped twice. A hand-rolled beacon can still send a stranger key and ingest will still store it; it just cannot be promoted.
  • Type is declared at registration, because the ALTER fixes it and the JSON does not.
  • No Update class. This is per-site runtime state, not release schema, so required_schema_version does not move.
  • THE ROW IS WRITTEN NOW AND THE COLUMN ARRIVES LATER, with a state saying which — pending, applied, failed. See 2.26.7: the ALTER cannot happen inside the request that asks for it. What a build reads is the TABLE, not the registry, so a row naming a column that is not there yet costs nothing; trusting the registry would fail every build with “Unknown column in field list”, which is a Property’s whole cube stopping minutes after somebody registered one dimension.

2.26.3ALGORITHM=INPLACE, on both the add and the drop Decided

The default is INSTANT, and INSTANT silently breaks every subsequent cube build. It leaves instant-column metadata, and EXCHANGE PARTITION then refuses the swap with error 1731 — the same failure 2.7.3 records. The build fails, does not swap, and the partition keeps its last good contents. So both directions pin the algorithm, as addColumnRebuilding() already does for release columns.

MySQL refuses LOCK=NONE rather than silently taking a stronger lock — it did so twice while this was being measured, error 1845 for a STORED generated column and 1846 for a column and its index in one statement — so acceptance is a guarantee. Reads and writes continue throughout; the only exclusive moment is the metadata flip at the end.

Registering several at once costs ONE rebuild. Ten columns in one ALTER measured 13,664ms against 13,057ms for one, a 5% margin, where the same ten as separate statements would cost ten rebuilds. Re-measured on a real 73-partition cube: one added column 4,361ms, two added 4,247ms, and one added and one dropped together 4,193ms. The rebuild is the cost; the clause count is not.

This section first concluded that batching therefore belongs in the UI rather than in a background reconcile pass. That is backwards, and 2.26.7 is why. The reconcile is what applies the DDL at all, so it is the thing that batches — and it batches better than a UI can, because it sweeps up everything registered AND de-registered since it last ran, in one statement, with no dependence on anyone remembering to submit them together.

ROW_FORMAT=DYNAMIC IS DECLARED, NOT INHERITED. It was inherited, and that is a table OWA might not be able to create at all. The formats differ in how much of a long column they can move off the page: DYNAMIC leaves a 20-byte pointer, COMPACT and REDUNDANT leave the first 768 bytes of each one inline. Measured on the cube, which has ten VARCHAR(1024) columns: creatable under DYNAMIC and refused with error 1118 under either of the others. The server default has been DYNAMIC since 5.7, so declaring it changes nothing on an ordinary installation and removes a dependency on innodb_default_row_format — a setting nobody here chooses — from a table v2 cannot do without.

utf8mb4: CONSIDERED AND DECLINED. Decided 23 Sep. Tables are created CHARACTER SET = utf8, which MySQL still maps to utf8mb3 at three bytes per character, so a four-byte character does not fit any text column in the schema. What that costs today, measured through real ingest: a page title of Summer sale 🎉 now on stores as Summer sale  now on — the event survives and the emoji is dropped, silently, by the entity layer before the insert. A raw INSERT of the same value is refused outright with error 1366, so nothing is at risk beyond the character itself.
It cannot simply be switched on. The cube at utf8mb4 is about 70,700 declared bytes against the 65,535 limit; CONVERT TO CHARACTER SET utf8mb4 on a real cube is refused. The only route is to convert the widest never-grouped columns to TEXT first, since those contribute 9–12 bytes rather than their width — which is a schema change to raw AND the cube, with a rebuild on every installation, to stop dropping emoji from page titles. Not worth it. Revisit only if something that matters more than emoji needs four-byte characters.

A VIRTUAL generated column over the JSON was measured as the alternative and rejected: ~330ms flat and retroactive over all history, which is better on both counts, but it puts the JSON extraction in the SCHEMA rather than in one dialect expression. A.1.9 wants the rebuild-and-swap idiom to port to columnar stores, and those have columns but generally not generated columns. A real column filled by the build also parses the JSON once at build time rather than on every read.

2.26.4No backfill, by default Decided

The column is NULL for rows that already exist and the next build fills it going forward. Backfilling is cmd=cube-rebuild over the range wanted, and it is the operator’s choice rather than a side effect of registering.

This is the opposite of GA and worth stating as a capability. GA’s registration is mandatory AND early: a custom dimension is not retroactive, so everything collected before it was registered is permanently unreportable. v2 keeps params on every raw row, so a registration made today can be backfilled across the whole of retained history. Registration can be late without penalty; the only bounds are raw retention and the cost of rebuilding the coarse end of history.

2.26.5User properties, and when they were set Decided

A JSON column on the visitor store, not a key-value table and not a second table. Measured at 100k visitors and 400k events: a key-value visitor store is 5× the rows and its pivot makes the build’s join 2.2× slower (1,097ms → 2,382ms). A JSON column keeps one row per visitor and reuses the join acq_* already makes, so the marginal cost is one JSON_VALUE per joined visitor — proportional to distinct visitors in the partition, not to events, and zero when no user-scoped dimension is registered because the join is demand-driven.

Each property carries when it was set, the way GA’s BigQuery export carries set_timestamp_micros:

{"plan": {"v": "enterprise", "ts": 1790000000000000}}

Registration therefore adds TWO columns, cd_<name> and cd_<name>_set_ts, in the same ALTER — which the 5% batching margin makes free. The timestamp does not become a dimension on its own: a microsecond value has one bucket per event, which is a pathological dimension. What it is FOR is the test kind — cd_<name>_set_ts <= ts, “the property was already in force at this event” — which is boolean, and which is the question a write-time stamp cannot otherwise answer. A cube row says the property’s value; without this it cannot say whether that value applied yet.

2.26.6What this changes about the visitor store Decided

The absence test moves from the ROW to the ACQUISITION. 2.9 writes the unresolved sentinel where the visitor store has no row, and the cube tests v.visitor_id IS NULL for it. That was only ever a proxy, and it breaks the moment anything else writes to that row — a user property arriving for a visitor whose acquisition is unknown would create a row, and the build would then resolve acq_source to direct rather than the sentinel: unknown silently becoming a claim.

  • the test becomes v.acq_ts IS NULL, renamed acquisition.missing since it no longer tests the row. Equivalently: stamp the acq_* columns when acq_ts IS NOT NULL, sentinel otherwise
  • the acquisition write fills acq_* while acq_ts IS NULL rather than skipping when the row exists, so a late first_visit on a queue drain still lands and write-once still holds
  • user properties are written last-value-wins, in the SAME transaction as the raw insert, with ts as the ordering guard so an out-of-order queue drain cannot overwrite a newer value with an older beacon

The two disciplines now coexist explicitly rather than by accident: acq_* is write-once evidence captured at first visit, and properties is mutable state the site sets whenever it likes. 2.9 already drew that line; this keeps it drawn while letting both live in one row.

The ALTER is longer than every request timeout there is, and a killed request does not stop it. Measured on this installation:

The part that settles it is what happens then: a PHP process killed three seconds into an eleven-second ALTER left the column absent at t+4s and present at t+15s, with the client never learning either. So a synchronous screen would hand somebody a timeout, add the column anyway, and invite a retry that pays a second full rebuild before failing on a duplicate column — the worst of every option.

So registering is a write, and a RECONCILE does the DDL: make this cube’s columns match its registry, in one ALTER. It runs in three places, and the first is the one that matters:

  • the cube build calls it before building, so it can never be forgotten — whatever else is or is not scheduled, a cube that gets built gets its columns;
  • a registered job, apply-custom-dimensions, every fifteen minutes and spread, so a dimension registered from a screen appears in minutes rather than at the next daily build. It is the only frequent default job, and may be: a run with nothing pending is ONE indexed read for the whole installation and does no DDL at all;
  • the CLI, inline, because there is no request there to time out. --defer opts out.

It must hold the cube’s own lock, the one a build takes (cube-build:<table>). A build derives its staging table from the live cube’s DDL and then swaps, so an ALTER landing between those two makes EXCHANGE PARTITION refuse the pair.

The row budget is therefore checked twice, and the two answer different questions. At registration it is advisory and immediate, because refusing “1,020 bytes needed, 800 left” while the person is looking at the screen is the whole value of it. Under the lock it is authoritative, because it sees every pending column at once — two registrations that each fit alone need not fit together, and only the second check can know. A registration refused there is marked failed with the reason, the ADDS are skipped and the DROPS still happen (dropping is what makes room), and the build carries on: one bad registration must not cost a Property its reporting.

Two windows open up, and both are deliberately harmless. Between registering and applying, the registry names a column that does not exist — the build simply does not fill it. Between de-registering and applying, the column exists and nothing names it — the build stops filling it and the next reconcile drops it. Neither is a state in which anything is wrong, only one in which something is untidy, which is what lets the expensive half wait for a moment that already holds the lock.

2.27A cube per property Shipped

One owa_event per Property, not one per installation. Decided 22 Sep. Raw stays single — it is written by ingest and read only by a build — and the CUBE is split, because the cube is what reports read and what custom dimensions add columns to.

2.27.1Why, and what it costs Decided

It is the same rule GA applies. A GA property owns its dataset, which is why custom definitions are registered there (properties.customDimensions, Editor at the property level) rather than on the account or the data stream. A property with several data streams shares one set of definitions across them. Splitting the cube per Property gives OWA the same shape, and with it:

  • Custom dimensions belong to a Property rather than to the whole installation, so two Properties can use the same key for different things. Sharing one cube forces one namespace — which is the v1 failure §2.26 criticises, cv3 meaning something different per site, arriving by a different road.
  • The row budget stops being shared. A cube that already has 73 columns takes exactly 16 more VARCHAR(255), 64 more VARCHAR(64) or 114 more VARCHAR(36) before the server refuses (error 1118, measured). Shared, one Property could exhaust the installation. Split, each has its own budget.
    THERE ARE TWO LIMITS AND WHICH ONE BINDS DEPENDS ON THE SERVER. This section twice claimed to know which, and was wrong both times.
    • 65,535 bytes — MySQL’s row DEFINITION limit, the sum of declared widths. A VARCHAR(255) on utf8mb3 costs 767: 255×3 plus two length bytes. TEXT and BLOB contribute only 9–12 whatever their declared size, which is the trap that broke the first attempt at pricing this.
    • ~8,126 bytes — InnoDB’s limit on the part of a row stored on the page, slightly under half a 16KB page. InnoDB moves variable-length columns off-page until the row fits, so a long VARCHAR is nearly free against this one and the cost is in the MANY SHORT columns. Measured on MySQL 8.0: dropping raw_ua bought no extra dimensions at all, and dropping eight wide columns bought two.
    Measured: MySQL 8.4 refuses at 65,535 and takes 25 custom dimensions; MySQL 8.0.46 refuses at 8,126 and takes 19. Same row format, same charset, same DDL. So the budget is MEASURED against the server in front of us (Dimensions::capacityFor()) and not calculated — two calculations were written, and the more careful one predicted 8.4’s refusal point exactly while 8.0 was refusing something it called fine.
  • Retention and granularity become per Property, as the partition commands already allow per table.

Entity\Event extends EventRaw, so the table name the parent constructor sets is owa_event_RAW — an unbound cube entity answered with a real table, and writing a cube's rows into raw is not a failure anything downstream would notice. The constructor removes it and an unbound instance refuses to name a table at all. And an empty site list has to mean 1 = 0 rather than no restriction: a Property whose profiles have been deleted or moved would otherwise be handed every other Property's traffic, and the build's rows-in-equals-rows-out check would agree with it.

Two things are deliberately NOT split. owa_event_raw stays single: ingest writes it on the hot path, nothing reports from it, and splitting it would multiply the write path's table count for no reader's benefit. owa_visitor_acquisition stays single too, because a visitor is shared across Properties by the same cookie — splitting it would give one person a first-touch per Property, which is a different claim from the one 2.9 makes.

2.27.3A cube is created on first data, by the build Shipped

Not when the Property is created. A cube is 72 partitions (§2.8) — 72 files and about 2.7 seconds — and a Property that never collects anything would pay all of it. At a handful that is nothing; the dev installation has 212 sites. GA works the same way: nothing is materialised for a property until it has at least one event.

THE BUILD WATCHES, NOT INGEST. The obvious reading of "create it on the first event" puts the creation in the beacon path, and that is the version to avoid: a 2.7-second CREATE TABLE inside a request, with every concurrent first event of that Property racing to do it. The build is already the right place — it runs on a schedule, it already holds a per-cube lock (§2.26), and it already asks which partitions hold rows for a range, which is most of the question. So:

  • ingest writes owa_event_raw and knows nothing about cubes
  • a build, finding raw rows for a Property with no cube, creates it and then builds it
  • a Property with no data has no cube, and therefore no reports — which is the same thing a Property with no data would show anyway

The delay is the whole of the cost: a Property's first data is not reportable until the next build, where an eagerly-created cube would have been ready to fill immediately. That is the same latency every other row already has — nothing is reportable until a build runs — so it adds a boundary case rather than a new kind of wait.

2.28.1Canonicalise the READINGS, never the evidence Decided

The split this plan already makes everywhere else settles most of it. page_location is EVIDENCE and stays byte-for-byte as it arrived: it is what a corrected parse is re-applied to, and stripping it means the question cannot be asked twice. GA reaches the same place — its page_location is the raw URL — and it is why v1 needed keepCompleteUrl() to stash the URL before its own canonicaliser ate it.

page_path, page_query and host are READINGS: they are what reports group by, and a reading that varies where the page does not is a broken report. They are already parsed at ingest, by a real URL parser, which is the only place that both can and should canonicalise.

2.28.1bWhat GA does, which answers two of these Measured

GA STRIPS THE FRAGMENT IN THE TRACKER, not on the server. From Google’s own developer documentation rather than a blog: page_location defaults to location.href, and “the default value excludes the fragment portion of the URL”. So the hash never leaves the browser. Our tracker sends document.URL, which keeps it.

That is a better answer than stripping it at ingest, and it costs nothing to adopt. Nothing is lost as evidence: a fragment has never carried a campaign tag, so the one thing page_location is evidence FOR is unaffected. It keeps whatever people put in fragments off the wire entirely, and it makes page_location groupable, which it is not today. GA reaches SPA navigation through history events instead, which is a separate mechanism from the hash.

GA REMOVES QUERY PARAMETERS AT COLLECTION, DESTRUCTIVELY, AND FOR A DIFFERENT REASON THAN v1 DOES. Its feature is called data redaction, configured per web data stream, and it “evaluates events before they are collected to find and remove any text it understands as an email address or query parameter key-value pair”. The examples Google gives are firstname, lastname, email_address. It is a PRIVACY control, not a tidiness one.

Which separates a thing v1 conflated, and is the useful finding here. query_string_filters is doing two unrelated jobs at once: keeping personal data out of storage, and keeping noise out of reports. They want opposite treatments. Redaction MUST be destructive and at ingest — the whole point is not to store the email address, and a build-time filter would mean it had already been stored. Report filtering SHOULD be at build and reversible, because the list is a setting an administrator edits and a corrected list ought to re-apply to history, which is the argument the cube exists for. So: two lists, two places, not one list doing both badly.

GA canonicalises the parts hardly at all. No trailing-slash collapsing, no default_page, no case folding — the Universal Analytics view setting for it has no GA4 equivalent, and the documented route is a property-level Modify event rule. So v1 does MORE here than GA does, and v2 doing nothing is GA parity but a v1 regression. That is a real choice rather than an oversight to correct, and it is the one still open.

2.25Cutover sequence Decided

ONE RELEASE, NOT A STAGED ROLLOUT. Decided 22 Sep. The five steps below are the order the WORK is done in, not a sequence of shipped releases with installations sitting between them. Every v2 pull request merges into a v2 integration branch, and that branch merges to master once reporting runs off v2 — so master always holds a working system and there is never a release in which v2 collects while v1 reports.

What follows from it: there is no later release to defer a removal to. v1’s tracker vocabulary — the cv1..cvN stores and their scoped getters — goes in the same release that adds setEventProperty and setUserProperty, rather than being deprecated across one. The one thing that is NOT a release event is dropping v1’s tables: that stays an administrator’s command, because an upgrade must not delete data. And accepting a v1-shaped beacon is a separate concern from any of this — a stale tracker keeps sending one long after the install has upgraded, so the server’s compat for cvN is not retired with the client’s.

  1. Build v2’s tables and the pass. They sit alongside v1 and nothing reads them yet.
  2. Migrate (§2.21). Non-destructive and re-runnable, against a v1 that stays intact.
  3. Compare (§2.22) over the migrated rows, until the differences are all ones the model explains.
  4. Switch collection to v2. One tracker, one pipeline; v1 stops receiving. v1’s reports stay up, reading history.
  5. Drop v1 when nobody wants its reports any more — a command that removes the 20 parallel tables and leaves the shared admin tables alone.

Step 4 retires v1’s handlers, not v1’s wire format, and what is different about it is narrower than it first looks. Cached trackers are the standing constraint on every tracker release — 1.x already carries the pattern in three places: taggedValue() prefers a tagged_* the beacon actually sent over its own re-parse, SessionHandlers falls back to the page-scoped flag for trackers cached before the two were split, and the state loader sniffs cookie format rather than assuming it. The mitigation is always the same: keep the old path, prefer the new.

Step 4 is the one release where that is unavailable, because deleting the old path is the point of the step. There is no fallback branch to add — the new code is the only code, and it has to understand v1’s vocabulary outright. Hence Classes\V2Event::name(), which maps base.page_request, dom.click and ecommerce.transaction onto the v2 names.

Measured, against the beacon contract: a cached tracker sends nothing v2 ignores, and fails to send exactly two things v2 wants — client_ts_usec and page_location. Both already have server-side answers: clock_offset_usec goes NULL, which is the honest reading when no client clock arrived, and keepCompleteUrl() stashes the URL before makeUrlCanonical() strips it. is_new_session_start, is_new_visitor_created and landing_url are already on v1’s wire — the first two were put there for this handover and nothing in 1.x reads them. So a cached beacon becomes a correct but thinner row, and the events only the v2 tracker raises simply do not arrive until the bundle refreshes. That is §1.2.4’s rule holding: values may degrade, records must not vanish.

The parallel pipeline is development scaffolding, and it ends at step 4. v2 does not ship alongside v1. During development a site can be switched on with the v2_raw_collection setting, so that ingest is exercised against real traffic before the switch instead of the switch being the first time it ever runs — which is the shape that produced the Update 023 and 026 failures. It is denylisted from the options form and off for every site. At step 4 the setting is deleted along with v1’s handler registrations, and Handler\EventRawHandlers registers unconditionally.

Nothing is irreversible until step 5, and step 5 is the administrator’s decision rather than an upgrade’s side effect. Steps 2 and 3 can repeat as often as needed, because the migration only ever writes v2’s side.

Step 4 is the one step with no rehearsal: it is a schema this installation has never run before, which is the shape that produced the Update 023 and 026 failures. The mitigation is that steps 2 and 3 have already exercised the tables and the pass against that installation’s own data before any collection depends on them.

AppendixEvidence and debate

A.1Why the design is what it is

The body states what v2 is. This is the evidence behind it — kept because the reason a design is not something is the most expensive thing to rediscover, and moved here because it was making the plan unreadable.

A.1.1GA: three traffic-source records

GA exposes the same three-way split as three separate records on an event row:

  • collected_traffic_source.* — manual_source, manual_medium, manual_campaign_*, gclid, dclid, srsltid. The tags as collected with the event. Evidence, not reading. Read from the tracker in A.1.32: GA ships raw tags and never a parsed source or medium.
  • session_traffic_source_last_click.* — session scope, and its name states the model. Nested per channel (manual_campaign, google_ads_campaign, cross_channel_campaign, sa360, dv360, cm360). Derived, not collected.
  • traffic_source.name / .medium / .source — user scope, documented as “the traffic source that first acquired the user” and explicitly “do not change if the user interacts with subsequent campaigns”. Write-once acquisition, materialised onto every event row.

That also narrows the realtime claim made above, and it should be narrowed. OWA’s raw layer does hold more than GA’s — the referring URL and the campaign tags are there on every event where GA carries only per-event collected values — so realtime can report a referring host. It cannot report a resolved source, medium or channel, because those do not exist until the pass runs. Richer than GA’s realtime, but not unboundedly so, and along a line that follows from the architecture rather than from a policy.

A.1.2GA: what the intraday table does not have

The line in GA’s BigQuery export documentation that settles the architecture: “This record is not populated in intraday tables.” GA’s intraday table is its raw layer and its daily table is its processed one, and user acquisition exists only in the second. That is the raw/denormalised split observed from outside GA, with the same value in the same place for the same reason — it cannot be known from the event alone, so it cannot be in the layer that is written one event at a time. geo and device, by contrast, are on every exported row including intraday, which is the ingest-time mechanical resolution above.

A.1.3Why lookup cost is not the reason

Why the store exists: retention, not lookup cost. The tempting answer is that the pass needs no table because it can join raw to raw — find the visitor’s first_visit row and read the arrival values off it. That works right up until raw is pruned. §1.5 banks on pruning raw to recover the storage doubling three layers cost; the moment the horizon passes a visitor’s first visit, their acquisition is not expensive to recover, it is gone, and every subsequent event they generate is permanently unattributable. Retaining raw forever to avoid that gives back the one mitigation the third layer had. A visitor-cardinality row survives the prune because it is not event-cardinality.

A.1.4The same test that removed the session table

So: one row per visitor, written when the first_visit event is seen, holding the arrival values. Maintained by the pass, not by ingest — the property that mattered for ITP and for keeping append pure is that the write path does no lookups, and that is untouched. Reports never join it either; it is an input to the build, and its values reach queries materialised onto event rows like everything else. It is neither owa_visitor reborn (no per-request write, no per-request read) nor a star-schema dimension (no query-time join, no FK on the fact row, so no repeat of the inner-join-drops-the-row failure §2.11 exists to prevent). Calling it a table is accurate; calling the pass stateless would not be.

A.1.5GA: why fourteen months does not bind

GA is worth being precise about here, because its fourteen months do not bind the way the number suggests. With “reset user data on new activity” the window slides on every event, so a user who returns at least once inside it never expires — and first-user attribution rides with the identity rather than being stored beside it. Someone acquired via organic search stays organic on the first-user dimensions forever, unchanged by any later campaign, for exactly as long as the identity survives. What ends it is documented as the identity being lost — cookie expiry, a new device, Safari’s caps — not the retention setting.

A.1.6What follows from GA holding a user record

Two things follow, and they pull in opposite directions. GA must therefore hold acquisition on a user record and cannot be deriving it from its own retained events, since those live 2 or 14 months while attribution persists indefinitely for an active user. The store described above is real and GA has one. But GA has it because GA supports the case, and our own data says the case barely occurs: with Chrome capping any first-party cookie at 400 days, even GA’s “forever” is about thirteen months in the dominant browser, which is the cap the TTL is set just above. The architecture differs; the reachable outcome does not, by much.

A.1.7Who the 0.172% are

0.172% of visitors have an active life longer than thirteen months. Among the 6,761 visitors active in the last 90 days, the oldest first visit is 2025-10-24 — under a year, with none at all over thirteen months, while 171,642 visitors first seen more than thirteen months ago exist in the table and never return. Repeat visits plainly work at short range (120,356 visitors have exactly one prior session), so this is not broken recognition at the margin; it is recognition decaying to nothing well before the window closes. The cause is the same browser cookie physics that set the window: Chrome’s 400-day cap, Safari’s seven days, and people changing device or clearing state. The theoretical hole is closed by the same mechanism that produced the TTL.

A.1.8Why reprocess cadence is bounded by the partition scheme

A swap replaces a whole partition, so the partition is the unit of work. 1.x partitions fact tables monthly for partition_detail_months (default 36) and then merges into blocks of up to partition_max_years_per_block (default 5), bounded by the server's open-file budget — each partition is a file. Carried over unchanged, rebuilding “today” would mean rebuilding the whole month: on the 31st every intraday pass rewrites 31 days, and the job's cost grows through the month for no benefit.
So the denormalised table wants a daily tier at the front — daily while a day is still being rebuilt, merged to monthly once it is final, and into year blocks later. That is three tiers and two merge steps rather than one, each merge a REORGANIZE that rewrites rows, but each bounded: one day's worth daily, one month's worth monthly.
Which gives the late-arrival window a concrete meaning rather than a policy: it is the point at which a day's partition stops being rebuilt and is merged. An event landing after that is outside the window by definition. Setting that number sets the reprocess cost, the freshness, and the merge schedule together — it is the one dial worth getting right.
The raw table needs none of this. If raw is pruned at a retention horizon rather than compacted, it only ever needs DROP PARTITION — free on MySQL and on columnar — so it can stay daily throughout and never pay a merge at all. Tiering exists to serve query efficiency, and nothing queries raw except realtime, which wants the recent end.
“Three tiers” is how this note framed it and is superseded by §2.8.1: what was built is one twelve-month lead whose granularity varies along it, not three schemes with three leads. The mechanics above are unchanged; the framing mattered because it implied a budget per tier, and there is one budget per table.

A.1.9The rebuild-and-swap idiom ports to columnar stores

The pass rebuilds a partition and swaps it into place, and that idiom is not a MySQL trick that has to be abandoned if the reporting store changes. Both tables key on yyyymmdd; rebuild one partition and swap it. MySQL has ALTER TABLE … EXCHANGE PARTITION; ClickHouse has ALTER TABLE dest REPLACE PARTITION p FROM staging, which is atomic and exists precisely for zero-downtime reloading — stronger than MySQL's, not weaker. Delta Lake's replaceWhere is looser still: selective overwrite by arbitrary predicate, with no requirement that the table be partitioned on those columns. (Iceberg unchecked; BigQuery's truncate-then-load pattern is established but its mechanics were not verified.) So the rebuild-and-swap idiom is not a MySQL trick abandoned at the columnar boundary — it is the native idiom on the other side.
Staging must mirror the target, on both engines. Both MySQL and ClickHouse require the staging table to mirror the target — same structure, partition key, ordering and primary key — so staging carries no convenience columns and a schema change must alter both in step. MySQL additionally refuses the exchange where foreign keys are involved, which the denormalised table would not have.
DROP PARTITION is metadata only; REORGANIZE rewrites every row it touches. 1.x already relies on this in production: PartitionRotateCli notes that “drops are not counted at all: DROP PARTITION discards a file and returns”, while extending the lead or merging is a REORGANIZE that rewrites rows. Columnar stores are the same shape only more so — the partition is the storage unit, so a drop unlinks files rather than scanning. Retention is therefore cheap on both; what is expensive on both is updating rows, which this design does not do.

A.1.10What the report work left on v2

Phase 4's report-config item asked for a widget format retrofitted into v1. What shipped (#1044, #1047, #1048) also made that format user-authored, which hands v2 one constraint and one asset. The constraint: rows in owa_custom_report are documents written by people, so the format is a compatibility surface now, and the narrowing that made authoring safe — fixed renderer, formatters chosen by name, excludeColumns as names rather than script — is load-bearing rather than stylistic. The asset: every metric, dimension and sort in an authored definition already resolves through the registry at save time and again at render time, because the registry changes under a saved report. That is the explicit enforcement §2.13 needs once a single table stops refusing non-additive combinations on its own. It was written to validate authored reports; it turns out to be the seam v2 needs for a different reason.

A.1.11Why msec is not fixed in 1.x

owa_request.msec is declared INT and fed the fractional part of microtime() as a string, so MySQL rounds it: the column holds 0 or 1 and nothing else (597 and 560 on the test install). Request ids cannot stand in — they are the tracker's random GUID, unique but unordered — so the 1.x fact table has no sub-second ordering at all. Fixing it in 1.x would be worse than leaving it: existing rows stay 0/1, so old and new rows would order differently inside one report, and a funnel spanning the cutover would be wrong in a way nobody could see. VisualizationFunnel::walk() resolves same-second events as a set rather than comparing them, and the two tests pinning that assumption (FunnelMathTest, GoalFunnelOrderTest) should be retired when v2 lands, not re-baselined.

A.1.13Why v1’s history cannot size the session change

What adopting v2’s session model costs v1’s numbers.

One discontinuity in v1's session-derived numbers, accepted deliberately. Three rules differ, and they are not of equal size:

Event-level history is untouched and nothing already stored is rewritten; the change still wants a UI annotation at its date. Coexistence is cheap because effectively all volume is parallel — v1 keeps its own facts and dimensions, and the shared admin set is 0.1 MB.

And v1's history cannot size it

owa_request does carry per-request medium, source_id and campaign_id, so the question looks answerable. It is not: setTrafficAttribution() stamps the decided, session-sticky result rather than the observation that produced it, so a mid-session tag change is collapsed before it is stored. A measurement on this install returns 0.246%, which is an artefact of that collapsing rather than a rate.

This is the same limitation §2.22 records for validating the attribution model — existing history is not a usable touchpoint log.

Not treated as a blocker. The expectation is that the effect is small: it requires a visitor to re-enter through a second tagged link inside the timeout, which is uncommon outside heavy paid-campaign traffic. If a number is wanted later, touchpoint data supplies it; nothing waits on it.

Touchpoint recording earns its place on data quality, not on this. Attribution is decided in the browser today — setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the verdict rather than the observation that produced it. So the server stores a conclusion it cannot check, and four things follow:

  • A client-side verdict cannot be corrected later. Fix the attribution logic and every row already written keeps the old verdict — there is nothing to recompute from.
  • Attribution dies with the cookie. Clearing owa_c destroys the stack, and the visitor's history is gone rather than re-derivable.
  • The 60-day original window is measured on the client's clock, which is unverifiable and, on a skewed device, wrong.
  • No post-hoc enrichment. This research measured the star's one real advantage as rewriting a dimension without touching facts (589×); attribution is precisely the dimension worth rewriting, and today it is the one that cannot be.

A.1.20A duplicate marker cannot happen; a lost beacon takes its marker with it

The marker's event id is derived from its own content like every other event's — wideStringGuid(site_id + visitor_id + session_id + ts + event_name) (§2.1.2) — so the same raise arriving twice produces the same row and the second insert is a duplicate-key no-op. No coordination is needed.

Concurrent tabs are not the case this covers. Two tabs that both decide a session is new each call Util.generateRandomGuid() and get different session_ids, so they raise two distinct markers, which is the right answer rather than a duplicate. A tab that reads an existing session from the store raises nothing at all, because is_new_session_start is scoped to the one request that created the session (§2.6.2). What the derived id collapses is one request received more than once.

A marker cannot be lost while its own page view survives, since both are one atomic write; losing the beacon loses both. A negative remainder is therefore a defect signal rather than a rounding artefact.

A.1.23Why a dimension names a shape instead of carrying SQL

The tempting shortcut is to let each computed dimension carry its own SQL. That works until the reporting store is not MySQL — and §2.1 deliberately holds that door open behind a second DSN. Then a store move rewrites every derived dimension by hand.

The dialect layer does not cover this today. MysqlDialect abstracts DDL and introspection — partitioning, keys, indexes, session sql_mode — and has no expression surface, nor an interface a second implementation could satisfy.

Declaring a shape is cheap rather than a mini-language only because the column-admission rule keeps the set closed. Once dimensions carry SQL strings instead, converting them means recovering intent from expressions — which is exactly where the report controllers were before they became configuration, and the narrowing that made that safe was the same move: names from a known list, never code (§1.7).

A.1.24What bounds the late-arrival window, and what does not

1.x has two queues, and they are not the same mechanism:

  • The incoming queue is a file. Tracking events are written to disk and processed later. Every event goes through it when it is enabled, and what it costs the window is simply drain cadence — a configured number, not a thing to measure.
  • The DB queue (owa_queue_item) is a retry queue, and it is the one with unbounded tails. An event reaches it on EVENT_FAILED, and the case that actually puts it there is a session-update event that cannot find its session — SessionHandlers aborts with “no existing session was found”, and SessionCommerceSummaryHandlers with “Session does not exist yet”.

That entire class of failure does not exist in v2. There is no session row to look for: session-scoped values ride every event and the event table is the session-grain table (§1.3). An event that would have been re-queued in 1.x is, in v2, just a row. So the retry queue’s reorder behaviour describes a failure mode v2 deletes, and sizing the window against it would be sizing against the wrong thing — conservatively, but wrong, which is more damaging than it appears when the number sets the whole rebuild cadence.

What is left to bound is therefore drain cadence plus client-side lateness: an unload beacon that landed behind a subsequent hit, a retry from the browser, a tab restored from bfcache, a device that was offline. None of that is visible in any server queue, which is the part that still needs a number.

A.1.31GA hit the same problem and pairs the ids

GA4 counts sessions by estimating distinct ga_session_id values, not by counting session_start events, and the parameter rides every event rather than only the marker. Two details are worth carrying:

  • ga_session_id is not unique on its own. It is the session-start timestamp in seconds, so two users starting together collide. Google's documented method is to count distinct combinations of user_pseudo_id/user_id and ga_session_id, joining the user id to the session id to get a unique identifier. Our session id is built the same way, which is why §1.2 counts the pair.
  • Counting the marker gives a different answer from the metric. Google documents both causes: session_start can be filtered out while the session id is still generated, and reports estimate with HyperLogLog++ at precision 12 while BigQuery counts exactly. Our marker cannot be filtered independently — it is raised server-side in the same atomic write as its beacon (§2.6.2) — and the count is exact either way.

A.1.33Three storage defects the first v2 table found

All three are in code v1 shares, all three were invisible to v1, and all three are the same shape: a rule written when absence had one storage form, applied to a table whose premise is that it has another.

  • Entity::applyStorageDefault() looks the (not set) label up by PROPERTY NAME across every registered map, with no notion of which entity is being written. A v2 column merely sharing a name with a v1 tracking property inherited v1’s sentinel: language, host and page_title all landed in owa_event_raw holding the literal string.   • Entity::writeValue() coerced an absent NUMERIC value to 0 unconditionally, where the text branch already honoured nullability. 0 is a real number, so such a column has no way to say absent at all — a beacon carrying no client clock is not one reporting zero skew.
  • setDataType('integer') turned absence into 0 before any handler saw it, because Event::get() answers false for a property the event does not carry and false is not numeric. Every registered integer property arrived on every event holding 0, mentioned or not. Absence now stays absent; garbage still becomes 0, which is the half that guard exists for.

v1 is unaffected by any of them, which is why they survived: its numeric columns are NOT NULL and store 0 either way, and its text columns already hold the label on every historical row. The general lesson is narrower than “shared code is risky” — it is that a compatibility rule needs a scope, and each of these had none, so it applied to rows that had nothing to be compatible with.

Nothing downstream filters anything, because the other version is not in scope: the picker lists one version's names with no change to CustomReportEdit, validation follows automatically, ResultSetManager needs no niceness-sort filter, and the name-collision blocker below dissolves — separate partitions cannot overwrite one another, so keying $this->dimensions by entity may prove unnecessary.

The distinction is scoping the registry once versus remembering to discriminate at ten consumers. Open: the service is a boot-time singleton, built before a query knows its profile, so either every accessor takes a version or the version becomes request-scoped ambient state. The explicit parameter is safer — ten call sites is tractable, and it keeps the version visible at each consumer rather than hidden in ambient state, the same silent-wrong-answer failure.

BLOCKER: the normalized dimension registry is name-keyed, so v2 would overwrite v1

The claim in §2.23 that dimensions behave like metrics is only true for denormalized ones. registerDimension() loops $entity_names but writes to two different shapes:

if ($denormalized) {
    $this->denormalizedDimensions[$dim_name][$entity] = $dim;   // entity-keyed
} else {
    $this->dimensions[$dim_name] = $dim;                        // NAME-keyed — last write wins
}

Measured of 103 registrations: 58 denormalized (safe), 41 normalized against a single entity (the overwrite is a no-op), and 3 normalized against all seven $fact_table_entities — month, userName, priorVisitCount.

This blocks v2 for all 44 normalized dimensions. v1 registers pageTitle against its dimension table, v2 registers pageTitle against the event table, and the second write replaces the first — the v1 definition is gone from the registry before any entity filter could run. No downstream selection can recover it, and renaming is not an option.

Fix: key $this->dimensions by entity, matching denormalizedDimensions, which already has the right shape. getDimension() has exactly one caller (ResultSetManager:970), so the change is that call site plus the registration loop. This is a prerequisite in 1.x: the registry must be able to hold two definitions under one name before a second set can exist at all.

Unverified, worth a trace: the 3 normalized multi-entity registrations keep only the last of seven entities, and $dim['entity'] then drives the JOIN (entityFactory(), getForeignKeyColumn(), $db->join()). date is registered against the same list with denormalized = true while month beside it is not, which looks like an oversight rather than a distinction. Not claimed as a live defect until traced.

Do not add the v2 entity to $fact_table_entities

Dimensions are registered against a shared array: registerDimension('date', $fact_table_entities, 'yyyymmdd', …). Appending the v2 entity to that one variable would make every dimension claim to work on v2 while still naming v1's columns — a one-line change producing broadly wrong SQL, and the obvious-looking way to “add v2 support”. v2 needs its own registrations with its own columns, exactly as metrics do.

Open: the vocabulary (site / profile / property / site_family) wants settling before anything is built, since it will surface in the UI, the API and the schema at once.

A.2.4Considered: an Observation Profile carries the version

Superseded by §2.23. The question was how a query knows which schema generation to read. This proposed answering it in the data model — decoupling the tracked website from the profile measuring it, so one website could have several profiles and each profile declared its version. It is the path GA took to GA4, and it works, but it is a large structural change to answer a question that a URL path answers for nothing. Recorded because the analysis of why the automatic signals all fail still stands, and anyone revisiting this should not re-derive it.

Everything above resolves the version at query time, and every automatic signal for doing so fails. A date boundary cannot work: §2.21 makes cutover per-feature so there is no single instant, dual-write means both stores hold the same period, the switch-off is an administrator's action rather than a release date, and the queue is asynchronous so an event accepted before a switch can land after it. Coverage watermarks fail for the same reason — during overlap both stores answer, and the data cannot say which is authoritative. An install-wide setting fails differently: since no data is migrated, v1 holds the history permanently (§2.24 keeps v1 reporting precisely for that), so a global flip would blank every historical report.

The proposal is to stop resolving it at query time and carry it in the data model instead. Decouple the tracked website from the profile that measures it: one website may have several profiles, and a profile declares its version. The whole experience fans out from the profile — a v2 profile shows v2 navigation, v2 reports, and queries the v2 REST endpoint. This is the path GA took to GA4. Each open question below gets a structural answer instead of a rule someone has to remember:

QuestionHow the profile answers it
Which version does a query use?The profile's. Never inferred, timed, or defaulted
Spanning the boundaryStructurally impossible — a result set is one profile — rather than a rule someone must remember. No cross-store union, no summing distinct_count across a seam

A.2.5What it requires Measured

site_id is md5($domain) (Site::generateSiteId(), and inline at SiteManager.php:44), so two profiles for one domain are impossible by construction. Only three call sites derive it, and just one re-derives at runtime — ServiceUser.php:283, in the permission path, which is the edge needing care and tests.

Two things are already in place. site_family exists as a column on owa_site and is written but never read anywhere — a dormant grouping slot, so “tracked website” can be defined freshly rather than migrated. And the per-site session store (owa_s_<siteId>) already gives two profiles on one domain independent session cookies, which is both correct and exactly GA's _ga_<property>.

Do not rewrite existing site_id values

Every site_id in the wild is md5(domain) and every fact row references it. The change is to stop deriving new ones and treat the column as opaque — existing identities keep their values and existing data is untouched. Decoupling identity from derivation does not require reissuing the identities already handed out.

No second tracking tag, and no second tracker, per §1.9. The tracker is extended in Phase 3, so it emits v2-rich events and the server degrades them for v1 — not v1-poor events upgraded for v2.

So the profile model requires no client change whatsoever: one tag, one event, and the server writes each received event into every profile configured for that website. The site → profiles mapping is server-side, so the page never learns that profiles exist, and §1.9's promise holds — nothing about the page changes on cutover day.

Independent of v2, md5(domain) already prevents tracking two configurations of one domain, renaming a domain without orphaning its data, and expressing one property across several domains. The decoupling is additive 1.x work with standalone value.

What the profile does not do is spare ResultSetManager. It settles where the version comes from, not how the manager acts on it, so the entity-pool change of §2.13 survives intact and is still the work: resolve the version from the profile behind siteId, filter candidate entities to that version before arsort($niceness), and error when none resolves. setSiteId() today only records a query param and a constraint rather than loading the site, so there is a little plumbing from siteId to a version — but nothing new threads through the REST API or the report configs, which is precisely what the profile model buys: an unambiguous input already present in every query.
