Part One

What v2 is

One table for every event, and the consequences that follow from it.

1.1The shape Decided

Every tracked interaction becomes one row in one table, GA4-style, replacing ten parallel fact tables and their dimension satellites. Ids are content-derived, so a write is a single insert with no lookups: no session upsert, no dimension check-and-create.

Measured Disk is a wash — within ±2%, because 1.x already denormalises 58 dimensions onto its facts. The win is not storage. It is throughput, one definition per metric instead of nine commerce metrics existing twice, and the deletion of an entire class of dimension-FK bugs this release cycle has been spent fixing.

The star keeps exactly one real advantage: post-hoc enrichment is 589× cheaper — rewriting one dimension row versus 565k event rows. That advantage is a row-store artefact and inverts on a columnar engine, and it has been explicitly traded away.

1.2What it deletes

Against the live registry: 78 metrics × 100 dimensions = 5,493 valid API pairs. Under v2, 4,443 (81%) work unchanged, 770 (14%) reference the eleven *InVisit dimensions which have zero references anywhere outside their own registration, and 280 (5%) need an exit page served by an is_exit flag. Nothing is genuinely lost.

Also retired: owa_session's 121 columns (45 of them goal columns) and nine derived date-part columns per fact row. The dead owa_exit entity is already gone — removed from 1.x in #1048 with its registration and its setting. Its table is deliberately left in place: dropping it is a destructive migration and a separate decision from deleting dead code. The name also moved to the legacy class-name test's RETIRED list, which asserts it is gone rather than merely dropping it — a real backward-compat break, taken deliberately.

base.feed_request joins it, and for the same kind of reason. It was carried in the v2 taxonomy as “OWA-specific; kept” until 20 Sep; measuring it showed the collection path is dead — newest row 2021-11-09 on peteradamsphoto and 2019-08-17 on demo. §1.4 records the removal. As with owa_exit, the table stays where it is: peteradamsphoto holds 350,744 historical rows, and dropping them is a destructive migration that is a separate decision from deciding v2 will not collect this. What v2 drops is the event type, the entity and the one dimension — feedType — that reads it.

The risk inverts. 1.x's entity boundaries prevent non-additive metric combinations — the resolver intersects entity sets, so bounceRate × pagePath is correctly refused today. A single table has no such boundary, so v2's registry must enforce explicitly what the schema currently enforces implicitly, or it newly permits nonsense.

1.3Sessions Decided

The design rule this produced: never make a record's existence depend on a single packet. A marker event rides on one beacon, so losing it erases the session while its other events still count. GA4's taxonomy is the guide, because it is the vocabulary the market already speaks and because arguing about event names is not where this project should spend its budget. Emit the markers; never count from them. They exist for grain, not merely for payload. A metric and a dimension combine only where a row exists at their shared grain — which is the entire job owa_session's 121 columns do in 1.x, and why removing the session-grain table would make “sessions by landing page” not slow but unavailable. They are also the natural thing to mark as a goal event, and they carry the attribution the client knows at that instant.

What they must not be is the basis of a count. GA4 emits session_start yet counts sessions by estimating distinct session ids, precisely because the marker goes missing (consent mode, app lifecycle). v2 counts from the rollup for the same reason, so a lost marker degrades that session's attribution and erases nothing. fsts stays on every event as the redundant floor for new-visitor.

One authority per metric — the trap this creates

If session totals come from the rollup while session breakdowns come from marker events, the two disagree whenever a marker is lost and the breakdown stops summing to the total. Both numbers are defensible, neither is wrong alone, and a user who notices stops trusting the product. So the rollup is the authority for session counts and their breakdowns, which means it carries the session's dimensional context — taken from the session's own events — plus a parameter map for custom variables.

The parameter map. 1.x spends ten columns (cv1_name…cv5_value) implementing exactly five custom-variable slots. The fixed slots are not a preference — they are what a fixed-width session row forces. On a parameter map the limit disappears, which is the unregistered custom-variable segmentation v2 wants.

The rollup's column list is a rebuild away, not a ceiling. Because it is derived from retained events, adding a session dimension later costs one rebuild — 50.4 s over the full corpus — and applies retroactively to all existing data with no change to collection. That is post-hoc enrichment recovered: the star's one measured advantage in this research (589×) was rewriting a dimension without touching facts, and a derived rollup restores exactly that at the session grain.

The session table proved unnecessary

An earlier draft kept a session-grain derived table (~30 columns, owa_session's grain reborn). It did not survive review: the v2 session primitives already make every session metric a single-pass aggregate over the fact table. Deltas are additive, so engagement time is SUM(delta) by anything; the engaged flag is sticky, so engaged sessions are a DISTINCT IF; and session-scoped values (source, campaign, landing page) are stamped on every event — a decision made for attribution that turns out to govern query shape. Measured: “sessions by landing page” as a first-event join costs 3.1 s over a year; as a plain group-by over sticky values, 215 ms. The session's context is embedded in its event rows, so the event table is the session-grain table. (This is also why owa_session genuinely is needed in 1.x — its events carry none of this.)

The markers are the breakdown fast path. With session_start in the stream, an interactive breakdown counts marker rows instead of deduplicating session ids — measured via 1.x's is_entry_page proxy: 92 ms vs 373 ms over a year, 218 ms vs 1,855 ms over three. The expensive DISTINCT is confined to the rollup job, bounded to its trailing window. A lost marker undercounts the breakdown and lands in (unknown). Duplicate markers (tab races, queue redelivery) are structurally impossible: the marker's event id is content-derived — hash(site_id + session_id + 'session_start') — so racing writers produce the same row and the second insert is a duplicate-key no-op, with no coordination and across subdomains, where the Web Locks API (origin-scoped) could not reach. A negative remainder is therefore a pure defect signal. The derived session table demotes to an optional materialization: derived state an install can add later with one rebuild if breakdown latency outgrows these shapes, a cache with a trigger condition rather than architecture.

Where a total and a breakdown meet on one screen, the total is authoritative and the API closes the gap — a synthetic row with dimension value (unknown) and the remainder as its metric value, which is simply true: sessions the total can see and the breakdown cannot attribute. The invariant “breakdowns sum to totals” is enforced at the API envelope rather than assumed from storage, and v1 already has the seam — result sets carry aggregates beside the dimensional rows. Two rules keep it honest: the row appears only for a positive remainder and is labelled (unknown), never blended into (not set); and a negative remainder is never clamped — breakdown exceeding total means a defect, and absorbing it would silently convert the parity harness's clearest bug signal into invisible correction.

Measured — the cost depends on how rich the stream is

1.x averages 2.10 events per session and 1.15 sessions per visitor, measured across two live installs. At that density the two markers would add roughly 89% to event volume, which is what made a flat rejection look reasonable.

But that density is an artefact of 1.x tracking almost nothing but pageviews. With the automatic events above — scroll, engagement, clicks, form interactions — a v2 session is more like 6–8 events, and the same two markers cost 25–30%. The marker overhead is inversely proportional to stream richness, so it falls as v2 does its job.

Goal events are author-named events Decided

They are called goal events, not key events Decided — 3 Sep 2026. GA renamed its conversions to key events in 2024, and this section was written in GA's vocabulary. OWA keeps its own word: a 1.x installation has goals, the people using it say goals, and “key event” would make every existing user translate before they could find the screen. The mechanism below is unchanged and is still GA's shape — only the noun is ours. Where this document describes what GA does, it still says key event, because that is what GA calls it.

1.x had twenty numbered goal slots. v2 has none: an author names a goal event and gives it an event type and a condition — “a click whose target is x” — and when the condition matches, the server materialises an additional row whose event_type is that name. The same mechanism as session_start above, and the same shape as GA, where a key event is an event whose name is marked as key.

The numbered slots are already gone in 1.x Shipped — see §2.6. A goal event is a row in owa_goal_event with its conditions in owa_goal_event_condition, which is this shape a schema early. So v2 inherits authored goal events rather than introducing them, and the migration is a re-home rather than a redesign.

Chosen over annotating the triggering event with a goal-event-name column because it needs no schema change: event_type already carries the name, so the table stays at 40 columns and per-goal-event reporting is an ordinary GROUP BY. Three rules come with it, stated here rather than left to whichever code is written first:

  • The materialised row is never counted as an ordinary event — the rule already set for session_start, for the same reason.
  • The triggering event stays an ordinary page_view with is_goal_event = 0. Flagging both would double-count and blur which row is the conversion.
  • The event_type vocabulary therefore stops being closed. Intended, given the site-opt-in group above — but stated so nobody discovers it by naming a goal event page_view.

Counting them is one metric plus one dimension, and isGoalEvent is registered as a dimension so it can be constrained on — in this engine a constraint name resolves through the dimension registry, so unregistered means unfilterable. Per-goal-event metrics follow GA's sessionKeyEventRate:<name> shape spelled in our noun — sessionGoalEventRate:<name> — parameterised rather than pre-registered, because the set of goal events is per-site while the catalog is built once per process. Full reasoning in EVENTS.html §7.14.

Counted once per session, for now Shipped — 1.x offers once per session and nothing else, and the save clamps to it whatever a request asks for. A conversion in 1.x is a column on the session row, so a second match in the same session has nowhere to go: once-per-event is a setting the storage can hold and the handler cannot honour, which is the quietest kind of wrong. v2 removes the constraint rather than the setting — a materialised row per match is per-event by construction — so the choice becomes real at cutover and the clamp is what should be deleted then.

1.5Visitor identity Decided

A visitor is arbitrary: it must be assigned, carried and trusted, where a page or a referrer is just a value a report groups by. That is what makes it the one identity v2 has to mint, and the only one it can get wrong.

Defect carried forward from 1.x

The visitor id looks 63 bits wide because it lands in a BIGINT. It is a 10-digit unix timestamp followed by 6 and 3 random digits, so inside any one second the space is 10⁹ — about 30 bits.

Expected collisions per year: 1.4 at 10 new visitors/sec, 156 at 100/sec, 15,752 at 1,000/sec. Each one silently and permanently merges two people.

Not a competitive gap — GA's _ga uses the same construction with one more bit. Correction: the entropy cannot be improved. The construction uses 60.6 of the 63 bits a signed BIGINT allows, and re-dividing the budget is provably worthless — coarsening the time bucket by k multiplies ids-per-bucket by k (pairs by k²), divides bucket count by k, and grows the random space by k, so k cancels; measured across second/minute/hour/day granularity the collisions per year are identical. The rate depends only on the total budget and arrival rate: ~0.8/year at 10 new visitors/sec. An accepted, quantified limit, not an open defect. The discarded salt was removed instead (PR #1017) — it could not be honoured for the same reason.

  • is_new_visitor stops being a marker and becomes derivable from the first-seen timestamp already carried on every event — the same rule that governs sessions.
  • Known users resolve at collection time only. Events collected before someone identified themselves stay anonymous forever. Same answer as goals and bot reclassification, for the same reason.
  • Cross-device requires a site-supplied user id or does not happen. No fingerprinting, no IP-and-user-agent heuristics — a probabilistic join produces a number nobody can check.

1.6Freshness and the API Decided

Two freshness tiers, and they separate helpfully. Cost tracks window width, not table size — so a thirty-minute window is trivial against raw events while a year is not. The rollup buys breadth, not recency.

ViewReadsFreshness
Realtime — “what is happening now”raw events, short windowimmediate
Historical — “last month by source”rolluplast job run

So the freshest number in the system is the most naively computed one, and “is my tracking working?” — the question that must never be stale — never touches a summary.

Realtime is one screen, not a mode on every report Decided

1.x expresses realtime as a Live View toggle on every report, and what that does is re-run the historical query more often. Each widget owns a setInterval calling getNewResultSet() — its full query, over the full period. On the traffic report that is nine widgets, so Live View across thirty days issues nine full-period aggregations every fifteen seconds, thirty-six queries a minute, to learn about whatever arrived in the last fifteen.

The cost scales with period width × widget count and not at all with how much changed, which is the tell: it is asking a historical question to get a realtime answer. The two tiers above exist precisely because those are different questions with different costs.

So realtime becomes a single dedicated screen — a short window over raw events, answering “what is happening now” and “is my tracking working”. That is the question the table above says must never be stale, and on a narrow window it is cheap by construction: one query, one partition, no summary touched. It is also what GA ships, and it removes the per-report auto-refresh control along with the per-widget polling behind it.

What this does not fix, and should not pretend to. Historical reports remain stale for the current day, because they read the rollup and the rollup runs on a schedule. The answer is composition rather than polling — a period metric is rollup(closed days) + raw(today), where closed days never change and so cache indefinitely, and only today's slice is volatile and bounded to one partition. That makes every report current without any refresh loop, and it is worth doing on its own merits. Recorded here as the follow-on, not folded into this decision.

Measured — the trap this creates

Partitioning is on yyyymmdd, so the obvious way to write “last 30 minutes” does not prune, and is unselective enough that the optimiser abandons the timestamp index too:

Eventual consistency is a rollup property, not a scheduling one. A rollup that advances a watermark can never converge: an event arriving after the watermark passes its own timestamp is not late, it is lost. So the rollup recomputes a trailing window idempotently. The window is the lateness horizon, and it is the number a test asserts against.

The API is the contract for both UIs. Metric and dimension discovery already exists — resultSet.relatedDimensions is what feeds the existing explorer widget's pickers — so v2 formalises it rather than inventing it. Freshness belongs in the response envelope beside the row count, because it is a property of a result set, not of the installation.

1.7The UI layer Decided

  • Reporting: client-rendered against the API. Charts and the grid rest on abandoned jQuery plugins (flot, jqgrid), which have to be replaced regardless.
  • Admin: stays server-rendered. It is forms and tables; a SPA buys nothing.
  • Reports become JSON. Most existing reports are one shape wearing different labels, and the bespoke remainder are largely dashboards — so a generic widget format with grid layout descriptors covers both, and can be retrofitted into 1.x additively.
  • Realtime is its own screen, not a refresh toggle on every report — see §1.6. One narrow view over raw events, which retires the per-widget polling that made Live View cost nine full-period aggregations every fifteen seconds.
  • Both reporting UIs run side by side for as long as wanted, sharing one session. A separate login for each would make comparison tedious enough that nobody does it — which turns the overlap period into a rubber stamp.
  • The charted metric is chosen by the reader, not by the report. Shipped in 1.x — clicking a metric box redraws the trend on that metric, and the boxes mark which one is charted. This paragraph used to end “there is no click handler on a metric box anywhere in the reporting JS”; there is one now, and chartMetric already means what the next paragraph says it should. Kept here because what v2 inherits is the reasoning, not the diagnosis: the result set already carried every series, so the only thing missing was a way to ask.

    This changes what the key means, which is why it belongs here rather than in the format: chartMetric stops being the charted metric and becomes the one charted first. Its absence keeps its current meaning — draw no chart — because a report that wants no trend is a different statement from one that has not chosen a starting series.

1.8Privacy and retention

  • Anonymise by default. The implementation exists; the default is simply wrong for a privacy-positioned product.
  • Installation-wide retention, enforced by a scheduled job, with a real default rather than “forever” — deliberately not per site, see §4.5.
  • An erasure command — forget visitor=<id> — reaching events, recording payloads and rollups, and tested, because an erasure path that silently misses a table is worse than none.
  • Retention and erasure share mechanics and must not share a code path. One is time-based and bulk; the other is subject-based and exact.

The single table cuts both ways here: erasure by visitor_id becomes one delete in one place, but denormalisation means an email in a URL query string now sits on every event that saw it. Erasure has to scan, not look up.

1.10The tables Decided

The column-admission rule (revised): a field is a column if its name is known at release time and it is scalar; params (JSON) is reserved for what cannot be a column — site-defined keys unknown at release time (unregistered custom variables; the alternatives are user-controlled DDL, a forbidden registration step, or a forbidden EAV join) and nested arrays (commerce items, which cost 1.x a separate fact table and a join). Params buys nothing else: the wide prototype measured storage as a wash, JSON extraction is slower than a column, and MySQL 8 INSTANT ADD COLUMN removes the ALTER cost for release-known fields. Columnar stores agree more strongly — wide and sparse is their native shape, and their JSON shredding covers the dynamic keys (one param key, one type, enforced at ingest). owa_event lands at 40 columns against owa_request's 58 + owa_session's 121.

Part Two

Derived dimensions declare a kind, not SQL Decided

Some new dimensions are functions of columns rather than columns — sourceMedium and firstSourceMedium concatenate two, and newVsReturning maps one (EVENTS.html §7.7, §7.12). The tempting shortcut is to let each carry its own SQL, which works until the reporting store is not MySQL — and §1.10 deliberately holds that door open behind a second DSN. Then a store move rewrites every derived dimension by hand.

The dialect layer does not cover this today: MysqlDialect abstracts DDL and introspection — partitioning, keys, indexes, session sql_mode — and has no expression surface, nor an interface for a second implementation to satisfy.

So a dimension declares its kind and the dialect renders it, and the reason that is cheap rather than a mini-language is that the column-admission rule keeps the set small and closed. Everything proposed so far needs three: concat, map and datePart. That makes a store migration O(kinds), not O(dimensions) — three renderers to write once, rather than a bill that grows quietly every time somebody adds a dimension.

Worth settling before the first one is built. Once dimensions carry SQL strings, converting them means recovering intent from expressions, which is precisely where the report controllers were before they became configuration — and the narrowing that made that safe was the same move: names from a known list, never code (§1.7).

Two defects the conversion uncovered

ConfigurableMetric's calculated type had never worked. It calls setChildMetric(), which existed only on CalculatedMetric — not on Core\Metric, which ConfigurableMetric extends. Supported on paper, fatal on first use, and never registered by anything, so nobody found out. “Supported but unused” was doing more work in the earlier draft than it could bear.

And registerMetricDefinition() filters its params with array_intersect_key() against a fixed map, so any key missing from that map is silently dropped rather than rejected. A new kind's parameter vanishes and the metric renders a subtraction against nothing.

What resists, and why it does not matter. Seven classes remain: three goal classes (which read the siteId request param to build per-site labels), repeatVisitors (the one composite expression), one unregistered class a parity test names by literal, and ConfigurableMetric itself. Every one is gone in v2 — the numbered goal slots become named goal events with a parameterised metric, and repeatVisitors becomes the newVsReturning dimension (EVENTS.html §7.7, §7.14). The evaluator stays out of scope. Formulas run through ResultSetManager::evalFormula(), which @ eval()s a PHP string — but moving a repo-shipped formula into a repo-shipped config entry does not move the trust boundary. The parser is the prerequisite for a user-authored metric builder, and a plain four-operator grammar would not cover today's set, since round(actions / visits, 1) needs function application. 1.12“(not set)” is a presentation choice, never a stored value Decided

Measured 16 tracking properties in modules/Base/Module.php declare 'default_value' => '(not set)'. Because those properties are required, the string is written to the fact row on every event that does not carry a real value — user_name among them, so on a default install every row carries the literal text.

This is the §1.12 problem in a different costume. A magic string is not absence; it is a value that merely looks like absence, and the difference shows up everywhere downstream. It groups as its own bucket, so a pie over the dimension draws a “(not set)” slice indistinguishable from a real category. It sorts among real values. It cannot be told apart from a visitor who genuinely typed that. And the codebase already knows it is lying: Visitor.php checks != '(not set)' before using a name, and TrackingEventHelpers does the same for REMOTE_HOST and search_terms — three separate places reconstructing an absence the schema threw away.

v2 stores absence as NULL and decides the label at render time. The reporting layer already formats values; “show nothing as (not set)” is a formatter's job, one place, changeable without touching data, and translatable. Baking it into the row makes a display string permanent and unrecoverable — the one thing §1.10 says facts must never be.

Follows the same rule as the boolean columns below it: the store records what happened, the presentation layer decides how to say it. Note this narrows what a nullable column means rather than widening it — NULL becomes unambiguously “not provided”, which is only useful if the write path never also writes a sentinel meaning the same thing.

1.13Boolean columns carry three values Open

A two-state fact must not be storable as three. In 1.x the boolean fact columns are nullable with no default, so is_repeat_visitor holds 1, 0 and NULL — and every one of those is a distinct GROUP BY bucket. A pie over the dimension draws two separate slices that both format as “No”, which is how this was found.

The cause in 1.x was a derivation that returned true for one branch and fell off the end for the other (setRepeatVisitorFlag, unchanged since 2015). That specific bug is fixed, but the shape is the problem: nothing in the schema, the entity layer or the ingestion pipeline stops a write path leaving NULL in a column that has only two meanings.

Update, 28 Aug — fixing the derivation was not enough, and the reason generalises. Rows written before that fix still hold NULL, so the third bucket survives in the data whatever the writer does now: the pie was still drawing two slices labelled “New” on a live install, months after the derivation was corrected. The client half had to change too — the chart now sums by label rather than emitting one slice per row, because a valueLabels map that folds two values onto one name is a statement that they mean the same thing, and a renderer that still draws them apart contradicts it. Two things for v2 follow: NOT NULL DEFAULT 0 fixes new writes and nothing else, so a schema that has ever permitted the third value needs a migration to close it; and any renderer that groups by a labelled value must fold labels, not rows.

For v2:

  • Declare booleans NOT NULL DEFAULT 0. The storage should refuse the third value rather than rely on every writer remembering. 1.x cannot retrofit this cheaply — it is an ALTER over every install’s session and fact tables — which is exactly why it belongs in a schema that is being defined rather than migrated.
  • Give the type a formatter, not each report. A boolean dimension should render as Yes/No wherever it is shown, from its declared type. 1.x now does this, and the same seam should exist in v2 rather than every widget re-solving it.
  • Let a report rename the values. Yes/No is the correct default and a poor label for a specific question — “New/Repeat” reads better on a visitor-type chart. 1.x added a per-widget valueLabels map for this; keep the split, with the type supplying the default and the report overriding it.
  • Decide NULL’s meaning where it is genuinely unknown. Some flags really do have an unknown state. Those want an explicit three-state type, not an accidental one.

Open question: whether 1.x should backfill the existing NULLs or normalise at read time. Reporting currently cannot express a normalised column — the dimension registry prefixes a table alias onto whatever it is given, so COALESCE(...) is not expressible as a dimension today.

1.14Three storage layers: raw, denormalised, rollup Decided

The fact table stops being primary. Events land in a raw, append-only table exactly as they arrived. A pass reads that and writes a denormalised fact table with session- and user-scoped values materialised onto every row. The day rollup aggregates from there. Queries hit the denormalised table; the raw table is the record of what was observed.

This began as an attempt to answer one narrow question — where does acquisition source live — and ended up dissolving most of it. The thing that makes it work is that a derived table can be rebuilt. You never UPDATE a fact row; you regenerate a partition. So no-retroactive-fact-updates survives intact, and it stops being a constraint that forces values onto the wire.

What it resolves, and each of these was an open question before:

  • No keyed store at ingest. Acquisition source is the visitor’s earliest raw event; session source is the session’s first. Both derivable in bulk, so no visitor store and no session store, and ingest stays a pure append with no lookups.
  • ITP becomes irrelevant. Safari caps a JS-set cookie at 7 days, and at 24 hours when the visitor arrives from a URL carrying gclid or fbclid — which is precisely the tagged arrival worth attributing. Any design that carries a long-lived attribution anchor client-side has that ceiling. Deriving from raw does not.
  • Columnar stores get what they want. Bulk load, partition replace, no row-level updates. The plan already says MySQL first with an eye to columnar later; this is the shape that survives the move rather than being rewritten for it.
  • The model becomes re-derivable. Change an attribution model or a lookback window, reprocess, replace the table. A verdict written at ingest cannot be revisited; evidence plus a pass can.
  • Identity stitching works. A user_id arriving mid-session relabels that visitor’s earlier events on the next pass, which is impossible if the fact row is final at write.
  • Session finalisation has a home. Engagement time, exit page, bounce and duration are not knowable until the session closes, so they were never materialisable at insert by any mechanism.

Realtime is a query of the raw table, and that is why its dimension set is smaller rather than arbitrarily limited. Only what is on the event can be reported live. Checked against GA’s Realtime API schema, whose entire dimension list is appVersion, audienceId/Name/ResourceName, city, cityId, country, countryId, deviceCategory, eventName, minutesAgo, platform, streamId, streamName, unifiedScreenName — every one derivable from the event itself, and no traffic-source dimension at all. The four metrics are activeUsers, eventCount, keyEvents, screenPageViews. Event-scoped custom dimensions are excluded, which reads as a cardinality limit rather than an access-path one.

OWA’s realtime can be richer than GA’s, for a reason already decided. GA carries no session-scoped values on the wire, so its session source is not raw-resident. OWA carries all of them — session_id, session_referer, prior_session_id, is_new_visitor, psts, sts, plus the tagged_* keys. So a raw-log realtime query gets event and session scope for free. Only user scope waits for the pass.

What to carry and what to derive

The rule is not “carry what cannot be derived”. That rule was tried and it is wrong: GA keeps first-seen and session count client-side — _ga is GA1.1.<random>.<first-seen> and the session cookie carries $o<session count> — and both are trivially derivable from history. The rule that actually explains the practice is about what kind of thing the value is.

  • Counters and anchors the client already maintains — carry them. vid, sid, session count, first-seen, last-hit. The client computed them for its own session decision, so sending them costs a few bytes and saves the server an expensive per-visitor ordered scan. Carrying is free denormalisation performed where the answer already exists, and the value is correct in raw immediately, with no pass.
  • Resolutions needing server-side data — derive them. Source and medium from the referrer and tags, geography from the address, device from the user agent. The client cannot know these without shipping OWA’s tables to the browser.
  • Decisions and models — derive, never carry. This is the one that matters. attribs is not wrong to retire because it is reconstructible; it is wrong because it is a verdict. A model frozen in a cookie cannot be revisited when the model changes, which is the reason Universal Analytics collapsed __utmz into a single id cookie and processed server-side in the first place.

By that rule nps and fsts stay — they are observations — and attribs goes, as already decided in the attribution notes.

Wire events and materialized events are different sets

One beacon can become several events. The client sends a single page_view carrying flags; the server raises session_start and first_visit from them. Confirmed against GA by capture: a first page view arrives as one en=page_view with both _fv=1 and _ss=1 and no separate beacon, and the two appear in BigQuery as distinct event_name rows.

That expansion happens at INGEST, into the raw log — not in the pass. The distinction is the whole point and it is easy to get backwards:

  • Per-beacon derivations go in at ingest. Raising first_visit from is_new_visitor_created is a pure function of one beacon. It needs no other event, no lookup and no ordering, so it belongs on the straight-line path where there is nothing to race and nothing to de-duplicate.
  • Cross-event derivations go in the pass. Acquisition source needs the visitor’s flagged event; session finalisation needs the session closed. Those require context the single beacon does not carry.

Putting the expansion in the pass instead breaks three things at once. The pass acquires a second job — synthesise as well as enrich — and must then be idempotent about creation across every rebuild, which is a much harder property than idempotent enrichment. Two passes over one partition, or a pass racing a rebuild, can double-raise. And realtime reads raw, so first_visit and session_start would be invisible live despite being exactly the events people report on.

It also makes the expansion atomic. All the rows one beacon becomes are written in a single handler, so they can be written in a single transaction. A page_view that landed without its session_start, or a first_visit without the page view it was raised from, is not something a later pass can repair — the flag was on the beacon that half-wrote, and re-reading raw would see the same partial state and reproduce it. The guarantee has to be made where the rows are created.

1.x does not do this today: Db::beginTransaction() exists and every fact table is already InnoDB, but the only callers are the schema-update CLI — each create() in the ingest path stands alone. Nothing has depended on it while one beacon meant one row. Once one beacon means three, it is load-bearing.

State the guarantee portably as one atomic write of everything a beacon becomes rather than as “a transaction”. On MySQL that is a transaction. ClickHouse has no general transactions, but a single multi-row INSERT lands as one part atomically, which satisfies the same requirement — so the guarantee ports even though the mechanism does not.

Ingest-time expansion keeps each layer honest: raw is the event stream as the system understands it — every event that happened, expanded but not enriched — and the pass is a pure row-in/row-out enrichment, idempotent by construction because it never creates anything. The taxonomy in §1.4 already names both events as server-materialized; this is where in the pipeline that happens.

OWA has the flags already, with three different lifetimes, and the distinction matters:

  • is_new_visitor_created — the one REQUEST that minted the visitor. GA's _fv. Raises first_visit.
  • is_new_session_start — the one REQUEST that created the session. GA's _ss. Raises session_start.
  • is_new_visitor — SESSION scoped, rides every beacon of the first session. Keeps is_repeat_visitor from flipping mid-session. Not the raiser.
  • is_new_session — PAGE scoped, rides every beacon from the page the session started on. What is_entry_page needs.

Keying acquisition off the flag rather than off a computed earliest event is what bounds the correction problem. If acquisition were derived as MIN(timestamp) per visitor, a late event that turned out to be earlier would invalidate every row that visitor already had, wherever those rows sat — requiring a visitor-to-partition index to even find them. Keyed off the flag, no other event can change the answer: the failure mode is absent then present, never wrong then corrected, and there is no earlier history to invalidate because the flagged event is the beginning.

What remains is only out-of-order arrival — a later event processed before the flagged one. Those rows are in the same or later days, never earlier, so the blast radius is bounded by how late an event can arrive, not by retention.

And that bound is smaller than an earlier draft of this section assumed, because it named the wrong queue. 1.x has two, and they are not the same mechanism:

  • The incoming queue is a file. Tracking events are written to disk and processed later. Every event goes through it when it is enabled, and what it costs the window is simply drain cadence — a configured number, not a thing to measure.
  • The DB queue (owa_queue_item) is a retry queue, and it is the one with unbounded tails. An event reaches it on EVENT_FAILED, and the case that actually puts it there is a session-update event that cannot find its session — SessionHandlers aborts with “no existing session was found”, and SessionCommerceSummaryHandlers with “Session does not exist yet”.

That entire class of failure does not exist in v2. There is no session row to look for: session-scoped values ride every event and the event table is the session-grain table (§1.4). An event that would have been re-queued in 1.x is, in v2, just a row. So the retry queue’s reorder behaviour describes a failure mode v2 deletes, and sizing the window against it would be sizing against the wrong thing — conservatively, but wrong, which is worse than it sounds when the number sets the whole rebuild cadence.

What is left to bound is therefore drain cadence plus client-side lateness: an unload beacon that landed behind a subsequent hit, a retry from the browser, a tab restored from bfcache, a device that was offline. None of that is visible in any server queue, which is the part that still needs a number.

How the denormalise pass actually works

The pass is one function run once per partition: read every raw row in partition P, write the same rows enriched into a staging table, swap staging into P. It creates nothing, deletes nothing and updates nothing in place, so rows in equals rows out is an invariant, not an aspiration — and a cheap defect detector, since any count mismatch is a bug by construction.

What it has to materialise does not split cleanly by scope. It splits by whether the value is an observation, a mechanical resolution, or a model — the same three-way cut §1.14 already makes for the wire, applied now to the pipeline. Scope decides how far the pass has to reach; that cut decides whether it reaches at all.

That also narrows the realtime claim made above, and it should be narrowed. OWA’s raw layer does hold more than GA’s — the referring URL and the campaign tags are there on every event where GA carries only per-event collected values — so realtime can report a referring host. It cannot report a resolved source, medium or channel, because those do not exist until the pass runs. Richer than GA’s realtime, but not unboundedly so, and along a line that follows from the architecture rather than from a policy.

GA is built this way, and its BigQuery export says so explicitly. The export carries three separate traffic-source records per event row, which is the same three-way cut arrived at above:

  • collected_traffic_source.* — manual_source, manual_medium, manual_campaign_*, gclid, dclid, srsltid. The tags as collected with the event. Evidence, not reading. Confirms what the beacon capture already showed: GA ships raw tags and never a parsed source or medium.
  • session_traffic_source_last_click.* — session scope, and its name states the model. Nested per channel (manual_campaign, google_ads_campaign, cross_channel_campaign, sa360, dv360, cm360). Derived, not collected.
  • traffic_source.name / .medium / .source — user scope, documented as “the traffic source that first acquired the user” and explicitly “do not change if the user interacts with subsequent campaigns”. Write-once acquisition, materialised onto every event row.

And the line in that documentation that settles the architecture: “This record is not populated in intraday tables.” GA’s intraday table is its raw layer and its daily table is its processed one, and user acquisition exists only in the second. That is the raw/denormalised split observed from outside GA, with the same value in the same place for the same reason — it cannot be known from the event alone, so it cannot be in the layer that is written one event at a time. geo and device, by contrast, are on every exported row including intraday, which is the ingest-time mechanical resolution above.

Whether GA keeps a user-acquisition table internally is not observable from outside. The shape is not in question: a write-once, user-scoped value that originates in one event which may be years old, absent from the streaming layer, present on every row of the processed one. Something has to hold it between those two facts.

A partition is not self-contained. “The partition is the unit of work” describes the write side exactly, and the read side not at all: a row written today belongs to a visitor whose first_visit may be two years back, and to a session that may have started yesterday. Two things follow,

1. Visitor acquisition needs a derived visitor table, and the reason is retention, not lookup cost. The tempting answer is that the pass needs no table because it can join raw to raw — find the visitor’s first_visit row and read the arrival values off it. That works right up until raw is pruned. §1.14 banks on pruning raw to recover the storage doubling three layers cost; the moment the horizon passes a visitor’s first visit, their acquisition is not expensive to recover, it is gone, and every subsequent event they generate is permanently unattributable. Retaining raw forever to avoid that gives back the one mitigation the third layer had. A visitor-cardinality row survives the prune because it is not event-cardinality.

A cost argument points the same way but is weaker than it first looks, and the difference is worth recording because it nearly went in as the headline. MySQL has no global secondary index on a partitioned table — every index is local — so an unqualified seek by visitor_id touches every partition. But visitor_fsts rides on every event (§1.10 column 9), so the partition holding the first_visit row is computable from the row doing the asking, and the seek is qualified rather than unqualified. Whether the optimiser actually prunes on a per-row join key, rather than only on a constant, is a measurement nobody here has taken. So the lookup is probably affordable, and retention is the decisive argument.

So: one row per visitor, written when the first_visit event is seen, holding the arrival values. Maintained by the pass, not by ingest — the property that mattered for ITP and for keeping append pure is that the write path does no lookups, and that is untouched. Reports never join it either; it is an input to the build, and its values reach queries materialised onto event rows like everything else. It is neither owa_visitor reborn (no per-request write, no per-request read) nor a star-schema dimension (no query-time join, no FK on the fact row, so no repeat of the inner-join-drops-the-row failure §1.12 exists to prevent). Calling it a table is accurate; calling the pass stateless would not be.

The test this passes is the one that deleted the session table. That draft kept a session-grain derived table and lost it because session-scoped values are stamped on every event, so the event table already was the session-grain table. Acquisition is the case where that is not true: it is user-scoped, it originates in one event that may be years old, and no later beacon carries it. Same test, opposite answer — which is the reason to keep exactly this one table and not a second.

And the table wants a TTL, because a repeat visitor is a bounded concept everywhere else. The instinct is that acquisition is write-once and therefore kept forever, which would make this the one table in v2 that grows without limit. Nobody in the field does that, and there are two separate expiries to keep apart — the client-side one, which is the familiar argument, and a server-side one on the visitor record, which is the relevant one here.

Two things fall out. The shape is a sliding inactivity window, not a fixed lifetime — GA resets on activity, Adobe counts from last seen — and the magnitude converges on roughly 12 to 14 months from two vendors who did not copy each other. That Chrome’s 400-day cap lands in the same place is probably not a coincidence: there is little point retaining a server-side profile past the longest cookie that can reach it.

So: expire a visitor row after N months of inactivity, default 13, and the table is bounded by active visitors rather than by all visitors ever. On the Safari share of traffic the cookie is gone in 7 days and the visitor is re-minted as new long before any server window applies, so the TTL is generous against reality rather than binding on it.

Expiring the row does not rewrite history, which is what makes it cheap. Events already denormalised keep the acquisition values stamped on them; only the ability to attribute future events for that visitor is lost, and a visitor returning after thirteen months of silence is a new acquisition by any reasonable reading. GA draws the same line explicitly — its retention setting “only affects explorations and funnel reports” and “does not affect standard aggregated reports”, which is exactly the distinction between the per-visitor record and the rows it has already stamped.

One wrinkle it creates in the write rule above. A sliding window needs last_seen, and the pass writing last_seen contradicts “insert-if-absent, never update”. The resolution is that the rule belongs to the acquisition columns, not to the row: those are write-once, while last_seen is a maintenance column the pass advances as GREATEST(last_seen, <partition max>) — monotonic, so a rerun of the same partition is a no-op and idempotency survives intact. Worth stating plainly, because “never update the visitor row” is the kind of rule that gets enforced literally by someone who was not in this conversation.

GA is worth being precise about here, because its fourteen months do not bind the way the number suggests. With “reset user data on new activity” the window slides on every event, so a user who returns at least once inside it never expires — and first-user attribution rides with the identity rather than being stored beside it. Someone acquired via organic search stays organic on the first-user dimensions forever, unchanged by any later campaign, for exactly as long as the identity survives. What ends it is documented as the identity being lost — cookie expiry, a new device, Safari’s caps — not the retention setting.

Two things follow, pulling in opposite directions, and both are worth stating. GA must therefore hold acquisition on a user record and cannot be deriving it from its own retained events, since those live 2 or 14 months while attribution persists indefinitely for an active user. The store described above is real and GA has one. But GA has it because GA supports the case, and our own data says the case barely occurs: with Chrome capping any first-party cookie at 400 days, even GA’s “forever” is about thirteen months in the dominant browser, which is where the TTL landed anyway. The architecture differs; the reachable outcome does not, by much.

A qualification on the 0.172%. Those are not 0.172% of randomly chosen visitors — they are, by construction, the most persistently engaged cohort on the site, the people who come back over years. Dropping acquisition for exactly them is a worse loss than the share implies, and anyone weighing this should weigh it as “the loyal returning segment” rather than as a rounding error. It does not change the recommendation; it changes how confident to be about it.

So the argument that the table is required does not survive. What survives is narrower and is a choice rather than a necessity:

  • It decouples raw retention from attribution reach, and that is now the whole case. Without it, raw retention is the attribution window: raw cannot be pruned sooner than thirteen months without silently losing acquisition, so §1.14’s own mitigation for the storage doubling — “recoverable by pruning raw” — is locked out for that whole period. With it, raw could be pruned at 30 or 90 days while attribution still reaches thirteen months. Whether that is worth a table depends entirely on how aggressively raw wants pruning, which is unmeasured.
  • A site with logins breaks the measurement. §1.5 makes cross-device identity depend on a site-supplied user_id, and a user_id outlives any cookie. peteradamsphoto has no logins, so its 0.172% is a floor for that class of site and says nothing about one where people sign in. Stitching also needs the old events to still exist to be relabelled, so it fails the same way and for the same reason.
  • Under a TTL the table is small enough that cost is not the argument either way. It holds active visitors, not all visitors ever: 6,761 against 445,055 request rows here, about 1.5%. Cheap — but cheap is not the same as needed.

The reasoning that nearly removed this store, and the trade that replaced it, are in §1.15.

Position, after the GA reading above: keep the store. The intermediate recommendation here was to ship without it and retain raw for the attribution window, on the strength of the 0.172%. What changed it is that GA — which supports the long-lived identity properly — has to hold acquisition on a user record, and that the 0.172% is the loyal returning cohort rather than a random slice. Keeping the store also leaves raw retention a free dial instead of pinning it to the attribution window, which is worth more than the table costs. The no-table build stays documented above as the fallback it is: if the store is ever dropped, raw retention becomes the attribution window and the rule in the next paragraph is what keeps the result honest.

One rule holds whichever way this goes. When a visitor’s first_visit is outside whatever window is in force, acquisition must resolve to NULL — never to their earliest retained event. That fallback looks harmless and is not: the answer would change every time the window slid forward, which is precisely the wrong-then-corrected failure that keying acquisition off the flag exists to prevent. Absent is a fact about the data; a drifting value is a defect.

The visitor store, if it is kept: do not partition it on last_seen

Partitioning on last_seen is the obvious move — expiry becomes DROP PARTITION, free and metadata-only, the same idiom raw uses. It does not work, and the reason is a hard MySQL constraint rather than a cost. Every unique key on a partitioned table must contain all partitioning columns, so the key becomes (visitor_id, last_seen_period) and uniqueness on visitor_id alone becomes unenforceable. Insert-if-absent is built on exactly that constraint. Lose it and a visitor can hold two acquisition rows in two partitions, silently, with nothing to say which is right — the write-once guarantee gone at the storage layer while the code still believes it holds.

The cost objections are real too, and would matter even if the constraint did not. last_seen is mutable, and updating a partitioning column makes MySQL physically move the row between partitions; every visitor migrates whenever their last_seen crosses a boundary. And the lookup is by visitor_id with no period in hand, so with only local indexes it dives into every partition — the by-id-across-partitions trap 1.x already documents.

If it is ever partitioned, partition on first-seen, which the id already carries. §1.10 keeps the time prefix in visitor_id, so the first-seen period is a pure function of the id. That fixes both cost problems at once: the column is immutable so no row ever migrates, and every lookup can supply the partition key it derives from the id it is already searching for, pruning to exactly one partition. Uniqueness also survives in substance — a given id can only ever hash to one period, so UNIQUE(visitor_id, first_seen_period) is uniqueness on visitor_id.

But first-seen partitioning buys nothing for expiry, which is the thing that wanted partitioning in the first place. Expiry is by inactivity, and a first-seen partition holds a mix of long-dead and still-active visitors, so it can never be dropped whole — only deleted within.

So: do not partition it at all, and expire with a plain DELETE. This is a visitor-cardinality table under a TTL, which means it holds active visitors: 6,761 on the measured install against 445,055 request rows. A site a hundred times busier is still under a million rows, where a monthly DELETE … WHERE last_seen < cutoff against an index is unremarkable. Partitioning exists to make drops free on tables of hundreds of millions of rows; here it costs the unique constraint or buys nothing, depending which column it picks.

What the visitor store holds, and what it deliberately does not

Two columns of content and one of maintenance. Acquisition — source, medium, campaign, ad, search terms — write-once from the first_visit event. And last_seen, which exists only to drive the TTL. Nothing else.

Session count does not belong here, and the reasoning generalises. nps is a counter the client already maintains and sends on every beacon, so in v2 it is already denormalised onto every event row. “How many sessions has this visitor had” is then MAX(nps) in a group-by, not a lookup — the same argument that removed the session table in §1.4. The rule: a value that rides every event is already on the visitor, and copying it to a visitor row adds a write without adding an answer. Only values that cannot be on the event — because they originate in one event that may be years old — earn a place here.

1.x is the cautionary version of exactly this, and it is worth stating because the mistake looks like tidiness. num_prior_sessions sits on owa_visitor AND on every fact row. Both registered dimensions that read it — “Prior Visits” and “Visits To Purchase” — read the fact-row copy, denormalised. The visitor copy is maintained by VisitorUpdateHandlers, which fires on every base.new_session, loads the visitor, runs a summarize query over owa_session, and writes a column no report can reach. A per-session row update plus an aggregate query, for nothing.

And last_seen being mutable does not put a write on the ingest path. That is the property worth protecting, since it is the one ITP made load-bearing: ingest stays a pure append with no lookups. Three things keep it that way.

  • The pass advances it, not ingest. One set-based UPDATE over the visitors seen in the partition being rebuilt, alongside the acquisition harvest that already happens there.
  • It is stored as a period, not a timestamp. The TTL is measured in months, so month precision is all it needs — which makes the value change at most once per visitor per month rather than once per session, and makes the common case a write that changes nothing.
  • GREATEST(last_seen, <partition max>) is monotonic, so rebuilding a partition twice is a no-op and the column cannot go backwards when partitions are rebuilt out of order.

So the store is written once per visitor for content, and touched in bulk at most monthly for maintenance. If a future column wants a per-session write, that is the signal it belongs on the event rather than here.

One write-volume note, since last_seen is the only mutable column. It does not need per-pass precision — the TTL is measured in months, so storing the period rather than the timestamp means the update fires at most once per visitor per month instead of once per visitor per partition rebuild. Still GREATEST, still monotonic, still idempotent on a rerun, but the common case becomes a no-op write that changes nothing.

Its write rule is insert-if-absent, never update, which is what makes a rerun safe: a visitor has exactly one first_visit in their life, so a second write of the same row can only be a reprocess of the same event. That is the same “absent then present, never wrong then corrected” property the flag keying buys, now expressed as a storage rule. A full rebuild of the table from raw must break ties deterministically — order by (timestamp, event_id), not timestamp alone — or two rebuilds can disagree.

2. Session finalisation puts a floor under the late-arrival window that queue reorder latency does not. A session running across midnight has rows in two partitions and cannot be finalised while building the first. The window already has to exceed how far the queue can reorder; it also has to exceed the longest session that can straddle a partition boundary, or the earlier day is sealed holding a session that was never closed. OWA’s session_length is 1800s, but that is the idle timeout between hits, not a cap on total duration — a session with a hit every 25 minutes runs indefinitely. So either the window carries an explicit session cap, or terminal values stay NULL and the row is corrected on the next rebuild, which the window makes free anyway. The second is the honest answer, and it costs nothing: §1.12 already says “(not set)” is presentation rather than storage, so “not final yet” and “no value” are the same NULL and the reporting layer already has to handle it.

The order within one run is forced, and getting it backwards is silent:

  1. Harvest. Insert-if-absent into the visitor table from this partition’s first_visit rows. Must precede step 3: a visitor whose first session and second session both fall in this partition needs their own acquisition row to already exist, and nothing about the second session’s rows carries it.
  2. Close. Compute terminal session values for sessions whose last event is in this partition and whose close is certain.
  3. Build. INSERT INTO staging SELECT … joining raw against the visitor table and the closed-session set.
  4. Swap. EXCHANGE PARTITION.
  5. Roll up. Replace that day’s rollup rows from the new partition.

Idempotency comes from the swap, not from clever SQL. Staging is built whole and is invisible until the exchange, so a run that dies in step 3 leaves the live table exactly as it was and the next run simply rebuilds. This is a stronger property than “the statements are rerunnable”, and it is the reason to build into staging rather than to write the target directly even where a direct write would be possible. The one piece of state that outlives a failed run is the visitor table, which is why its write rule has to be insert-if-absent independently.

Step 5 is not optional and is easy to forget. The rollup is downstream of the denormalised table, so rebuilding a partition invalidates that day’s aggregates. Replacing them has to be part of the same job rather than a separately scheduled one, or a rebuilt day is served from stale aggregates until whenever the rollup next runs — a discrepancy that surfaces as “the report and the detail disagree” and is miserable to diagnose.

The whole thing runs in the database. Every step is INSERT … SELECT against tables in one schema; no step needs a row in PHP. That matters more than it sounds: a pass that fetches rows, enriches in PHP and writes them back is bounded by round trips and by memory_limit, and on this class of box that is the difference between a job that runs and a job that OOMs. It also keeps the pass expressible on a columnar engine, where the equivalent is likewise a single INSERT SELECT. Window functions make step 2 straightforward and need MySQL 8.0 — the repo declares no minimum server version anywhere, so v2 should state one rather than discover it on someone’s 5.7.

Scheduling needs nothing new. The job scheduler shipped in #997 already has per-job locking (getJobLock / releaseJobLock, with --force-release for a lock left by a dead process), which is exactly the “two runs must not build the same partition” guard. Registering is one line beside rotate-partitions in Base\Module::registerJobs(). Two cautions from how that scheduler actually behaves: the lock is keyed on the job name, so one name serialises every partition the job touches — fine, and probably wanted, but it means the window cannot be rebuilt in parallel without per-partition names. And ScheduleRunCli::MAX_RUNTIME (240s) is checked before starting a job and never mid-job, so a long pass is not interrupted; it just delays whatever else was due to that tick.

The cost profile is why the partition tier at the front has to be fine. Rebuilding today’s partition costs however much of today has happened, so an intraday cadence rewrites a growing table all day — cheap at 08:00, a full day’s rows at 23:59. That is tolerable when a partition is a day and untenable when it is a month, which is the same argument the partition cycle above makes from the other direction. Two cadences fall out: a frequent run on the current partition setting the attributed-freshness tier, and a less frequent run over the rest of the late-arrival window, which is where a late first_visit actually gets picked up.

Sub-hourly is already expressible, and the pass already qualifies to run that way. Core\Cron supports step syntax, so */15 * * * * parses and describes itself as “every 15 minutes”; the crontab line is a one-minute resolution floor rather than the schedule, so anything down to a minute is available. No new mechanism.

The constraint that matters is the one Core\Cron states in its own header: a scheduled job must be CONVERGENT, not incremental. The due test is level-triggered and does not backfill — a job missed for three days runs once at the next tick, not once per missed occurrence — so anything that processes “the next unit of work” loses data across a gap. The pass passes that test by construction: it rebuilds a whole partition from raw and swaps, so one run after an outage leaves exactly the state twenty runs would have. That is the same property the swap-as-commit design already provides, and it is worth naming here because the rule is enforced by convention rather than by code, and a pass written to enrich only what it had not enriched yet would violate it while looking correct.

Two behaviours of the shipped scheduler are worth knowing before picking an interval. The per-job lock means a run that outlasts its interval does not pile up — the next tick finds the lock held, logs that the job is already running, and skips; the job simply runs less often than asked, which is the right failure. And ScheduleRunCli::MAX_RUNTIME (240s) is a budget checked before a job starts and never mid-job, so a long pass is never interrupted part-way; it only delays whatever else was due on that tick.

The interval and the partition granularity are one decision, not two. Each run rebuilds however much of the current partition exists, so at */15 that is 96 rebuilds a day, and on a monthly partition the last of them rewrites a month. On a daily partition it rewrites at most a day, and the cost is flat across the month instead of climbing through it. A sub-hourly cadence is affordable on daily partitions and not really affordable on anything coarser. So v2 needs a daily entry in PARTITION_CUTS, which had only monthly, half-month and quarter-month. Added in PR #1113, kept in 1.x because it is additive: nothing adopts it on its own — partition-init still defaults to monthly, partition-rotate still infers from the table, and partition-reorganize requires the granularity to be named.

It was one array entry plus one latent defect, which is the part worth remembering. daily is the first granularity whose cuts a short month cannot carry, and inferPartitionGranularity() compared a table's boundaries against the raw constant rather than cutsForMonth()'s clamped result — so a daily table inferred as null in every month but the 31-day ones, and a null there makes rotation fall back to monthly, silently changing a table's granularity on a scheduled run. The clamp had existed all along and had never once applied, because every other granularity cuts at or below the 22nd.

What is still unsettled here: whether the rebuild set is the whole window every time (simple, no change tracking, and the only thing that is provably correct given a late flagged event) or something narrower; and that partitioning on yyyymmdd alone means one partition holds every site, so a multi-site install pays one big site’s rebuild cost in every site’s freshness. Subpartitioning by site is the obvious answer and multiplies the partition count by the site count, straight into the budget §1.14 is already spending. Left to §4.5.

The tracker carries the landing URL, and the server parses it Decided

Today the tracker parses the landing URL against campaignKeys and sends six tagged_* parameters on every beacon of the session. The parse moves to the server; what rides the wire becomes one field, the landing URL itself.

This is not what GA does, and the difference is deliberate rather than an oversight. Re-measured by capture across four session shapes, nine page views, with the complete parameter set dumped rather than a filtered subset:

  • A campaign session's first hit carries the tags in dl. Hit 2 and hit 3 carry no campaign parameter of any name — the two hits differ in exactly _fv, _nsi, _ss and _eu, and nothing else.
  • Neither cookie holds attribution. _ga is GA1.1.<cid>.<first-seen>; _ga_<ID> is GS2.1.s<sid>$o<count>$g<engaged>$t<last hit>$j<n>$l0$h0.
  • A second page tagged with a different campaign sends the NEW tags as collected. GA neither suppresses them nor resends the originals — which is collected_traffic_source per event against session_traffic_source_last_click derived.

And it stays a column on the denormalised row, not just an input the pass consumes. Two reasons, and the second is the one that matters.

  • §1.4 already requires it. “Sessions by landing page” at 215 ms against 3.1 s as a first-event join is the measurement that removed the session table, and the scope table above already lists landing page as session-scoped and stamped on every row. Keeping the URL rather than a stripped path costs one column.
  • It decouples re-derivability from raw retention. If the denormalised rows keep only the resolved source, medium and campaign, then the moment raw is pruned those answers are final — there is no evidence left to re-read. Keeping the landing URL on the row means the evidence outlives raw, and a parser fix or an ns change can be reapplied to years of history. That is exactly the argument that justified the visitor table, one layer down.

The honest cost is realtime, and it is narrower than it first looks. A raw row from later in the session will not carry the landing URL, so a live query cannot resolve session campaign for it. It still carries session_referer, so referring host, and referral against organic-search, still work live. Narrower than losing session source altogether, and still ahead of GA, whose Realtime API has neither. The claim above that OWA's realtime is richer than GA's survives; it is just richer by referer rather than by campaign.

How the partition cycle actually runs

If a rebuild replaces a whole partition, the partition scheme decides the unit of work — so the rebuild window wants fine partitions and everything older wants coarse ones. That is a two-stage lead, three operations, and only one of them costs anything.

whenoperationcost
continuously, far aheadREORGANIZE pmax INTO (monthly…, pmax)metadata — pmax is empty
shortly before a month goes currentREORGANIZE p2026MM INTO (<fine partitions>)metadata — that month is still empty too
after the month closes and its window expiresREORGANIZE <fine> INTO p2026MMrewrites the month, once

The fine partitions are never carved from pmax. They are carved from an already-created, still-empty monthly partition shortly before it goes current, so the daily lead only has to cover the reorder window plus margin — days or weeks. The long lead stays monthly and stays far out, exactly as 1.x runs it today (demo's reaches 13 months).

That split is forced, not stylistic: the lead is filled at the table's own granularity. 1.x keeps PARTITION_MONTHS_AHEAD (12) whole future months ahead, and extendPartitions() fills to that boundary at whatever granularity the table already uses — the number of months is fixed, the number of partitions is not. A table taken wholly to quarter-month therefore carries ~48 partitions of lead rather than 12, against a PARTITION_COUNT_LIMIT of 400 whose own docblock notes that quarter-month over a decade reaches 480. Making the whole table fine-grained to get a fine-grained rebuild window would spend the partition budget on empty future months. The two-stage lead spends it only where the rebuild actually happens.

Do not confuse that lead with the detail window. Three separate month-counts govern partitioning in 1.x and only one of them is about granularity: PARTITION_CUTS is the granularity itself and is not a month count at all; PARTITION_DETAIL_MONTHS (36, and already cited below) is how long a period keeps that granularity before compaction may merge it into year blocks; PARTITION_MONTHS_AHEAD (12) is the lead. Granularity is never a stored setting — it is inferred per table from the existing layout, defaults to monthly, and only partition-reorganize changes it, which is the seam a two-stage scheme has to extend.

pmax must never receive a row. That is the load-bearing invariant, and everything else here is tuning. 1.x already depends on it without saying so: the cost of extending the lead is “proportional to what is sitting in the catch-all” — measured at 1.52s to create 31 partitions when it is empty. Let rows land there and the next carve stops being metadata and becomes a rewrite, while rows that belong in a dated partition sit in the catch-all instead.

One job, and merge before carve. These are separate ALTER statements — MySQL permits one partition operation per statement — but they belong in one run of one job under one lock, which is how PartitionRotateCli already works (extend, then a REORGANIZE per merge, then drops). Order matters for the high-water mark, because merge and carve move the count in opposite directions: merging first frees roughly a month of partitions before the carve consumes roughly a month, so a run peaks near its starting count rather than a month above it. It also fails better — a run that dies between the two leaves the table below where it started, never over budget.

The rebuild granularity is an open trade, and there is a middle rung already built. PARTITION_CUTS offers monthly, half-month and quarter-month; there is no daily, though adding one is a single entry and cutsForMonth() already clamps cuts past a short month's end, so February and leap years fall out correctly. Daily gives the smallest rebuild and the most partitions — two months of them transiently, since the next month must be carved before the current one's window expires. Quarter-month gives a week-sized rebuild, about four partitions a month, and no new granularity. Which is right depends on rebuild cost, and that is unmeasured.

The rotation job becomes a dependency of ingest correctness, not housekeeping. Today a stalled rotation is untidy. Under this scheme the lead erodes, rows reach pmax, and the invariant breaks — so it wants an alarm rather than a log line. 1.x has had two scheduler-adjacent stalls already.

Additive work in 1.x

What ships now, reduces risk, and is inherited by v2 rather than redone.

2.1Why this matters more than it looks

Every item here is proved against real traffic before v2 depends on it, and each one narrows what the rewrite has to get right on the first attempt. The evidence that this is the correct posture is recent: converting one id width across two installations took five pull requests, a storage upgrade and most of a day, with tracking dropped in the window where the flag and the data disagreed. A total schema change is not that problem scaled up — it is a different and much worse problem, and the way to survive it is to arrive with most of the pieces already running.

One decision unlocked much of this list. Because the server fans a single tracker's events out to both pipelines, the wire format no longer has to satisfy v1 — compatibility is a server-side translation. 2.5Order of operations Decided

Sequenced on three rules: bugs whose cost accrues daily go first, because every day of delay is data you cannot recover; foundations before the things built on them; and the expensive irreversible work last, when the most is known.

Standing precondition — coverage before development

No phase item starts until the behavior it touches is pinned by tests, in the form the work demands. Bug fixes begin with a failing test demonstrating the defect — the test is the bug report. Behavior-preserving work (PDO, cookie consolidation, Util.js, CORS) begins with a characterization suite of current behavior — cookie bytes in both formats, emitted beacons per event type, generated SQL text, endpoint headers — because “same behavior, different plumbing” has no other definition of broke something. Expect the pins to be most of the job; the swap under them is the small half. Every pin is mutation-checked at creation (break the behavior, watch it fail, restore) — a vacuous pin certifies the refactor didn't break what it broke.

Part Three

Migration

Coexistence, not conversion. No 1.x data is ever converted.

3.1One tracker, two pipelines Decided

A single tracker describes each event richly enough that both pipelines can consume it. The server fans one received event out to both — v1's handlers write the star, v2's write the event table — and at parity the fan-out to v1 is switched off. Nothing about the page changes on that day.

Two trackers would have split each site's data by which snippet happened to be deployed, so v1's history would step or stop the moment a site upgraded — destroying the value of the thing being kept.

Amended: one session model, adopted by both pipelines Decided

A session id is decided in the browser, from a cookie, and v1 and v2 disagree about when a session begins: v2 creates sessions only on page-view events, withholds the store until sendAccepted, and embeds creation time in the id (§1.4). One cookie cannot hold two models, so fanning one stream out unchanged would give v2 rows carrying v1's session boundaries — the v2 session model inherited rather than implemented.

An intermediate draft concluded from this that the page must carry two tracker configurations, one per profile. That is not the decision. Two configurations would mean two session state machines in the tracker — the riskiest surface in the project — and would break the property this section exists to provide, because two streams are not the same events and raw counts would only match within a tolerance.

Instead the tracker gets one session model, v2's, and v1 adopts it. One tracker, one cookie, one beacon, one stream; the server writes v1's star from it as before and v2's event table when enabled. The fan-out described above therefore stands exactly as written, and the two pipelines keep consuming identical events — which is what lets the integrity check of §3.3 stay a diff rather than a tolerance.

The cost is one discontinuity in v1's session-derived numbers, accepted deliberately — but not where an earlier draft put it. Three rules differ, and they are not of equal size:

That last is GA's behaviour and the reason the tracker must notice a mid-session tag change and restart cleanly (EVENTS.html §7). Its size depends entirely on traffic mix — near zero for organic-only sites, material for campaign-heavy ones — so there is no single number to quote.

And v1's history cannot size it

owa_request does carry per-request medium, source_id and campaign_id, so the question looks answerable. It is not: setTrafficAttribution() stamps the decided, session-sticky result rather than the observation that produced it, so a mid-session tag change is collapsed before it is stored. A measurement on this install returns 0.246%, which is an artefact of that collapsing rather than a rate.

This is the same limitation §3.3 records for validating the attribution model — existing history is not a usable touchpoint log.

Not treated as a blocker. The expectation is that the effect is small: it requires a visitor to re-enter through a second tagged link inside the timeout, which is uncommon outside heavy paid-campaign traffic. If a number is wanted later, touchpoint data supplies it; nothing waits on it.

Touchpoint recording earns its place on data quality, not on this. Attribution is decided in the browser today — setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the verdict rather than the observation that produced it. So the server stores a conclusion it cannot check, and four things follow:

  • A model bug is permanent. Fix the attribution logic and every row already written keeps the old verdict — there is nothing to recompute from.
  • Attribution dies with the cookie. Clearing owa_c destroys the stack, and the visitor's history is gone rather than re-derivable.
  • The 60-day original window is measured on the client's clock, which is unverifiable and, on a skewed device, wrong.
  • No post-hoc enrichment. This research measured the star's one real advantage as rewriting a dimension without touching facts (589×); attribution is precisely the dimension worth rewriting, and today it is the one that cannot be.

Recording the touchpoints makes attribution derived rather than reported: recomputable, correctable, and independent of whether a cookie survived. That is the reason to do it early, and it stands whether or not the session step is ever quantified.

Event-level history — page views, clicks, geo, referrers — is untouched by all of this, and nothing already stored is rewritten. The change still wants a UI annotation at its date, per §1.10's rule for definition changes.

3.2Early cutover, per feature Decided

Fan-out is per event type, not global. A feature skips the dual-write period entirely when both hold:

  1. v1 has no history worth preserving for it — nothing to strand, no oracle to compare against
  2. keeping it dual-written would mean renovating v1 storage to carry data only v2 can use

Domstreams qualify on both. Everything v2 changes about them is storage-shaped: a recording becomes an attachment rather than a parallel fact row, the payload moves outside the row, the encoding becomes delta tuples plus gzip (~30× measured). Dual-writing leaves only bad options — either the new capture has nowhere to land, or owa_domstream is renovated to accept a format v1 will never report on. Heatmaps follow, being built on the same capture.

3.3The parity harness — two instruments, not one Decided

Both pipelines consume identical events, so v1 can serve as an oracle — but only below the session boundary, and an earlier draft of this section did not say so. The correction matters enough to state first, because it changes what this harness is for.

v1 is not an oracle for anything session-scoped

This section already made the argument for attribution — parity there “would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right.” That reasoning is not special to attribution. v2 keeps the event and changes the session, so it applies to everything the session model touches.

And the divergence propagates. Per-site session stores give site B its own session where v1 shared one; sessions are created only by page-view events; the store is withheld until sendAccepted. So visits is a different number by design — and visits is the denominator of 6 of the 8 formulas in the tree. Bounce rate, pages/visit, actions/visit and revenue/visit all diverge without anything about their own definitions changing. Separately, 18 of 34 metric classes bind to base.session directly.

Which means the “intended differences” list below is not five enumerable items, it is most of the surface — and the warning attached to it turns on itself. An exclusion list that large is not an exclusion list; it is the majority case, and a real regression hides comfortably inside it.

Attribution has a warm-up — it cannot be cut over cold

Today attribution is decided in the browser. setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the decided result — source_id, medium, campaign_id — not the observation that produced it.

Two consequences for the sequence. Existing history is not a usable touchpoint log, so the server-side model cannot be validated by replaying it — parity against v1 attribution would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right. And original is a sliding 60-day window, not first-touch-ever, so a server-side implementation produces nothing trustworthy until it has observed 60 days of traffic.

Therefore recording raw touchpoints is itself an additive 1.x item, and an early one — earlier than the switch-over it serves. Start it and the warm-up runs in the background while other phases proceed; start it at cutover and it becomes a 60-day hold on the one part of v2 that cannot be hurried.

3.4Profiles carry the version Proposed

Everything above resolves the version at query time, and every automatic signal for doing so fails. A date boundary cannot work: §3.2 makes cutover per-feature so there is no single instant, dual-write means both stores hold the same period, the switch-off is an administrator's action rather than a release date, and the queue is asynchronous so an event accepted before a switch can land after it. Coverage watermarks fail for the same reason — during overlap both stores answer, and the data cannot say which is authoritative. An install-wide setting fails differently: since no data is migrated, v1 holds the history permanently (§3.6 keeps v1 reporting precisely for that), so a global flip would blank every historical report.

The proposal is to stop resolving it at query time and carry it in the data model instead. Decouple the tracked website from the profile that measures it: one website may have several profiles, and a profile declares its version. The whole experience fans out from the profile — a v2 profile shows v2 navigation, v2 reports, and queries the v2 REST endpoint. This is the path GA took to GA4, and it dissolves rather than solves the open questions:

What it requires — and it is smaller than it sounds Measured

site_id is md5($domain) (Site::generateSiteId(), and inline at SiteManager.php:44), so two profiles for one domain are impossible by construction. Only three call sites derive it, and just one re-derives at runtime — ServiceUser.php:283, in the permission path, which is the edge needing care and tests.

Two things are already in place. site_family exists as a column on owa_site and is written but never read anywhere — a dormant grouping slot, so “tracked website” can be defined freshly rather than migrated. And the per-site session store (owa_s_<siteId>) already gives two profiles on one domain independent session cookies, which is both correct and exactly GA's _ga_<property>.

Do not rewrite existing site_id values

Every site_id in the wild is md5(domain) and every fact row references it. The change is to stop deriving new ones and treat the column as opaque — existing identities keep their values and existing data is untouched. Decoupling identity from derivation does not require reissuing the identities already handed out.

No second tracking tag, and no second tracker. An earlier draft of this section argued for one; that contradicted §3.1, which is Decided and whose reasoning still holds — two trackers split a site's data by which snippet happened to be deployed, so v1's history steps or stops the moment a site upgrades, destroying the thing v1 is being kept for. The fidelity argument was also backwards: the tracker is extended in Phase 3, so it already emits v2-rich events and the server degrades them for v1 — not v1-poor events upgraded for v2. There is no fidelity gap to protect against.

So the profile model requires no client change whatsoever: one tag, one event, and the server writes each received event into every profile configured for that website. The site → profiles mapping is server-side, so the page never learns that profiles exist, and §3.1's promise holds — nothing about the page changes on cutover day.

Independent of v2, md5(domain) already prevents tracking two configurations of one domain, renaming a domain without orphaning its data, and expressing one property across several domains. The decoupling is additive 1.x work with standalone value.

What the profile does not do is spare ResultSetManager. It settles where the version comes from, not how the manager acts on it, so the entity-pool change of §1.11 survives intact and is still the work: resolve the version from the profile behind siteId, filter candidate entities to that version before arsort($niceness), and error when none resolves. setSiteId() today only records a query param and a constraint rather than loading the site, so there is a little plumbing from siteId to a version — but nothing new threads through the REST API or the report configs, which is precisely what the profile model buys: an unambiguous input already present in every query.

Nothing feeds the manager a “v2 list” Measured

A fair question is what supplies ResultSetManager with the v2 metric and dimension sets. The answer is that no new channel is needed. getMetricEntities() asks the service singleton for every registered implementation of a requested name, instantiates each, and keys it by its own entity:

$classes = $s->getMetricClasses($metric_name);   // every implementation
foreach ($classes as $map) {
    $m = metricFactory($map['class'], $map['params']);
    $this->metricObjectsByEntityMap[ $m->getEntityName() ][ $metric_name ] = $m;
}

So a v2 registration appears alongside the v1 one automatically. Dimensions behave identically — registerDimension() loops $entity_names into one entry per entity, and lookup is denormalizedDimensions[$name][$entity]. The v2 set is just more registrations carrying the v2 entity, or more config entries once §1.11 lands. This is the same reason report configs need no version field.

Which relocates the filter. Because implementations are built before anything is selected, the version filter belongs in getMetricEntities() — skip a class whose entity is the wrong version, so wrong-version objects are never constructed — rather than at the niceness sort, where they already exist. And the recursion into child metrics means filtering children constrains their calculated parents for free.

Scope the catalog by entity, not by version Decided

Refinement of the section below. Partitioning by version works but spreads a version concept through every accessor, and concepts like that leak until they are everywhere. Keying off the entity achieves the same isolation using something already present in every registration and already understood across the codebase: a profile determines a candidate entity set, the accessors scope to it, and the word “version” survives only in the profile record and the migration machinery — which is the one place generational schema changes are actually relevant.

It is still a single choke point rather than scattered filtering: every consumer goes through the accessor, so there is one place to be right instead of ten. And it improves the API independently of v2 — getAllMetrics() today returns everything regardless of whether it is queryable in the current context, so an entity-scoped picker is more correct even with one generation.

Superseded: partition by version Measured

The paragraphs above proposed registering the v2 set into the existing registry and discriminating downstream — a filter in getMetricEntities(). That is wrong, and the reason is enumeration rather than resolution. getAllMetrics() and getAllDimensions() return the flat, name-keyed map, and they are consumed in ten places:

So partition at the aggregation points instead. There are exactly two, and they are the only places module registries merge into the service:

The distinction is scoping the registry once versus remembering to discriminate at ten consumers. Open: the service is a boot-time singleton, built before a query knows its profile, so either every accessor takes a version or the version becomes request-scoped ambient state. The explicit parameter is safer — ten call sites is tractable, and it keeps the version visible at each consumer rather than hidden in ambient state, which is the same silent-wrong-answer failure in a different costume.

}

Measured of 103 registrations: 58 denormalized (safe), 41 normalized against a single entity (the overwrite is a no-op), and 3 normalized against all seven $fact_table_entities — month, userName, priorVisitCount.

This blocks v2 for all 44 normalized dimensions. v1 registers pageTitle against its dimension table, v2 registers pageTitle against the event table, and the second write replaces the first — the v1 definition is gone from the registry before any entity filter could run. No downstream selection can recover it, and renaming is not an option.

Fix: key $this->dimensions by entity, matching denormalizedDimensions, which already has the right shape. getDimension() has exactly one caller (ResultSetManager:970), so the change is that call site plus the registration loop. This is a prerequisite in 1.x: the registry must be able to hold two definitions under one name before a second set can exist at all.

Unverified, worth a trace: the 3 normalized multi-entity registrations keep only the last of seven entities, and $dim['entity'] then drives the JOIN (entityFactory(), getForeignKeyColumn(), $db->join()). date is registered against the same list with denormalized = true while month beside it is not, which looks like an oversight rather than a distinction. Not claimed as a live defect until traced.

Do not add the v2 entity to $fact_table_entities

Dimensions are registered against a shared array: registerDimension('date', $fact_table_entities, 'yyyymmdd', …). Appending the v2 entity to that one variable would make every dimension claim to work on v2 while still naming v1's columns — a one-line change producing broadly wrong SQL, and the obvious-looking way to “add v2 support”. v2 needs its own registrations with its own columns, exactly as metrics do.

Open: the vocabulary (site / profile / property / site_family) wants settling before anything is built, since it will surface in the UI, the API and the schema at once.

Domain aliases stay v1-only, and narrow Decided

A Property will hold the domains of the website it describes, and the temptation is to make that list do two further jobs it should not do.

It does not widen CORS. matchAllowedOrigin() today matches a request's Origin against each site's domain and nothing else — aliases are not consulted. Feeding alternates into that allowlist would grant cross-origin API access that installs do not have today, as a side effect of moving a setting into a column. The allowlist stays exactly as wide as it is.

And the alias itself narrows to a variant of the same domain. Its documented purpose is collapsing www.mydomain.com and mydomain.com; nothing needs it to map one website onto an unrelated one, and a general redirect map is a much larger thing to reason about than the help text implies. Restricting it to same-domain variants keeps the real use case and removes the rest.

Both jobs then disappear together with v1: canonicalisation is v1-only machinery (§1.9), and CORS never depended on aliases in the first place. So the fragile parts of the current implementation — a naive substring replace, and a strpos( $url, $da ) that misses a match at position zero — want not carrying forward rather than fixing.

3.5Organization › Property › Observation Profile Decided

§3.4 established that a profile carries the version, which is what lets two generations coexist without a query ever inferring one. This is the structure that holds profiles, and it is larger than that section assumed: not “sites gain a grouping” but a three-tier hierarchy, touching users and permissions as well as measurement.

TierIsCarriesGA equivalent
Organizationwho is doing the measuringuser accounts and their rolesAccount
Propertythe website or appname, domain, description — what the thing isProperty
Observation Profilea way of measuring itthe tracker id, the schema generation, settings and filters — how it is measuredData Stream

Today's owa_site fuses the middle and bottom tiers: it holds domain and name (Property) beside site_id and settings (Profile). Splitting them is what the whole thing turns on, and site_family — the column that is written but never read — is superseded rather than repurposed, since property_id does that job properly.

Timezone belongs to the Profile, not the Property. It is applied once at write into yyyymmdd and is not retroactive (§1.10), so it describes the measurement rather than the website. Two profiles on one property may legitimately record in different zones.

Permissions are the consequential part

owa_user carries a global role today, with per-site rows in owa_site_user narrowing access. Moving accounts under an Organization makes that role org-scoped, and every existing grant — which points at a site, i.e. a future Profile — has to be repointed.

Grant at the Property, not the Profile. Someone who may see a website should see its measurements; a per-profile grant would mostly express “you may read the v1 data but not the v2 data”, which nobody wants and which would silently split a user's view at cutover. It also makes the migration mechanical.

One organization per user to begin with. Multi-org membership is a real feature with a real question attached (which org am I acting in?), and nothing here needs it. Note the existing trap while touching this: the allowed-users form replaces the whole grant set, so a partial submission revokes everyone omitted.

Migration for existing installs

  1. One Organization; every existing user joins it, keeping its role.
  2. One Property per existing site, taking its domain, name and description.
  3. One Observation Profile per existing site, keeping its site_id unchanged — the rule from the identity work, and one every fact row depends on.
  4. Grants move from site to Property.

Nothing a tracker sends changes, and no fact row is touched.

The v2 pipeline is switched on per Property Decided

Each Observation Profile has its own tracker id, but the page carries one — §3.1 settles that the tracker has a single session model and the server fans one stream to both pipelines. So a v2 profile is not populated by adding a tag.

It is populated by a setting on the Property. Turn it on and incoming events for that property are written to the v2 event table as well as the star; leave it off and nothing changes. That makes v2 collection an opt-in per website, decided by whoever owns it, rather than something an OWA upgrade starts doing.

Note what this separates. The session change ships with the tracker and reaches every install at upgrade — it is not opt-in, and §3.1 records why that is accepted. The v2 pipeline is opt-in and reaches nobody until asked for. Conflating them would mean either a silent schema change or a tracker that carries two session models to keep the switch honest.

3.6Cutover sequence

  1. Ship the additive work in 1.x releases, each standing on its own
  2. v2 creates its tables alongside; the single tracker's events fan out to both pipelines, except for features on the early-cutover list
  3. Run both for an overlap period, comparing the two UIs over the same events — which is what makes it a test rather than an impression
  4. When satisfied, switch off the fan-out to v1 and keep v1 reporting for history
  5. When the history is no longer wanted, a command drops the 20 parallel tables, leaving the shared admin tables untouched

No step is irreversible until the last one, and the last one is the administrator's decision rather than an upgrade's side effect.

Part Four

Supporting decisions

Settled questions that would otherwise resurface mid-build.

4.1Schema versioning Decided

One schema version, one numbered update sequence. An update may touch v1 tables, v2 tables or both. v1 and v2 are not two schemas that coexist; they are one schema containing both shapes — which removes the version pair, and with it any compatibility matrix or cross-sequence ordering question.

This is smaller than it sounds, because the mechanism already works this way: only Base has ever had updates, install() builds tables from entity registration and never replays updates, and the apply loop already sorts numerically, stops at first failure and resumes.

The sharp edge

A dropped v1 is a supported state, so every update written afterwards must tolerate those tables being absent — not just ones that mean to touch them. The apply loop stops at the first failure, so one update assuming owa_session exists blocks every later update for those installs, and isUpdateRequired() then wedges them out of the admin over a table they deliberately removed.

Worth a helper on the update base class rather than a documented convention — the failure lands on the update written eighteen months from now.

Measured A fresh install creates both shapes: 19 empty tables cost 27.0 MB, nearly all per-partition tablespace overhead on 15 partitioned fact tables. Cheap enough to accept, and it keeps a fresh install able to serve a v1 beacon without being migrated forward into v1 first.

4.2Scheduling Decided

The scheduler shipped in 1.11 — one crontab line, jobs dispatched from it, per-job overlap locking, level-triggered so a missed occurrence runs once rather than backfilling. v2 needs no new machinery, only a registration.

The convergence rule it already imposes on registered jobs is the same property the rollup needs, arrived at from the other direction: a watermark rollup would be both non-convergent and not eventually consistent. One defect, two symptoms.

New in v2: the scheduler stops being optional. 1.x runs correctly with no cron entry; v2's rollup does not. That belongs in install verification, not in how the software is shipped.

4.3Packaging Decided

Unchanged. Same tarball, same Release Packager workflow, same wizard. No Composer requirement for end users, no build step at install time, no new runtime dependency. The distribution model is the reason a self-hosted tool gets installed at all, and a rewrite is exactly when one is tempted to modernise it into something needing a toolchain on the target machine. The schema changing is not a reason for the delivery mechanism to change.

4.4Testing Decided

The two harnesses of §3.3 are the primary tests — pipeline integrity generated and exhaustive, model characterization hand-written and small. Neither alone is “the” test, and reporting them as one is the failure mode that section describes. Around it: 77 test files and 509 methods today, of which only 8 files are named for star-schema artefacts — most of the suite tests CLI commands, settings, auth, validation, the queue and the scheduler, and ports unchanged. What genuinely expires is the part testing the star's mechanics.

Three hazards, the first two already known here:

  • Order-dependent tests — CI already runs an isolation sweep executing each file alone. More valuable during a rewrite, not less
  • Vacuous assertions — double-quoted PHP needles containing $this-> interpolate away and pass unconditionally. A rewrite writes many tests quickly, which is the condition that produced these the first time. Worth a lint
  • Silently narrowing coverage — a test deleted because it tested the star, never replaced, leaves no trace. A green suite that is green because it asks less

Claims in this plan that are worth nothing untested: the rollup folds in a late event on the next run; an event beyond the horizon does not, but still lands in the event table; running the rollup twice changes nothing; a throwing v2 handler fails neither the v1 write nor the request; the update sequence runs clean with v1 dropped; and generated realtime SQL carries a closed partition-key range — asserted on the SQL, since a timing assertion on a small fixture would pass either way.

4.5Multi-site

The area needing least work: a single event table handles tenancy naturally, site_id is a column, isolation is a WHERE, and it already leads the composite indexes. Permissions are already per-site.

Two things change. site_id becomes more load-bearing — it leads every composite index and every report's WHERE — so it must be immutable. And site_family is written by site creation and read nowhere; it was built for a UI that never shipped, and should be dropped rather than ported.

Retention stays installation-wide, not per site. A partition of the shared event table holds every site’s rows, so varying retention by site could not be a partition drop — it would need a row-level DELETE sweeping every partition, leaving fragmentation behind and competing with live writes. Uniform retention is a metadata-only partition drop, effectively instant, and already implemented. The single table makes the simpler policy the cheap one.

4.6Open questions Open

Everything unsettled, in one place. Sections that raise a question link here rather than carrying their own list.

QuestionState
Beacon volumePiggyback plus one terminal beacon estimated at ~+27% events; never tested against real traffic patterns.
Mixed-tier reportsWhether one table may carry event-grain and session-grain columns together — one object with two as-of times, which no single freshness marker describes honestly.
Reprocess cadence, and it is bounded by the partition schemeA swap replaces a whole partition, so the partition is the unit of work. 1.x partitions fact tables monthly for partition_detail_months (default 36) and then merges into blocks of up to partition_max_years_per_block (default 5), bounded by the server's open-file budget — each partition is a file. Carried over unchanged, rebuilding “today” would mean rebuilding the whole month: on the 31st every intraday pass rewrites 31 days, and the job's cost grows through the month for no benefit.
So the denormalised table wants a daily tier at the front — daily while a day is still being rebuilt, merged to monthly once it is final, and into year blocks later. That is three tiers and two merge steps rather than one, each merge a REORGANIZE that rewrites rows, but each bounded: one day's worth daily, one month's worth monthly.
Which gives the late-arrival window a concrete meaning rather than a policy: it is the point at which a day's partition stops being rebuilt and is merged. An event landing after that is outside the window by definition. Setting that number sets the reprocess cost, the freshness, and the merge schedule together — it is the one dial worth getting right.
The raw table needs none of this. If raw is pruned at a retention horizon rather than compacted, it only ever needs DROP PARTITION — free on MySQL and on columnar — so it can stay daily throughout and never pay a merge at all. Tiering exists to serve query efficiency, and nothing queries raw except realtime, which wants the recent end.
Late-arrival windowHow far back each pass reaches, and what becomes of an event landing outside it.
IdempotencyA pass must be rerunnable with identical output. Same discipline as a schema update’s up().
Partition swap, and it ports. Both tables on yyyymmdd; rebuild one partition and swap it. MySQL has ALTER TABLE … EXCHANGE PARTITION; ClickHouse has ALTER TABLE dest REPLACE PARTITION p FROM staging, which is atomic and exists precisely for zero-downtime reloading — stronger than MySQL's, not weaker. Delta Lake's replaceWhere is looser still: selective overwrite by arbitrary predicate, with no requirement that the table be partitioned on those columns. (Iceberg unchecked; BigQuery's truncate-then-load pattern is established but its mechanics were not verified.) So the rebuild-and-swap idiom is not a MySQL trick abandoned at the columnar boundary — it is the native idiom on the other side.
The portable constraint is structural match. Both MySQL and ClickHouse require the staging table to mirror the target — same structure, partition key, ordering and primary key — so staging carries no convenience columns and a schema change must alter both in step. MySQL additionally refuses the exchange where foreign keys are involved, which the denormalised table would not have.
Dropping is free; reorganising is not. 1.x already relies on this in production: PartitionRotateCli notes that “drops are not counted at all: DROP PARTITION discards a file and returns”, while extending the lead or merging is a REORGANIZE that rewrites rows. Columnar stores are the same shape only more so — the partition is the storage unit, so a drop unlinks files rather than scanning. Retention is therefore cheap on both; what is expensive on both is updating rows, which is what this design avoids.
Raw retention, which trades storage against how far back the model can be re-derived.
Worst-case client-side lateness, which sets the late-arrival window and therefore the whole cadence. Revised: this was written as “queue reorder latency”, to be measured as a drain after a stall, citing 1.x's two long stalls — the notify poison-pill and the legacy-class decode failure. Both were owa_queue_item stalls, and that queue only ever holds retries of events whose session could not be found, which v2 has no equivalent of. The unbounded tail those incidents represent is v1-only. What remains is the file queue's drain cadence, which is configured rather than measured, and lateness originating at the client, which is not visible server-side and is the genuinely open number.
Cost on a small installUnmeasured. Demo is 326k sessions and peteradamsphoto 203k in total, not per day, so a pass over these volumes should be seconds — but it runs on an RDS instance shared with eight WordPress sites, and that is the constraint to measure against, not the row count.
Distinct visitors do not sumEvery other measure above is additive across rows; unique visitors is not, so a rollup row cannot carry it and have breakdowns add up. §1.9 promises "every number exact, every breakdown summing to its total", which this would violate the moment anyone puts uniques on a trend. Either uniques come from raw or the denormalised table and are therefore slower, or the rollup carries a sketch and the exactness promise is narrowed in writing.
A parameter map in an aggregate key has no bound§1.3 wants custom variables in the rollup, and that is the feature that removes 1.x's five fixed slots. But unregistered keys with unbounded values multiply the row count by their cardinality — the thing a rollup exists to avoid. Promotable-per-site (§1.11's treatment of param paths) is the obvious lever and is not the same decision.
PII — closed. The tool cannot police its inputs: PII arrives through custom variables, URLs and referrers regardless of what happens to the one declared field (measured: 3 real values in 135,798 rows). The operator is the data controller; OWA has the same standing as their web server logs. Crypto-shredding and the pseudonym mapping are dropped; declared user fields are ordinary event params. What remains are the operator's real obligations made practical: anonymise-by-default, retention, and forget visitor=<id> — which deletes events wholesale and so reaches PII through every channel, declared or stuffed.
