IArchitecture

1.1The shape Decided

Every tracked interaction becomes one row in one table, GA4-style, replacing ten parallel fact tables and their dimension satellites. A write is a single insert with no lookups — no session upsert, no dimension check-and-create — and the ids of events that must collapse on redelivery are derived from their own content rather than assigned.

1.2Sessions Decided

A session is not a table and not a row. Session totals come from the day rollup; session context is stamped on every event. Marker events (§1.3) exist for what they carry, not for what they count.

1.2.1Engagement is measured in deltas

engagement_msec rides every outgoing event: the time accrued on the current page since the last report. Attribution to the enclosing envelope is then automatically correct, and losing a beacon costs one increment rather than one page.

The hide-time user_engagement event carries the residue since the last event. It fires on any hide, at any size — the engaged threshold (§1.2.3) gates read-time classification, never the send, or it would bake itself into collection. Its id is content-derived, hash(page_view_id + seq). It is beaconed at hide and then rides the session's next request as parameters rather than a separate catch-up beacon; the server materialises the row and duplicates collapse at the table. Final-page dwell is the one irreducible lossy attempt, and the thing 1.x cannot measure at all.

1.2.2Engaged is derived at read time, never stored

A session is engaged if any of three things is true. No sticky client-set flag is stored, so there is no classification for the derivation to disagree with.

DisjunctWhy it is loss-tolerant
SUM(engagement_msec) ≥ thresholddeltas ride every event, so one lost beacon costs one increment
pageviews ≥ 2a row per pageview
a goal eventa row of its own

1.2.3Bounce means not engaged

A bounce is a session that is not engaged, by the three disjuncts above. The single-pageview definition is retired: it measures beacon count rather than attention, and 1.x cannot see final-page time at all. v1 history keeps the old definition in its own UI, so neither system's trend steps.

  • The threshold is per-site, defaults to 10 seconds, and is retroactively tunable — events are immutable and only the lens changes — with a UI annotation at any change date, since historical bounce numbers move with it.
  • Parity expectation, declared in advance: v2 bounce ≤ v1 bounce. A v2 number above v1's is a defect, not an intended difference.
  • Engaged as a dimension is deferred past v2.0. The question installs actually ask — which URLs have the most engagement — is a one-pass SUM(msec) GROUP BY pagePath with no classification involved. Nothing is stored, so adding it later is a query-builder feature rather than a schema change.

1.2.4A record's existence never depends on one packet

Values may degrade. Records must not vanish. A marker event rides a single beacon, so losing one would erase a session while its other events still counted — which is exactly why session totals are taken from the rollup rather than by counting markers (§1.3.2). A delta or a stamped value rides every event, so losing one costs nothing or a single increment. Where a design can put a value on either shape, it goes on every event.

1.3Events and markers Decided

GA4's taxonomy is the guide, because it is the vocabulary the market already speaks. The event set itself — what the tracker sends automatically, what a site opts into, and how each maps to 1.x and to GA4 — is tabulated in §2.2.

Two of those events are markers, and no browser ever sends them. session_start and first_visit are materialised by the server from state that already rides the session's first page_view request, so they cost nothing on the wire. The rest of this section is what they are for, and the counting rules that follow from a marker being losable.

1.3.1What the markers are for

A metric and a dimension can only be combined where a row exists at their shared grain. session_start is what gives sessions that row: without it, “sessions by landing page” is not slow, it is unavailable. Supplying that grain is the job owa_session's 121 columns do in 1.x.

Markers also carry the attribution the client knew at that moment — session-scoped on session_start, user-scoped on first_visit — and they are the natural thing to name as a goal event.

1.3.2Totals, breakdowns, and the (unknown) row

A marker rides one beacon, so it can go missing. That single fact sets three rules:

NumberComes fromWhy
A session totalthe day rollupA lost marker then degrades that session's attribution without erasing the session. GA4 counts sessions the same way, for the same reason
A session breakdowncounting marker rowsFar cheaper than a DISTINCT over session ids
The differencea synthetic (unknown) rowTwo different sources can disagree, so the API states the gap instead of hiding it

The rollup is therefore the authority for session counts and their breakdowns, which is why it carries the session's dimensional context rather than only its measures (§2.1). Where a total and a breakdown meet on one screen the total wins, and the (unknown) row carries the remainder — sessions the total can see and the breakdown cannot attribute. Two rules keep that honest:

  • the row appears only for a positive remainder, and is labelled (unknown), never blended into (not set), which means something else entirely (§2.11);
  • a negative remainder is never clamped. A breakdown exceeding its total is a defect, and absorbing it would turn the parity harness's clearest signal into silent correction.

1.3.3Goal events are author-named events Decided

1.x had twenty numbered goal slots. v2 has none. An author names a goal event and gives it an event type and a condition — “a click whose target is x” — and when the condition matches, the server materialises an additional row whose event_type is that name. That is the marker mechanism again, pointed at a condition the author wrote, and it is the shape GA uses for key events.

Three rules come with it:

  • the materialised row is never counted as an ordinary event, the rule already set for session_start;
  • the triggering event stays an ordinary page_view with is_goal_event = 0, because flagging both would double-count and blur which row is the conversion;
  • the event_type vocabulary therefore stops being closed — intended, but stated here so nobody discovers it by naming a goal event page_view.

They are called goal events, not key events. GA renamed its conversions to key events in 2024; a 1.x installation has goals, and the people using it say goals, so OWA keeps its own noun. Where this document describes what GA does, it still says key event. The numbered slots are already gone in 1.x, so v2 inherits authored goal events rather than introducing them — counting, per-goal metrics and the once-per-session clamp are §2.20.

1.4Visitor identity Decided

A visitor is arbitrary: it must be assigned, carried and trusted, where a page or a referrer is just a value a report groups by. That makes it the one identity v2 has to mint, and the only one it can get wrong.

  • The entropy limit is accepted, not fixed. The id is a unix timestamp plus 9 random digits. The budget is nearly all spent — 60.6 of a signed BIGINT's 63 bits — but it is spent on the timestamp, so within any one second only about 30 bits of it separate two visitors. It cannot be improved: re-dividing the budget provably cancels, because coarsening the time bucket by k multiplies ids per bucket by k and grows the random space by the same k. The rate is ~0.8 collisions/year at 10 new visitors/sec, and each one silently merges two people. GA's _ga uses the same construction with one more bit. The discarded salt was removed rather than honoured (PR #1017).
  • is_new_visitor becomes derivable from the first-seen timestamp carried on every event, rather than being a marker.
  • Known users resolve at collection time only. Events collected before someone identified themselves stay anonymous forever — the same answer as goals and bot reclassification.
  • Cross-device requires a site-supplied user id or does not happen. No fingerprinting and no IP-and-user-agent heuristics: a probabilistic join produces a number nobody can check.

1.5The three storage layers Decided

LayerGrainServesRows (measured)

Rollupday × dimensional contexttotals and trends, start-day attributed5,785

The fact table stops being primary. Events land in raw exactly as they arrived. A pass reads that and writes a denormalised fact table with session- and user-scoped values materialised onto every row. The rollup aggregates from there. Queries hit the denormalised table; raw is the record of what was observed.

The thing that makes it work is that a derived table can be rebuilt. You never UPDATE a fact row, you regenerate a partition — so no-retroactive-fact-updates survives intact, and stops being a constraint that forces values onto the wire. How the pass runs is §2.7; how partitions are cycled is §2.8.

1.5.1No session table

There is no session-grain derived table. Session context is stamped on every event row, so the event table is the session-grain table, and every session metric is a one-pass aggregate over it.

Session metricHow it is computed
engagement timeSUM(delta) by anything — the deltas are additive
engaged sessionsDISTINCT IF
source, campaign, landing pagegroup by the column, stamped on every event of the session

owa_session is needed in 1.x for the opposite reason: its events carry none of this. The derived table is not forbidden either — it demotes to an optional materialisation an install can add later with one rebuild, if breakdown latency ever outgrows these shapes.

OWA's realtime can be richer than GA's, because OWA carries session-scoped values on the wire and GA does not — so event and session scope are both raw-resident here, and only user scope waits for the pass.

1.5.3What to carry and what to derive

The rule is not “carry what cannot be derived” — GA carries first-seen and session count, both readily derivable. The rule is about what kind of thing the value is:

KindTreatmentWhy
Counters and anchors the client already maintainsCarryvid, sid, session count, first-seen, last-hit. The client computed them for its own session decision, so sending them costs a few bytes and saves an expensive per-visitor ordered scan. Correct in raw immediately, with no pass
Resolutions needing server-side dataDeriveSource and medium from the referrer and tags, geography from the address, device from the user agent. The client cannot know these without shipping OWA's tables to the browser
Decisions and modelsDerive, never carryattribs is wrong to carry not because it is reconstructible but because it is a verdict. A model frozen in a cookie cannot be revisited when the model changes

By that rule nps and fsts stay — they are observations — and attribs goes.

1.5.4The visitor store

v2 keeps one visitor-grain table, for a single value that cannot ride an event: acquisition — the source, medium, campaign, ad and search terms of the visit that created the visitor. It originates in one first_visit event that may be years old, and no later beacon carries it. Everything else about a visitor already rides every event and is recovered by a group-by, so nothing else earns a row here.

  • It holds acquisition, written once and never updated, plus last_seen, which exists only to drive the TTL. Column by column it is §2.9.
  • A visitor row expires after N months of inactivity, default 13. A sliding inactivity window rather than a fixed lifetime — the shape every other vendor uses, and roughly where two of them independently land.
  • Expiring a row does not rewrite history. Events already denormalised keep the acquisition values stamped on them; only the ability to attribute future events is lost, and a visitor returning after thirteen months of silence is a new acquisition by any reasonable reading.
  • When first_visit falls outside the window, acquisition resolves to NULL — never to the visitor's earliest retained event. That fallback would change the answer every time the window slid forward. Absent is a fact about the data; a drifting value is a defect.

The vendor retention survey and the measured visitor lifespans are A.1; the argument that nearly removed this table is A.2.

1.5.5Consequences for decisions already taken

  • Raw plus denormalised roughly doubles event storage before the rollup, recoverable by pruning raw — at the cost of re-derivability past that horizon, which is one of the main benefits.
  • §1.6's two freshness tiers get a mechanism: event-grain immediate is the raw table, everything attributed waits for the pass. The tier boundary is no longer a policy, it is where the data physically is.

1.6Freshness and the API Decided

Two freshness tiers. Cost tracks window width, not table size, so a thirty-minute window is trivial against raw events while a year is not — the rollup buys breadth, not recency.

ViewReadsFreshness
Realtime — “what is happening now”raw events, short windowimmediate
Historical — “last month by source”rolluplast job run

So the freshest number in the system is the most naively computed one, and “is my tracking working?” — the question that must never be stale — never touches a summary.

1.6.1Realtime is one screen, not a mode on every report

1.x expresses realtime as a Live View toggle on every report, which re-runs the historical query more often: on the traffic report that is nine full-period aggregations every fifteen seconds. The cost scales with period width × widget count and not at all with how much changed, which is the tell — it asks a historical question to get a realtime answer.

Realtime becomes a single dedicated screen, a short window over raw events. One query, one partition, no summary touched. This is also what GA ships, and it removes the per-report auto-refresh control and the per-widget polling behind it.

What this does not fix: historical reports remain stale for the current day, because they read the rollup. The answer is composition rather than polling — rollup(closed days) + raw(today), where closed days never change and cache indefinitely. Recorded as the follow-on, not folded into this decision.

1.6.2Eventual consistency is a rollup property, not a scheduling one

A rollup that advances a watermark can never converge: an event arriving after the watermark passes its own timestamp is not late, it is lost. So the rollup recomputes a trailing window idempotently. The window is the lateness horizon, and it is the number a test asserts against.

1.6.3The API is the contract for both UIs

Metric and dimension discovery already exists — resultSet.relatedDimensions feeds the existing explorer widget's pickers — so v2 formalises it rather than inventing it. Freshness belongs in the response envelope beside the row count, because it is a property of a result set rather than of the installation.

1.7The UI layer Decided

  • Reporting is client-rendered against the API. Charts and the grid rest on abandoned jQuery plugins (flot, jqgrid) which have to be replaced regardless.
  • Admin stays server-rendered. It is forms and tables; a SPA buys nothing.
  • Reports become JSON. Most existing reports are one shape wearing different labels, so a generic widget format with grid layout descriptors covers both them and the dashboards, and retrofits into 1.x additively.
  • Both reporting UIs run side by side for as long as wanted, sharing one session. A separate login for each would make comparison tedious enough that nobody does it, turning the overlap period into a rubber stamp.
  • The charted metric is chosen by the reader, not by the report. The result set already carries every series, so the only thing missing was a way to ask. chartMetric stops being the charted metric and becomes the one charted first; its absence keeps its current meaning of drawing no chart, because a report wanting no trend is a different statement from one that has not chosen a starting series.

1.8Privacy and retention Decided

  • Anonymise by default. The implementation exists; the default is simply wrong for a privacy-positioned product.
  • Installation-wide retention, enforced by a scheduled job, with a real default rather than “forever” — deliberately not per site, see §2.17.
  • An erasure command — forget visitor=<id> — reaching events, recording payloads and rollups, and tested, because an erasure path that silently misses a table is worse than none.
  • Retention and erasure share mechanics and must not share a code path. One is time-based and bulk; the other is subject-based and exact.

The single table cuts both ways: erasure by visitor_id becomes one delete in one place, but denormalisation means an email in a URL query string now sits on every event that saw it. Erasure has to scan, not look up.

1.9One tracker, two pipelines Decided

A single tracker describes each event richly enough that both pipelines can consume it. The server fans one received event out to both — v1's handlers write the star, v2's write the event table — and at parity the fan-out to v1 is switched off. Nothing about the page changes on that day.

Two trackers would have split each site's data by which snippet happened to be deployed, so v1's history would step or stop the moment a site upgraded, destroying the value of the thing being kept.

1.9.1One session model, adopted by both pipelines

v1 and v2 disagree about when a session begins, and one cookie cannot hold two models. The tracker gets one session model, v2's, and v1 adopts it. One tracker, one cookie, one beacon, one stream; the server writes v1's star from it as before and v2's event table when enabled. The integrity check of §2.22 can therefore be a diff rather than a tolerance.

1.9.2What it costs v1's numbers

One discontinuity in v1's session-derived numbers, accepted deliberately. Three rules differ, and they are not of equal size:

RuleEffect on v1's counts
Sessions begin only on page-view eventsNone in practice. Integrations call trackPageView first regardless
The midnight rule splits a session spanning midnightMeasured 0.106% — 8 sessions in 7,547, mean duration 109s. Negligible
The store is withheld until sendAcceptedEdge cases only: a lost beacon means no session where one would previously have been recorded
A session restarts when new attribution tags are seenThe material change. A visitor who arrives tagged, browses, then re-enters through another tagged link inside the timeout now starts a new session where v1 kept one

That last is GA's behaviour, and the reason the tracker must notice a mid-session tag change and restart cleanly. Its size depends entirely on traffic mix — near zero for organic-only sites, material for campaign-heavy ones — and cannot be taken from v1's own history, because setTrafficAttribution() stores the decided verdict rather than the observation. Not treated as a blocker — A.1.

Event-level history — page views, clicks, geo, referrers — is untouched, and nothing already stored is rewritten. The change still wants a UI annotation at its date. Coexistence is cheap because effectively all volume is parallel: v1 keeps its own facts and dimensions, and the shared admin set is 0.1 MB.

1.9.3The v2 pipeline is switched on per site Decided

The page carries one tracker, and the server fans one stream to both pipelines, so a site is not moved onto v2 by changing its tag. It is moved by a setting: turn it on and that site's incoming events are written to the v2 event table as well as the star; leave it off and nothing changes. v2 collection is therefore opt-in per website, decided by whoever owns it, rather than something an OWA upgrade starts doing.

Note what this separates. The session change is not opt-in — it ships with the tracker and reaches every install at upgrade, and the cost of that is the table above. The v2 pipeline is opt-in and reaches nobody until asked for. Conflating the two would mean either a silent schema change or a tracker carrying two session models to keep the switch honest.

1.10What v2 deletes Decided

Against the live registry: 78 metrics × 100 dimensions = 5,493 valid API pairs. Under v2, 4,443 (81%) work unchanged, 770 (14%) reference the eleven *InVisit dimensions which have zero references anywhere outside their own registration, and 280 (5%) need an exit page served by an is_exit flag. Every pair is either unchanged or has a stated replacement.

Also retired: owa_session's 121 columns (45 of them goal columns) and nine derived date-part columns per fact row. The dead owa_exit entity is already gone — removed from 1.x in #1048 with its registration and its setting. Its table is deliberately left in place: dropping it is a destructive migration and a separate decision from deleting dead code. The name also moved to the legacy class-name test's RETIRED list, which asserts it is gone rather than merely dropping it — a real backward-compat break, taken deliberately.

base.feed_request goes the same way, and for the same kind of reason: the collection path is empirically dead on both installs (§1.11). What v2 drops is the event type, the entity and the one dimension — feedType — that reads it. As with owa_exit, the table stays where it is, because dropping 350,744 historical rows is a destructive migration and a separate decision.

The risk inverts. 1.x's entity boundaries prevent non-additive metric combinations — the resolver intersects entity sets, so bounceRate × pagePath is correctly refused today. A single table has no such boundary, so v2's registry must enforce explicitly what the schema currently enforces implicitly, or it newly permits nonsense.

IIImplementation

2.1Table layouts Decided

The column-admission rule: a field is a column if its name is known at release time and it is scalar; params (JSON) is reserved for what cannot be a column — site-defined keys unknown at release time (unregistered custom variables; the alternatives are user-controlled DDL, a forbidden registration step, or a forbidden EAV join) and nested arrays (commerce items, which cost 1.x a separate fact table and a join). Params buys nothing else: the wide prototype measured storage as a wash, JSON extraction is slower than a column, and MySQL 8 INSTANT ADD COLUMN removes the ALTER cost for release-known fields. Columnar stores agree more strongly — wide and sparse is their native shape, and their JSON shredding covers the dynamic keys (one param key, one type, enforced at ingest). The three layouts below land at 35, 47 and 25 columns against owa_request's 58 + owa_session's 121.

Which layer a column belongs to follows one cut: a column belongs to raw if it is an observation or a mechanical resolution, and to the denormalised table if a pass has to derive it. That is the same cut §1.5 applies to the wire, one layer down.

Two logical stores. The application tables (sites, users, config, goals, job state) require a SQL store — MySQL-class, transactional, never abstracted away. 2.5.1Choosing the interval

The interval and the partition granularity are one decision, not two. Each run rebuilds however much of the current partition exists, so at */15 that is 96 rebuilds a day: on a monthly partition the last of them rewrites a month, and the cost climbs through the month. On a daily partition it rewrites at most a day, flat. A sub-hourly cadence is affordable on daily partitions and not on anything coarser — which is why daily was added to PARTITION_CUTS in PR #1113, additively: nothing adopts it on its own.

Two cadences fall out. A frequent run on the current partition, which sets the attributed-freshness tier; and a less frequent run across the rest of the late-arrival window, which is where a late first_visit is actually picked up.

One constraint from the shipped scheduler is easy to miss: the lock is keyed on the job name, so a single name serialises every partition that job touches. Rebuilding the window in parallel would need per-partition job names.

2.6Ingest Decided

One beacon does not become one row. What the client sends and what the system stores are different sets, and the expansion between them happens here rather than in the pass.

2.6.1One beacon becomes several events

One beacon can become several events. The client sends a single page_view carrying flags; the server raises session_start and first_visit from them. Confirmed against GA by capture: a first page view arrives as one en=page_view with both _fv=1 and _ss=1 and no separate beacon, and the two appear in BigQuery as distinct event_name rows.

That expansion happens at ingest, into the raw log, not in the pass. The test for which side a derivation falls on:

  • Per-beacon derivations go in at ingest. Raising first_visit from is_new_visitor_created is a pure function of one beacon. It needs no other event, no lookup and no ordering, so it belongs on the straight-line path where there is nothing to race and nothing to de-duplicate.
  • Cross-event derivations go in the pass. Acquisition source needs the visitor’s flagged event; session finalisation needs the session closed. Those require context the single beacon does not carry.

Putting the expansion in the pass instead breaks three things at once. The pass acquires a second job — synthesise as well as enrich — and must then be idempotent about creation across every rebuild, which is a much harder property than idempotent enrichment. Two passes over one partition, or a pass racing a rebuild, can double-raise. And realtime reads raw, so first_visit and session_start would be invisible live despite being exactly the events people report on.

2.6.2The expansion is one atomic write

It also makes the expansion atomic. All the rows one beacon becomes are written in a single handler, so they can be written in a single transaction. A page_view that landed without its session_start, or a first_visit without the page view it was raised from, is not something a later pass can repair — the flag was on the beacon that half-wrote, and re-reading raw would see the same partial state and reproduce it. The guarantee has to be made where the rows are created.

1.x does not do this today: Db::beginTransaction() exists and every fact table is already InnoDB, but the only callers are the schema-update CLI — each create() in the ingest path stands alone. Nothing has depended on it while one beacon meant one row. Once one beacon means three, a half-written set is possible.

State the guarantee portably as one atomic write of everything a beacon becomes rather than as “a transaction”. On MySQL that is a transaction. ClickHouse has no general transactions, but a single multi-row INSERT lands as one part atomically, which satisfies the same requirement — so the guarantee ports even though the mechanism does not.

Ingest-time expansion gives each layer one job: raw is the event stream as the system understands it — every event that happened, expanded but not enriched — and the pass is a pure row-in/row-out enrichment, idempotent by construction because it never creates anything. The taxonomy in §1.3 already names both events as server-materialized; this is where in the pipeline that happens.

2.6.3The flags, and why acquisition keys off one

OWA has the flags already, with three different lifetimes, and the distinction matters:

  • is_new_visitor_created — the one REQUEST that minted the visitor. GA's _fv. Raises first_visit.
  • is_new_session_start — the one REQUEST that created the session. GA's _ss. Raises session_start.
  • is_new_visitor — SESSION scoped, rides every beacon of the first session. Keeps is_repeat_visitor from flipping mid-session. Not the raiser.
  • is_new_session — PAGE scoped, rides every beacon from the page the session started on. What is_entry_page needs.

Keying acquisition off the flag rather than off a computed earliest event is what bounds the correction problem. If acquisition were derived as MIN(timestamp) per visitor, a late event that turned out to be earlier would invalidate every row that visitor already had, wherever those rows sat — requiring a visitor-to-partition index to even find them. Keyed off the flag, no other event can change the answer: the failure mode is absent then present, never wrong then corrected, and there is no earlier history to invalidate because the flagged event is the beginning.

What remains is only out-of-order arrival — a later event processed before the flagged one. Those rows are in the same or later days, never earlier, so the blast radius is bounded by how late an event can arrive, not by retention.

2.7The denormalisation pass Decided

The pass is one function run once per partition: read every raw row in partition P, write the same rows enriched into a staging table, swap staging into P. It creates nothing, deletes nothing and updates nothing in place, so rows in equals rows out always holds. Any count mismatch is therefore a bug, which makes it a cheap check to run after every run.

Every column the pass fills is one of three things, and which one decides whether the pass has to touch it at all:

  • Observed — the value arrived on the beacon and is already in raw. The pass copies it across.
  • Resolved at ingest — a deterministic lookup with no model and no cross-event context, like geography from the address or device from the user agent. Done before the pass runs, which is why realtime can report on it.
  • Derived by the pass — either a classification that can change later (source and medium from the referrer; channel grouping), or a value that needs rows other than this one (session totals, or acquisition from a first_visit that may sit in another partition).

Scope is a separate question, and it only decides how far the pass has to reach for a derived value: an event-scoped one needs the row, a session-scoped one needs the session's other rows, a visitor-scoped one may need an event from years ago.

What changes is who stamps them and which layer they exist in: the pass, and the denormalised table, not the tracker and not raw.

Whether GA keeps a user-acquisition table internally is not observable from outside. The shape is not in question: a write-once, user-scoped value that originates in one event which may be years old, absent from the streaming layer, present on every row of the processed one. Something has to hold it between those two facts.

A partition is not self-contained. “The partition is the unit of work” describes the write side exactly, and the read side not at all: a row written today belongs to a visitor whose first_visit may be two years back, and to a session that may have started yesterday. So the pass needs somewhere to look up a visitor's acquisition (§2.9), and it cannot finalise a session whose last event has not arrived yet — which is what the late-arrival window exists to bound.

Why the pass needs a visitor store, what that store holds and how long it keeps it are §2.9.

2.7.1How one run is ordered

A session that is still open sets its own floor under the late-arrival window. A session running across midnight has rows in two partitions and cannot be finalised while building the first. The window already has to exceed how far the queue can reorder; it also has to exceed the longest session that can straddle a partition boundary, or the earlier day is sealed holding a session that was never closed. OWA’s session_length is 1800s, but that is the idle timeout between hits, not a cap on total duration — a session with a hit every 25 minutes runs indefinitely. So either the window carries an explicit session cap, or terminal values stay NULL and the row is corrected on the next rebuild, which the window makes free anyway. v2 takes the second, at no cost: §2.11 already says “(not set)” is presentation rather than storage, so “not final yet” and “no value” are the same NULL and the reporting layer already has to handle it.

The five steps must run in this order. Each one reads what the step before it wrote, and getting them backwards produces wrong rows rather than an error:

  1. Harvest. Insert-if-absent into the visitor table from this partition’s first_visit rows. Must precede step 3: a visitor whose first session and second session both fall in this partition needs their own acquisition row to already exist, and nothing about the second session’s rows carries it.
  2. Close. Compute terminal session values for sessions whose last event is in this partition and whose close is certain.
  3. Build. INSERT INTO staging SELECT … joining raw against the visitor table and the closed-session set.
  4. Swap. EXCHANGE PARTITION.
  5. Roll up. Replace that day’s rollup rows from the new partition.

The swap is what a rerun depends on. Staging is built whole and is invisible until the exchange, so a run that dies in step 3 leaves the live table exactly as it was and the next run simply rebuilds. This is a stronger property than “the statements are rerunnable”, and it is the reason to build into staging rather than to write the target directly even where a direct write would be possible. The one piece of state that outlives a failed run is the visitor table, which is why its write rule has to be insert-if-absent independently.

Step 5 is part of the job, not a separate one. The rollup is downstream of the denormalised table, so rebuilding a partition invalidates that day’s aggregates. Replacing them has to be part of the same job rather than a separately scheduled one, or a rebuilt day is served from stale aggregates until whenever the rollup next runs — the symptom is that a report and its detail view disagree, with nothing in either to indicate why.

The whole thing runs in the database. Every step is INSERT … SELECT against tables in one schema; no step needs a row in PHP. A pass that fetches rows, enriches in PHP and writes them back is bounded by round trips and by memory_limit, and on this class of box that is the difference between a job that runs and a job that OOMs. It also keeps the pass expressible on a columnar engine, where the equivalent is likewise a single INSERT SELECT. Window functions make step 2 straightforward and need MySQL 8.0 — the repo declares no minimum server version anywhere, so v2 should state one rather than discover it on someone’s 5.7.

2.8The partition cycle Decided

If a rebuild replaces a whole partition, the partition scheme decides the unit of work — so the rebuild window wants fine partitions and everything older wants coarse ones. That is a two-stage lead, three operations, and only one of them costs anything.

whenoperationcost
continuously, far aheadREORGANIZE pmax INTO (monthly…, pmax)metadata — pmax is empty

The fine partitions are never carved from pmax. They are carved from an already-created, still-empty monthly partition shortly before it goes current, so the daily lead only has to cover the reorder window plus margin — days or weeks. The long lead stays monthly and stays far out, exactly as 1.x runs it today (demo's reaches 13 months).

That split is forced, not stylistic: the lead is filled at the table's own granularity. 1.x keeps PARTITION_MONTHS_AHEAD (12) whole future months ahead, and extendPartitions() fills to that boundary at whatever granularity the table already uses — the number of months is fixed, the number of partitions is not. A table taken wholly to quarter-month therefore carries ~48 partitions of lead rather than 12, against a PARTITION_COUNT_LIMIT of 400 whose own docblock notes that quarter-month over a decade reaches 480. Making the whole table fine-grained to get a fine-grained rebuild window would spend the partition budget on empty future months. The two-stage lead spends it only where the rebuild actually happens.

Do not confuse that lead with the detail window. Three separate month-counts govern partitioning in 1.x and only one of them is about granularity: PARTITION_CUTS is the granularity itself and is not a month count at all; PARTITION_DETAIL_MONTHS (36) is how long a period keeps that granularity before compaction may merge it into year blocks; PARTITION_MONTHS_AHEAD (12) is the lead. Granularity is never a stored setting — it is inferred per table from the existing layout, defaults to monthly, and only partition-reorganize changes it, which is the seam a two-stage scheme has to extend.

pmax must never receive a row. Everything else in this section is tuning; this one is required for the scheme to work at all. 1.x already depends on it without saying so: the cost of extending the lead is “proportional to what is sitting in the catch-all” — measured at 1.52s to create 31 partitions when it is empty. Let rows land there and the next carve stops being metadata and becomes a rewrite, while rows that belong in a dated partition sit in the catch-all instead.

One job, and merge before carve. These are separate ALTER statements — MySQL permits one partition operation per statement — but they belong in one run of one job under one lock, which is how PartitionRotateCli already works (extend, then a REORGANIZE per merge, then drops). Order matters for the high-water mark, because merge and carve move the count in opposite directions: merging first frees roughly a month of partitions before the carve consumes roughly a month, so a run peaks near its starting count rather than a month above it. It also fails better — a run that dies between the two leaves the table below where it started, never over budget.

The rebuild granularity is an open trade, and there is a middle rung already built. PARTITION_CUTS offers monthly, half-month and quarter-month; daily was added in PR #1113 and cutsForMonth() already clamps cuts past a short month's end, so February and leap years fall out correctly. Daily gives the smallest rebuild and the most partitions — two months of them transiently, since the next month must be carved before the current one's window expires. Quarter-month gives a week-sized rebuild, about four partitions a month, and no new granularity. Which is right depends on rebuild cost, and that is unmeasured.

The rotation job becomes a dependency of ingest correctness, not housekeeping. Today a stalled rotation is untidy. Under this scheme the lead erodes, rows reach pmax, and the invariant breaks — so it wants an alarm rather than a log line. 1.x has had two scheduler-adjacent stalls already.

Adding it was one array entry, and it exposed one latent defect. daily is the first granularity whose cuts a short month cannot carry, and inferPartitionGranularity() compared a table's boundaries against the raw constant rather than cutsForMonth()'s clamped result — so a daily table inferred as null in every month but the 31-day ones, and a null there makes rotation fall back to monthly, silently changing a table's granularity on a scheduled run. The clamp had existed all along and had never once applied, because every other granularity cuts at or below the 22nd.

2.9The visitor store Decided

Two columns of content and one of maintenance. Acquisition — source, medium, campaign, ad, search terms — write-once from the first_visit event. And last_seen, which exists only to drive the TTL. Nothing else.

Session count does not belong here, and the reasoning generalises. nps is a counter the client already maintains and sends on every beacon, so in v2 it is already denormalised onto every event row. “How many sessions has this visitor had” is then MAX(nps) in a group-by, not a lookup — the same argument that removed the session table (§1.5.1). The rule: a value that rides every event is already on the visitor, and copying it to a visitor row adds a write without adding an answer. Only values that cannot be on the event — because they originate in one event that may be years old — earn a place here.

1.x is the cautionary version of exactly this, and it is worth stating because the mistake looks like tidiness. num_prior_sessions sits on owa_visitor AND on every fact row. Both registered dimensions that read it — “Prior Visits” and “Visits To Purchase” — read the fact-row copy, denormalised. The visitor copy is maintained by VisitorUpdateHandlers, which fires on every base.new_session, loads the visitor, runs a summarize query over owa_session, and writes a column no report can reach. A per-session row update plus an aggregate query, for nothing.

And last_seen being mutable does not put a write on the ingest path. That is the property worth protecting, since it is the one ITP made load-bearing: ingest stays a pure append with no lookups. Three things keep it that way.

  • The pass advances it, not ingest. One set-based UPDATE over the visitors seen in the partition being rebuilt, alongside the acquisition harvest that already happens there.
  • It is stored as a period, not a timestamp. The TTL is measured in months, so month precision is all it needs — which makes the value change at most once per visitor per month rather than once per session, and makes the common case a write that changes nothing.
  • GREATEST(last_seen, <partition max>) is monotonic, so rebuilding a partition twice is a no-op and the column cannot go backwards when partitions are rebuilt out of order.

So the store is written once per visitor for content, and touched in bulk at most monthly for maintenance. If a future column wants a per-session write, that is the signal it belongs on the event rather than here.

The two rules do not conflict: insert-if-absent applies to the acquisition columns, not to the row. Those are write-once; last_seen is a maintenance column the pass advances monotonically. Worth stating plainly, because “never update the visitor row” is the kind of rule that gets enforced literally by someone who was not in this conversation.

Its write rule is insert-if-absent, never update, so a rerun cannot corrupt it: a visitor has exactly one first_visit in their life, so a second write of the same row can only be a reprocess of the same event. That is the same “absent then present, never wrong then corrected” property the flag keying buys, now expressed as a storage rule. A full rebuild of the table from raw must break ties deterministically — order by (timestamp, event_id), not timestamp alone — or two rebuilds can disagree.

Two things about this table are open — the rebuild set, and what partitioning on yyyymmdd alone costs a multi-site install. Both are in §3.1.

2.9.1Do not partition it on last_seen

Partitioning on last_seen is the obvious move — expiry becomes DROP PARTITION, free and metadata-only, the same idiom raw uses. It does not work, and the reason is a hard MySQL constraint rather than a cost. Every unique key on a partitioned table must contain all partitioning columns, so the key becomes (visitor_id, last_seen_period) and uniqueness on visitor_id alone becomes unenforceable. Insert-if-absent is built on exactly that constraint. Lose it and a visitor can hold two acquisition rows in two partitions, silently, with nothing to say which is right — the write-once guarantee gone at the storage layer while the code still believes it holds.

The cost objections are real too, and would matter even if the constraint did not. last_seen is mutable, and updating a partitioning column makes MySQL physically move the row between partitions; every visitor migrates whenever their last_seen crosses a boundary. And the lookup is by visitor_id with no period in hand, so with only local indexes it dives into every partition — the by-id-across-partitions trap 1.x already documents.

If it is ever partitioned, partition on first-seen, which the id already carries. §2.1 keeps the time prefix in visitor_id, so the first-seen period is a pure function of the id. That fixes both cost problems at once: the column is immutable so no row ever migrates, and every lookup can supply the partition key it derives from the id it is already searching for, pruning to exactly one partition. Uniqueness also survives in substance — a given id can only ever hash to one period, so UNIQUE(visitor_id, first_seen_period) is uniqueness on visitor_id.

But first-seen partitioning buys nothing for expiry, and expiry is the only reason to partition this table. Expiry is by inactivity, and a first-seen partition holds a mix of long-dead and still-active visitors, so it can never be dropped whole — only deleted within.

So: do not partition it at all, and expire with a plain DELETE. This is a visitor-cardinality table under a TTL, which means it holds active visitors: 6,761 on the measured install against 445,055 request rows. A site a hundred times busier is still under a million rows, where a monthly DELETE … WHERE last_seen < cutoff against an index is unremarkable. Partitioning exists to make drops free on tables of hundreds of millions of rows; here it costs the unique constraint or buys nothing, depending which column it picks.

2.10The landing URL and campaign parse Shipped

Today the tracker parses the landing URL against campaignKeys and sends six tagged_* parameters on every beacon of the session. The parse moves to the server; what rides the wire becomes one field, the landing URL itself.

This is not what GA does, and the difference is deliberate rather than an oversight. Re-measured by capture across four session shapes, nine page views, with the complete parameter set dumped rather than a filtered subset:

  • A campaign session's first hit carries the tags in dl. Hit 2 and hit 3 carry no campaign parameter of any name — the two hits differ in exactly _fv, _nsi, _ss and _eu, and nothing else.
  • Neither cookie holds attribution. _ga is GA1.1.<cid>.<first-seen>; _ga_<ID> is GS2.1.s<sid>$o<count>$g<engaged>$t<last hit>$j<n>$l0$h0.
  • A second page tagged with a different campaign sends the NEW tags as collected. GA neither suppresses them nor resends the originals — which is collected_traffic_source per event against session_traffic_source_last_click derived.

And it stays a column on the denormalised row, not just an input the pass consumes. Two reasons, and the second is the one that matters.

  • §1.3 already requires it. “Sessions by landing page” at 215 ms against 3.1 s as a first-event join is the measurement that removed the session table, and the scope table above already lists landing page as session-scoped and stamped on every row. Keeping the URL rather than a stripped path costs one column.
  • It decouples re-derivability from raw retention. If the denormalised rows keep only the resolved source, medium and campaign, then the moment raw is pruned those answers are final — there is no evidence left to re-read. Keeping the landing URL on the row means the evidence outlives raw, and a parser fix or an ns change can be reapplied to years of history. That is exactly the argument that justified the visitor table, one layer down.

The cost falls on realtime, and it is narrow. A raw row from later in the session will not carry the landing URL, so a live query cannot resolve session campaign for it. It still carries session_referer, so referring host, and referral against organic-search, still work live. Narrower than losing session source altogether, and still ahead of GA, whose Realtime API has neither. The claim in §1.5 that OWA's realtime is richer than GA's survives; it is just richer by referer rather than by campaign.

2.11Absence is stored as NULL Decided

A magic string is not absence; it is a value that merely looks like absence, and the difference shows up everywhere downstream. It groups as its own bucket, so a pie over the dimension draws a “(not set)” slice indistinguishable from a real category. It sorts among real values. It cannot be told apart from a visitor who genuinely typed that. And the codebase already knows it is lying: Visitor.php checks != '(not set)' before using a name, and TrackingEventHelpers does the same for REMOTE_HOST and search_terms — three separate places reconstructing an absence the schema threw away.

v2 stores absence as NULL and decides the label at render time. The reporting layer already formats values; “show nothing as (not set)” is a formatter's job, one place, changeable without touching data, and translatable. Baking it into the row makes a display string permanent and unrecoverable — the one thing §2.1 says facts must never be.

Follows the same rule as the boolean columns below it: the store records what happened, the presentation layer decides how to say it. Note this narrows what a nullable column means rather than widening it — NULL becomes unambiguously “not provided”, which is only useful if the write path never also writes a sentinel meaning the same thing.

2.12Boolean columns carry three values Decided

A nullable boolean holds three values, and GROUP BY gives each its own bucket. In 1.x the boolean fact columns are nullable with no default, so is_repeat_visitor holds 1, 0 and NULL — and every one of those is a distinct GROUP BY bucket. A pie over the dimension draws two separate slices that both format as “No”, which is how this was found.

The cause in 1.x was a derivation that returned true for one branch and fell off the end for the other (setRepeatVisitorFlag, unchanged since 2015). That specific bug is fixed, but the shape is the problem: nothing in the schema, the entity layer or the ingestion pipeline stops a write path leaving NULL in a column that has only two meanings.

Fixing the derivation is not enough, and the reason generalises. Rows written before such a fix still hold NULL, so the third bucket survives in the data whatever the writer does now: the pie was still drawing two slices labelled “New” on a live install, months after the derivation was corrected. The client half had to change too — the chart now sums by label rather than emitting one slice per row, because a valueLabels map that folds two values onto one name is a statement that they mean the same thing, and a renderer that still draws them apart contradicts it. Two things for v2 follow: NOT NULL DEFAULT 0 fixes new writes and nothing else, so a schema that has ever permitted the third value needs a migration to close it; and any renderer that groups by a labelled value must fold labels, not rows.

For v2:

  • Declare booleans NOT NULL DEFAULT 0. The storage should refuse the third value rather than rely on every writer remembering. 1.x cannot retrofit this cheaply — it is an ALTER over every install’s session and fact tables — which is exactly why it belongs in a schema that is being defined rather than migrated.
  • Give the type a formatter, not each report. A boolean dimension should render as Yes/No wherever it is shown, from its declared type. 1.x now does this, and the same seam should exist in v2 rather than every widget re-solving it.
  • Let a report rename the values. Yes/No is the correct default and a poor label for a specific question — “New/Repeat” reads better on a visitor-type chart. 1.x added a per-widget valueLabels map for this; keep the split, with the type supplying the default and the report overriding it.
  • Some flags have a real unknown state, and want an explicit three-state type. Some flags really do have an unknown state. Those want an explicit three-state type, not an accidental one.

Open question: whether 1.x should backfill the existing NULLs or normalise at read time. Reporting currently cannot express a normalised column — the dimension registry prefixes a table alias onto whatever it is given, so COALESCE(...) is not expressible as a dimension today.

2.14Schema versioning Decided

One schema version, one numbered update sequence. An update may touch v1 tables, v2 tables or both. v1 and v2 are not two schemas that coexist; they are one schema containing both shapes — which removes the version pair, and with it any compatibility matrix or cross-sequence ordering question.

The mechanism already works this way: only Base has ever had updates, install() builds tables from entity registration and never replays updates, and the apply loop already sorts numerically, stops at first failure and resumes.

The sharp edge

A dropped v1 is a supported state, so every update written afterwards must tolerate those tables being absent — not just ones that mean to touch them. The apply loop stops at the first failure, so one update assuming owa_session exists blocks every later update for those installs, and isUpdateRequired() then wedges them out of the admin over a table they deliberately removed.

Worth a helper on the update base class rather than a documented convention — the failure lands on the update written eighteen months from now.

2.15Packaging Decided

Unchanged. Same tarball, same Release Packager workflow, same wizard. No Composer requirement for end users, no build step at install time, no new runtime dependency. The distribution model is the reason a self-hosted tool gets installed at all, and a rewrite is exactly when one is tempted to modernise it into something needing a toolchain on the target machine. The schema changing is not a reason for the delivery mechanism to change.

2.16Testing Decided

The two harnesses of §2.22 are the primary tests — pipeline integrity generated and exhaustive, model characterization hand-written and small. Neither alone is “the” test, and reporting them as one is the failure mode that section describes. Around it: 77 test files and 509 methods today, of which only 8 files are named for star-schema artefacts — most of the suite tests CLI commands, settings, auth, validation, the queue and the scheduler, and ports unchanged. What genuinely expires is the part testing the star's mechanics.

Three hazards, the first two already known here:

  • Order-dependent tests — CI already runs an isolation sweep executing each file alone. More valuable during a rewrite, not less
  • Vacuous assertions — double-quoted PHP needles containing $this-> interpolate away and pass unconditionally. A rewrite writes many tests quickly, which is the condition that produced these the first time. Worth a lint
  • Silently narrowing coverage — a test deleted because it tested the star, never replaced, leaves no trace. A green suite that is green because it asks less

Claims in this plan that are worth nothing untested: the rollup folds in a late event on the next run; an event beyond the horizon does not, but still lands in the event table; running the rollup twice changes nothing; a throwing v2 handler fails neither the v1 write nor the request; the update sequence runs clean with v1 dropped; and generated realtime SQL carries a closed partition-key range — asserted on the SQL, since a timing assertion on a small fixture would pass either way.

2.17Multi-site Decided

The area needing least work: a single event table handles tenancy naturally, site_id is a column, isolation is a WHERE, and it already leads the composite indexes. Permissions are already per-site.

Two things change. site_id becomes more load-bearing — it leads every composite index and every report's WHERE — so it must be immutable. And site_family is written by site creation and read nowhere; it was built for a UI that never shipped, and should be dropped rather than ported.

Retention stays installation-wide, not per site. A partition of the shared event table holds every site’s rows, so varying retention by site could not be a partition drop — it would need a row-level DELETE sweeping every partition, leaving fragmentation behind and competing with live writes. Uniform retention is a metadata-only partition drop, effectively instant, and already implemented. The single table makes the simpler policy the cheap one.

2.19Build order Decided

Three rules: defects whose cost accrues daily go first, since a day of delay is data that cannot be recovered; foundations before what is built on them; the expensive irreversible work last, when the most is known.

Standing precondition — coverage before development

2.20Goals became goal events Shipped

3 Sep 2026 — branch feat/key-events, PR #1064.

Unplanned work, recorded here because it moved a v2 decision into 1.x rather than merely preparing for one. §1.3 says v2 has no numbered goal slots and that an author names a goal event and gives it a condition. That is now true in 1.x.

  • Goals move from a settings blob into their own tables. owa_goal_event with its conditions in owa_goal_event_condition, replacing twenty numbered slots in a serialised settings blob. The old screen listed twenty rows whether or not anybody had filled them in, because the storage was a fixed-length array and the screen showed the storage; the new one lists what exists, so “counts nothing yet” became a state the UI can represent.
  • A goal event takes several conditions, combined with ALL or ANY, over any tracking property, with seven comparisons. 1.x had one URL and one match type, which could not express “a purchase over 50 from the pricing page”.
  • A goal event belongs to the website, not to one way of measuring it, so a site and an app reporting into the same website count a conversion against the same definition.
  • Counted once per session, clamped. See the note in §1.3: v2 removes the constraint rather than the setting.

The funnel is the part that matters to v2. A funnel was configuration — rows hanging off a goal, read by a report. It is a visualization now: a saved analysis of a path, computed at read time from the fact rows, listed beside custom reports but on its own surface because it computes rather than configures. Two consequences this plan should carry:

  • Nothing in reporting reads owa_session's goal columns. The 45 numbered goal{N} identifiers in §2.13's “falls out” row can retire without taking the funnel with them, because the funnel never consulted them. It reads the events. That was not true a fortnight ago and it removes a migration hazard nobody had costed.
  • A funnel step can name a goal event, and it means what writing that goal event's conditions into the step by hand would mean — the conditions are compiled into a row predicate and matched against the facts. Deliberately not a lookup of the stored conversion: a flag on the session has no timestamp, so there is nothing to order, and it is stamped forward-only, so a goal event created this morning would draw an empty funnel over last month. This is also how GA does it, and it is the same read-time evaluation v2 assumes throughout.

One measurement worth keeping. The funnel counts a closed, indirectly-followed sequence per subject — GA's defaults. Three ways of doing the sequencing in SQL were built and benchmarked against scratch tables carrying owa_request's real schema, with a realistic drop-off over three steps at 262,144 rows: nested derived tables 3.87s, a temporary table per step 3.06s, window functions 3.01s, against 1.11s for one flat scan walked in the application. All four agree on the counts. Every SQL formulation reads the fact table once per step; the scan reads it once, and narrowing does not rescue them — the variant that genuinely shrinks its input at each level is still three times slower, and the composite index those joins want made the worst of them worse. v2 should not assume that moving a per-subject sequence into SQL is the faster choice; on this shape of question it is not, and the memory problem that suggested it was actually get_results() materialising the scan rather than the scan itself.

2.21Early cutover, per feature Decided

Fan-out is per event type, not global. A feature skips the dual-write period entirely when both hold:

  1. v1 has no history worth preserving for it — nothing to strand, no oracle to compare against
  2. keeping it dual-written would mean renovating v1 storage to carry data only v2 can use

Domstreams qualify on both. Everything v2 changes about them is storage-shaped: a recording becomes an attachment rather than a parallel fact row, the payload moves outside the row, the encoding becomes delta tuples plus gzip (~30× measured). Dual-writing leaves only bad options — either the new capture has nowhere to land, or owa_domstream is renovated to accept a format v1 will never report on. Heatmaps follow, being built on the same capture.

2.22The parity harness Decided

Both pipelines consume identical events, so v1 can serve as an oracle — but only below the session boundary. That is what this harness is for.

v1 is not an oracle for anything session-scoped

This section already made the argument for attribution — parity there “would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right.” That reasoning is not special to attribution. v2 keeps the event and changes the session, so it applies to everything the session model touches.

And the divergence propagates. Per-site session stores give site B its own session where v1 shared one; sessions are created only by page-view events; the store is withheld until sendAccepted. So visits is a different number by design — and visits is the denominator of 6 of the 8 formulas in the tree. Bounce rate, pages/visit, actions/visit and revenue/visit all diverge without anything about their own definitions changing. Separately, 18 of 34 metric classes bind to base.session directly.

Which means the “intended differences” list below is not five enumerable items, it is most of the surface — and the warning attached to it turns on itself. An exclusion list that large is not an exclusion list; it is the majority case, and a real regression hides comfortably inside it.

Attribution has a warm-up — it cannot be cut over cold

Today attribution is decided in the browser. setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the decided result — source_id, medium, campaign_id — not the observation that produced it.

Two consequences for the sequence. Existing history is not a usable touchpoint log, so the server-side model cannot be validated by replaying it — parity against v1 attribution would prove only that the new code reproduces the old verdicts, which is not the same as proving the new model right. And original is a sliding 60-day window, not first-touch-ever, so a server-side implementation produces nothing trustworthy until it has observed 60 days of traffic.

Therefore recording raw touchpoints is itself an additive 1.x item, and an early one — earlier than the switch-over it serves. Start it and the warm-up runs in the background while other phases proceed; start it at cutover and it becomes a 60-day hold on the one part of v2 that cannot be hurried.

2.23Profiles carry the version Proposed

Everything above resolves the version at query time, and every automatic signal for doing so fails. A date boundary cannot work: §2.21 makes cutover per-feature so there is no single instant, dual-write means both stores hold the same period, the switch-off is an administrator's action rather than a release date, and the queue is asynchronous so an event accepted before a switch can land after it. Coverage watermarks fail for the same reason — during overlap both stores answer, and the data cannot say which is authoritative. An install-wide setting fails differently: since no data is migrated, v1 holds the history permanently (§2.24 keeps v1 reporting precisely for that), so a global flip would blank every historical report.

The proposal is to stop resolving it at query time and carry it in the data model instead. Decouple the tracked website from the profile that measures it: one website may have several profiles, and a profile declares its version. The whole experience fans out from the profile — a v2 profile shows v2 navigation, v2 reports, and queries the v2 REST endpoint. This is the path GA took to GA4. Each open question below gets a structural answer instead of a rule someone has to remember:

2.23.1What it requires Measured

site_id is md5($domain) (Site::generateSiteId(), and inline at SiteManager.php:44), so two profiles for one domain are impossible by construction. Only three call sites derive it, and just one re-derives at runtime — ServiceUser.php:283, in the permission path, which is the edge needing care and tests.

Two things are already in place. site_family exists as a column on owa_site and is written but never read anywhere — a dormant grouping slot, so “tracked website” can be defined freshly rather than migrated. And the per-site session store (owa_s_<siteId>) already gives two profiles on one domain independent session cookies, which is both correct and exactly GA's _ga_<property>.

Do not rewrite existing site_id values

Every site_id in the wild is md5(domain) and every fact row references it. The change is to stop deriving new ones and treat the column as opaque — existing identities keep their values and existing data is untouched. Decoupling identity from derivation does not require reissuing the identities already handed out.

No second tracking tag, and no second tracker, per §1.9. The tracker is extended in Phase 3, so it emits v2-rich events and the server degrades them for v1 — not v1-poor events upgraded for v2.

So the profile model requires no client change whatsoever: one tag, one event, and the server writes each received event into every profile configured for that website. The site → profiles mapping is server-side, so the page never learns that profiles exist, and §1.9's promise holds — nothing about the page changes on cutover day.

Independent of v2, md5(domain) already prevents tracking two configurations of one domain, renaming a domain without orphaning its data, and expressing one property across several domains. The decoupling is additive 1.x work with standalone value.

What the profile does not do is spare ResultSetManager. It settles where the version comes from, not how the manager acts on it, so the entity-pool change of §2.13 survives intact and is still the work: resolve the version from the profile behind siteId, filter candidate entities to that version before arsort($niceness), and error when none resolves. setSiteId() today only records a query param and a constraint rather than loading the site, so there is a little plumbing from siteId to a version — but nothing new threads through the REST API or the report configs, which is precisely what the profile model buys: an unambiguous input already present in every query.

2.23.2Nothing feeds the manager a “v2 list” Measured

A fair question is what supplies ResultSetManager with the v2 metric and dimension sets. The answer is that no new channel is needed. getMetricEntities() asks the service singleton for every registered implementation of a requested name, instantiates each, and keys it by its own entity:

$classes = $s->getMetricClasses($metric_name);   // every implementation
foreach ($classes as $map) {
    $m = metricFactory($map['class'], $map['params']);
    $this->metricObjectsByEntityMap[ $m->getEntityName() ][ $metric_name ] = $m;
}

So a v2 registration appears alongside the v1 one automatically. Dimensions behave identically — registerDimension() loops $entity_names into one entry per entity, and lookup is denormalizedDimensions[$name][$entity]. The v2 set is just more registrations carrying the v2 entity, or more config entries once §2.13 lands. This is the same reason report configs need no version field.

Which relocates the filter. Because implementations are built before anything is selected, the version filter belongs in getMetricEntities() — skip a class whose entity is the wrong version, so wrong-version objects are never constructed — rather than at the niceness sort, where they already exist. And the recursion into child metrics means filtering children constrains their calculated parents for free.

2.23.3Domain aliases stay v1-only, and narrow Decided

A Property will hold the domains of the website it describes, and the temptation is to make that list do two further jobs it should not do.

It does not widen CORS. matchAllowedOrigin() today matches a request's Origin against each site's domain and nothing else — aliases are not consulted. Feeding alternates into that allowlist would grant cross-origin API access that installs do not have today, as a side effect of moving a setting into a column. The allowlist stays exactly as wide as it is.

And the alias itself narrows to a variant of the same domain. Its documented purpose is collapsing www.mydomain.com and mydomain.com; nothing needs it to map one website onto an unrelated one, and a general redirect map is a much larger thing to reason about than the help text implies. Restricting it to same-domain variants keeps the real use case and removes the rest.

Both jobs then disappear together with v1: canonicalisation is v1-only machinery (§1.11), and CORS never depended on aliases in the first place. So the fragile parts of the current implementation — a naive substring replace, and a strpos( $url, $da ) that misses a match at position zero — want not carrying forward rather than fixing.

2.24Cutover sequence Decided

  1. Ship the additive work in 1.x releases, each standing on its own
  2. v2 creates its tables alongside; the single tracker's events fan out to both pipelines, except for features on the early-cutover list
  3. Run both for an overlap period, comparing the two UIs over the same events — which is what makes it a test rather than an impression
  4. When satisfied, switch off the fan-out to v1 and keep v1 reporting for history
  5. When the history is no longer wanted, a command drops the 20 parallel tables, leaving the shared admin tables untouched

No step is irreversible until the last one, and the last one is the administrator's decision rather than an upgrade's side effect.

AppendixEvidence and debate

A.1Why the design is what it is

The body states what v2 is. This is the evidence behind it — kept because the reason a design is not something is the most expensive thing to rediscover, and moved here because it was making the plan unreadable.

A.1.1GA: three traffic-source records

GA exposes the same three-way split as three separate records on an event row:

  • collected_traffic_source.* — manual_source, manual_medium, manual_campaign_*, gclid, dclid, srsltid. The tags as collected with the event. Evidence, not reading. Confirms what the beacon capture already showed: GA ships raw tags and never a parsed source or medium.
  • session_traffic_source_last_click.* — session scope, and its name states the model. Nested per channel (manual_campaign, google_ads_campaign, cross_channel_campaign, sa360, dv360, cm360). Derived, not collected.
  • traffic_source.name / .medium / .source — user scope, documented as “the traffic source that first acquired the user” and explicitly “do not change if the user interacts with subsequent campaigns”. Write-once acquisition, materialised onto every event row.

That also narrows the realtime claim made above, and it should be narrowed. OWA’s raw layer does hold more than GA’s — the referring URL and the campaign tags are there on every event where GA carries only per-event collected values — so realtime can report a referring host. It cannot report a resolved source, medium or channel, because those do not exist until the pass runs. Richer than GA’s realtime, but not unboundedly so, and along a line that follows from the architecture rather than from a policy.

A.1.2GA: not populated in intraday tables

GA is built this way, and its BigQuery export says so explicitly. The export carries three separate traffic-source records per event row, which is the same three-way cut arrived at above:

A.1.3GA: what is and is not observable

And the line in that documentation that settles the architecture: “This record is not populated in intraday tables.” GA’s intraday table is its raw layer and its daily table is its processed one, and user acquisition exists only in the second. That is the raw/denormalised split observed from outside GA, with the same value in the same place for the same reason — it cannot be known from the event alone, so it cannot be in the layer that is written one event at a time. geo and device, by contrast, are on every exported row including intraday, which is the ingest-time mechanical resolution above.

A.1.4Why lookup cost is not the reason

Why the store exists: retention, not lookup cost. The tempting answer is that the pass needs no table because it can join raw to raw — find the visitor’s first_visit row and read the arrival values off it. That works right up until raw is pruned. §1.5 banks on pruning raw to recover the storage doubling three layers cost; the moment the horizon passes a visitor’s first visit, their acquisition is not expensive to recover, it is gone, and every subsequent event they generate is permanently unattributable. Retaining raw forever to avoid that gives back the one mitigation the third layer had. A visitor-cardinality row survives the prune because it is not event-cardinality.

A.1.5The same test that removed the session table

So: one row per visitor, written when the first_visit event is seen, holding the arrival values. Maintained by the pass, not by ingest — the property that mattered for ITP and for keeping append pure is that the write path does no lookups, and that is untouched. Reports never join it either; it is an input to the build, and its values reach queries materialised onto event rows like everything else. It is neither owa_visitor reborn (no per-request write, no per-request read) nor a star-schema dimension (no query-time join, no FK on the fact row, so no repeat of the inner-join-drops-the-row failure §2.11 exists to prevent). Calling it a table is accurate; calling the pass stateless would not be.

A.1.6GA: why fourteen months does not bind

0.172% of visitors have an active life longer than thirteen months. Among the 6,761 visitors active in the last 90 days, the oldest first visit is 2025-10-24 — under a year, with none at all over thirteen months, while 171,642 visitors first seen more than thirteen months ago exist in the table and never return. Repeat visits plainly work at short range (120,356 visitors have exactly one prior session), so this is not broken recognition at the margin; it is recognition decaying to nothing well before the window closes. The cause is the same browser cookie physics that set the window: Chrome’s 400-day cap, Safari’s seven days, and people changing device or clearing state. The theoretical hole is closed by the same mechanism that produced the TTL.

A.1.7What follows from GA holding a user record

GA is worth being precise about here, because its fourteen months do not bind the way the number suggests. With “reset user data on new activity” the window slides on every event, so a user who returns at least once inside it never expires — and first-user attribution rides with the identity rather than being stored beside it. Someone acquired via organic search stays organic on the first-user dimensions forever, unchanged by any later campaign, for exactly as long as the identity survives. What ends it is documented as the identity being lost — cookie expiry, a new device, Safari’s caps — not the retention setting.

A.1.8Who the 0.172% are

The measured share pulls in two directions at once, and both are worth stating. GA must therefore hold acquisition on a user record and cannot be deriving it from its own retained events, since those live 2 or 14 months while attribution persists indefinitely for an active user. The store described above is real and GA has one. But GA has it because GA supports the case, and our own data says the case barely occurs: with Chrome capping any first-party cookie at 400 days, even GA’s “forever” is about thirteen months in the dominant browser, which is where the TTL landed anyway. The architecture differs; the reachable outcome does not, by much.

A.1.9Why reprocess cadence is bounded by the partition scheme

A swap replaces a whole partition, so the partition is the unit of work. 1.x partitions fact tables monthly for partition_detail_months (default 36) and then merges into blocks of up to partition_max_years_per_block (default 5), bounded by the server's open-file budget — each partition is a file. Carried over unchanged, rebuilding “today” would mean rebuilding the whole month: on the 31st every intraday pass rewrites 31 days, and the job's cost grows through the month for no benefit.
So the denormalised table wants a daily tier at the front — daily while a day is still being rebuilt, merged to monthly once it is final, and into year blocks later. That is three tiers and two merge steps rather than one, each merge a REORGANIZE that rewrites rows, but each bounded: one day's worth daily, one month's worth monthly.
Which gives the late-arrival window a concrete meaning rather than a policy: it is the point at which a day's partition stops being rebuilt and is merged. An event landing after that is outside the window by definition. Setting that number sets the reprocess cost, the freshness, and the merge schedule together — it is the one dial worth getting right.
The raw table needs none of this. If raw is pruned at a retention horizon rather than compacted, it only ever needs DROP PARTITION — free on MySQL and on columnar — so it can stay daily throughout and never pay a merge at all. Tiering exists to serve query efficiency, and nothing queries raw except realtime, which wants the recent end.

A.1.10The rebuild-and-swap idiom ports to columnar stores

The pass rebuilds a partition and swaps it into place, and that idiom is not a MySQL trick that has to be abandoned if the reporting store changes. Both tables key on yyyymmdd; rebuild one partition and swap it. MySQL has ALTER TABLE … EXCHANGE PARTITION; ClickHouse has ALTER TABLE dest REPLACE PARTITION p FROM staging, which is atomic and exists precisely for zero-downtime reloading — stronger than MySQL's, not weaker. Delta Lake's replaceWhere is looser still: selective overwrite by arbitrary predicate, with no requirement that the table be partitioned on those columns. (Iceberg unchecked; BigQuery's truncate-then-load pattern is established but its mechanics were not verified.) So the rebuild-and-swap idiom is not a MySQL trick abandoned at the columnar boundary — it is the native idiom on the other side.
Staging must mirror the target, on both engines. Both MySQL and ClickHouse require the staging table to mirror the target — same structure, partition key, ordering and primary key — so staging carries no convenience columns and a schema change must alter both in step. MySQL additionally refuses the exchange where foreign keys are involved, which the denormalised table would not have.
DROP PARTITION is metadata only; REORGANIZE rewrites every row it touches. 1.x already relies on this in production: PartitionRotateCli notes that “drops are not counted at all: DROP PARTITION discards a file and returns”, while extending the lead or merging is a REORGANIZE that rewrites rows. Columnar stores are the same shape only more so — the partition is the storage unit, so a drop unlinks files rather than scanning. Retention is therefore cheap on both; what is expensive on both is updating rows, which is what this design avoids.

A.1.11What the report work left on v2

Phase 4's report-config item asked for a widget format retrofitted into v1. What shipped (#1044, #1047, #1048) also made that format user-authored, which hands v2 one constraint and one asset. The constraint: rows in owa_custom_report are documents written by people, so the format is a compatibility surface now, and the narrowing that made authoring safe — fixed renderer, formatters chosen by name, excludeColumns as names rather than script — is load-bearing rather than stylistic. The asset: every metric, dimension and sort in an authored definition already resolves through the registry at save time and again at render time, because the registry changes under a saved report. That is the explicit enforcement §1.10 says v2 will need once a single table stops refusing non-additive combinations on its own. It was written to validate authored reports; it turns out to be the seam v2 needs for a different reason.

A.1.12Why msec is not fixed in 1.x

owa_request.msec is declared INT and fed the fractional part of microtime() as a string, so MySQL rounds it: the column holds 0 or 1 and nothing else (597 and 560 on the test install). Request ids cannot stand in — they are the tracker's random GUID, unique but unordered — so the 1.x fact table has no sub-second ordering at all. Fixing it in 1.x would be worse than leaving it: existing rows stay 0/1, so old and new rows would order differently inside one report, and a funnel spanning the cutover would be wrong in a way nobody could see. VisualizationFunnel::walk() resolves same-second events as a set rather than comparing them, and the two tests pinning that assumption should be retired when v2 lands, not re-baselined.

A.1.14Why v1’s history cannot size the session change

And v1's history cannot size it

owa_request does carry per-request medium, source_id and campaign_id, so the question looks answerable. It is not: setTrafficAttribution() stamps the decided, session-sticky result rather than the observation that produced it, so a mid-session tag change is collapsed before it is stored. A measurement on this install returns 0.246%, which is an artefact of that collapsing rather than a rate.

This is the same limitation §2.22 records for validating the attribution model — existing history is not a usable touchpoint log.

Not treated as a blocker. The expectation is that the effect is small: it requires a visitor to re-enter through a second tagged link inside the timeout, which is uncommon outside heavy paid-campaign traffic. If a number is wanted later, touchpoint data supplies it; nothing waits on it.

Touchpoint recording earns its place on data quality, not on this. Attribution is decided in the browser today — setTrafficAttribution() reads the owa_c cookie's attribs stack, applies the model, and the event carries the verdict rather than the observation that produced it. So the server stores a conclusion it cannot check, and four things follow:

  • A client-side verdict cannot be corrected later. Fix the attribution logic and every row already written keeps the old verdict — there is nothing to recompute from.
  • Attribution dies with the cookie. Clearing owa_c destroys the stack, and the visitor's history is gone rather than re-derivable.
  • The 60-day original window is measured on the client's clock, which is unverifiable and, on a skewed device, wrong.
  • No post-hoc enrichment. This research measured the star's one real advantage as rewriting a dimension without touching facts (589×); attribution is precisely the dimension worth rewriting, and today it is the one that cannot be.

Recording the touchpoints makes attribution derived rather than reported: recomputable, correctable, and independent of whether a cookie survived. That is the reason to do it early, and it stands whether or not the session step is ever quantified.

A.1.19Why a page carries no identity hash

An earlier draft called the column page_uri and gave a page an identity, hash(site_id + uri). A hash has to commit to its input before anyone asks a question, which forced a decision about whether the query string was part of a page's identity — and neither literal answer was any good. Keep the query in the hash and every campaign-tagged arrival becomes a distinct page, fragmenting the landing-page report into one row per tag combination. Drop it and the campaign evidence is gone from raw entirely. Storing the complete URL and deriving the path readings at read time is what GA does, and it defers the question to the reader who is actually asking it.

The marker's event id is content-derived — hash(site_id + session_id + 'session_start') — so racing writers produce the same row and the second insert is a duplicate-key no-op. No coordination is needed, and it holds across subdomains, where the Web Locks API is origin-scoped and could not reach.

A.1.24Why a dimension names a shape instead of carrying SQL

The tempting shortcut is to let each computed dimension carry its own SQL. That works until the reporting store is not MySQL — and §2.1 deliberately holds that door open behind a second DSN. Then a store move rewrites every derived dimension by hand.

The dialect layer does not cover this today. MysqlDialect abstracts DDL and introspection — partitioning, keys, indexes, session sql_mode — and has no expression surface, nor an interface a second implementation could satisfy.

Declaring a shape is cheap rather than a mini-language only because the column-admission rule keeps the set closed. Once dimensions carry SQL strings instead, converting them means recovering intent from expressions — which is exactly where the report controllers were before they became configuration, and the narrowing that made that safe was the same move: names from a known list, never code (§1.7).

A.1.25What bounds the late-arrival window, and what does not

1.x has two queues, and they are not the same mechanism:

  • The incoming queue is a file. Tracking events are written to disk and processed later. Every event goes through it when it is enabled, and what it costs the window is simply drain cadence — a configured number, not a thing to measure.
  • The DB queue (owa_queue_item) is a retry queue, and it is the one with unbounded tails. An event reaches it on EVENT_FAILED, and the case that actually puts it there is a session-update event that cannot find its session — SessionHandlers aborts with “no existing session was found”, and SessionCommerceSummaryHandlers with “Session does not exist yet”.

That entire class of failure does not exist in v2. There is no session row to look for: session-scoped values ride every event and the event table is the session-grain table (§1.3). An event that would have been re-queued in 1.x is, in v2, just a row. So the retry queue’s reorder behaviour describes a failure mode v2 deletes, and sizing the window against it would be sizing against the wrong thing — conservatively, but wrong, which is more damaging than it appears when the number sets the whole rebuild cadence.

What is left to bound is therefore drain cadence plus client-side lateness: an unload beacon that landed behind a subsequent hit, a retry from the browser, a tab restored from bfcache, a device that was offline. None of that is visible in any server queue, which is the part that still needs a number.

A.2.3Superseded: partition by version

Refinement of §2.23. Partitioning by version works but spreads a version concept through every accessor, and concepts like that leak until they are everywhere. Keying off the entity achieves the same isolation using something already present in every registration and already understood across the codebase: a profile determines a candidate entity set, the accessors scope to it, and the word “version” survives only in the profile record and the migration machinery — which is the one place generational schema changes are actually relevant.

It is still a single choke point rather than scattered filtering: every consumer goes through the accessor, so there is one place to be right instead of ten. And it improves the API independently of v2 — getAllMetrics() today returns everything regardless of whether it is queryable in the current context, so an entity-scoped picker is more correct even with one generation.

Superseded: partition by version Measured

Kept for the measurement, which still stands; the entity-scoped approach of §2.23 is preferred.

That section originally proposed registering the v2 set into the existing registry and discriminating downstream — a filter in getMetricEntities(). That is wrong, and the reason is enumeration rather than resolution. getAllMetrics() and getAllDimensions() return the flat, name-keyed map, and they are consumed in ten places:

The picker is built from array_keys( getAllMetrics() ). Array keys are unique, so with both sets registered it offers one visits that silently means two different things, and the validation loops beside it are equally version-blind. Selection never gets the chance to be wrong, because the wrong definition was already offered and accepted as valid. A filter at one consumer fixes one consumer.

So partition at the aggregation points instead. There are exactly two, and they are the only places module registries merge into the service:

_loadMetrics()    : $this->metrics    = array_merge_recursive( $this->metrics, $module->metrics );
_loadDimensions() : $this->dimensions = array_merge( $this->dimensions, $module->dimensions );

Group by version there rather than flattening, and resolve accessors within a version. Nothing downstream filters anything, because the other version is not in scope: the picker lists one version's names with no change to CustomReportEdit, validation follows automatically, ResultSetManager needs no niceness-sort filter, and the name-collision blocker below dissolves — separate partitions cannot overwrite one another, so keying $this->dimensions by entity may prove unnecessary.

The distinction is scoping the registry once versus remembering to discriminate at ten consumers. Open: the service is a boot-time singleton, built before a query knows its profile, so either every accessor takes a version or the version becomes request-scoped ambient state. The explicit parameter is safer — ten call sites is tractable, and it keeps the version visible at each consumer rather than hidden in ambient state, the same silent-wrong-answer failure.

BLOCKER: the normalized dimension registry is name-keyed, so v2 would overwrite v1

The claim in §2.23 that dimensions behave like metrics is only true for denormalized ones. registerDimension() loops $entity_names but writes to two different shapes:

if ($denormalized) {
    $this->denormalizedDimensions[$dim_name][$entity] = $dim;   // entity-keyed
} else {
    $this->dimensions[$dim_name] = $dim;                        // NAME-keyed — last write wins
}

Measured of 103 registrations: 58 denormalized (safe), 41 normalized against a single entity (the overwrite is a no-op), and 3 normalized against all seven $fact_table_entities — month, userName, priorVisitCount.

This blocks v2 for all 44 normalized dimensions. v1 registers pageTitle against its dimension table, v2 registers pageTitle against the event table, and the second write replaces the first — the v1 definition is gone from the registry before any entity filter could run. No downstream selection can recover it, and renaming is not an option.

Fix: key $this->dimensions by entity, matching denormalizedDimensions, which already has the right shape. getDimension() has exactly one caller (ResultSetManager:970), so the change is that call site plus the registration loop. This is a prerequisite in 1.x: the registry must be able to hold two definitions under one name before a second set can exist at all.

Unverified, worth a trace: the 3 normalized multi-entity registrations keep only the last of seven entities, and $dim['entity'] then drives the JOIN (entityFactory(), getForeignKeyColumn(), $db->join()). date is registered against the same list with denormalized = true while month beside it is not, which looks like an oversight rather than a distinction. Not claimed as a live defect until traced.

Do not add the v2 entity to $fact_table_entities

Dimensions are registered against a shared array: registerDimension('date', $fact_table_entities, 'yyyymmdd', …). Appending the v2 entity to that one variable would make every dimension claim to work on v2 while still naming v1's columns — a one-line change producing broadly wrong SQL, and the obvious-looking way to “add v2 support”. v2 needs its own registrations with its own columns, exactly as metrics do.

Open: the vocabulary (site / profile / property / site_family) wants settling before anything is built, since it will surface in the UI, the API and the schema at once.
