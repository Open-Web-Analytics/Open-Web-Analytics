Every event, every column, and who fills it

For each event owa_event will carry: the properties it persists, whether the tracker or the server sets them, and — for the server's share — whether the value must be captured while the HTTP request is still open or can wait for the drain.

28 Aug 2026Companion to PLAN.html §1.4, §1.10 Branch research/v2-single-fact-table

PLAN.html settles what v2 stores: a 40-column event table (§1.10) and a GA4-shaped taxonomy (§1.4). It does not settle when each column acquires its value, and that question decides which deployment topologies are possible. An installation that queues events — or runs a logging node with no database at all — can only defer work that is still doable later. Everything else has to happen while the request is open, because the request is where it lives.

CLIENT Arrives in the beacon. The server's only jobs are validation and storage. A Irreducible. Reads the HTTP request itself. When the response is sent the value is gone forever, so no topology can defer it. A* Defined, and empty. “In the request by policy” had one instance — geolocation, held there because anonymisation was about to destroy its input. §7.1 moved both to the drain, and the category emptied. Kept in the legend because the question it asks is the right one to ask of anything added later. B Deferrable. A pure function of values already captured. Safe to compute at the drain. by INSERT A second, independent axis. Some deferrable values still cannot be left NULL and filled in afterwards — they must be resolved by the time the row is written. This is not a reason to compute them during the request, because in a queued topology the insert happens at the drain too.

Corrected 28 Aug

An earlier version of this page marked id, yyyymmdd and is_key_event as request-time work. That was wrong, and wrong in an instructive way: it confused must exist at insert with must be captured during the request. Those are the same moment only when there is no queue. All three are B.

Part One

The boundary

What dies with the request, and what merely looks like it does.

1.1Three things make a value irreducible

After two rounds of checking this page against its own definition, one reason survives. Both others were struck: one confused at insert with during the request, the other dissolved once §7.1 ordered geolocation and masking. What is left is physics, and it is a short list.

  • It is the request. The connection's IP, the User-Agent, Host and Accept-Language headers, and the server's clock at receipt. Nothing reconstructs these afterwards.
  • (Struck.) This list used to include “the row cannot be written without it”, naming id and yyyymmdd. That is a real constraint but not this one: it says those values must exist at insert, and in a queued topology the insert happens at the drain. Both are pure functions of things already captured (ts, session_id), so both are deferrable. They are marked by INSERT instead.
  • (Also struck.) “A destructive step is about to remove the input” had exactly one instance — geolocation, ahead of IP masking. §7.1 moves both to the drain and orders them, so the destructive step no longer forces anything into the request. It was still the right question: answering it is what moved the work.

The clock is the one people get wrong. §1.10 already pins it: ts is stamped once at edge receipt and travels with the queue item. A queue that timestamps at drain would date every event to whenever the worker happened to run, and at-least-once redelivery would give the same event two different times. 1.x learned this the hard way in the other direction — last_req is a client clock that gets subtracted from a server clock, and the schema records no provenance for either.

1.2What deferral actually buys

The expensive request-time work in 1.x is not the insert. It is user-agent parsing, geolocation lookup and attribution resolution — three operations that touch external data and together dominate the handler. All three are B by nature. That is the whole prize: a logging node that captures the request and defers those three does almost no work per beacon, which is what makes a static-config-only node viable at all.

Part Two

Where 1.x already draws it

The classification exists in the code. v2 inherits the boundary, not just the idea.

2.1The existing three-way split

Core/Module.php::registerTrackingProperties() classifies every tracking property as one of three kinds, in these words:

1.x classIts own definitionCountv2 equivalent
environmental“dependent on the PHP SERVER environment”7A — the request
regular“set by clients”19CLIENT
derived“derived from or dependent on other properties”34B, mostly

The environmental seven are REMOTE_HOST, HTTP_USER_AGENT, HTTP_HOST, language, ip_address, timestamp and microtime — which is the irreducible set, arrived at independently and years earlier.

2.2And it already sequences them correctly

CoreAPI::logEvent() runs in this order, and the order is the specification:

setTrackerProperties( $event, $environmentals );   // A — stamp the request
if ( $event->get('do_not_log') ) return false;
$bcap->robotCheck();                               // A* — refuse bots at ingest
isIpAddressExcluded( $event->get('ip_address') );   // A* — needs the IP
isSiteRegistered( $site_id );                      // A* — needs the app store

if ( queue_events ) $q->sendMessage( $event );      // ← everything after here is B
else                performAction( $processor );    //   the 34 derived properties

Environmentals are stamped before the queue and travel with the message; the derived properties are computed by the processor, which is exactly what the queue defers. So v2 does not need to invent this boundary; it needs to keep it.

What is worth being explicit about is the three checks 1.x puts on the request side — bot refusal, IP exclusion, site validation. None of them is irreducible. Each needs configuration rather than the request, so each can move to the drain in a topology where the edge has no store; what they buy by running early is queue volume, not correctness. A bot refused at the drain still never becomes a row, because §1.9's ban is on reclassifying stored rows and a queued message is not one.

Part Three

Every property, by stage

One list. What sends it, when, and whether it survives into the table.

Seventy-nine properties move through the v2 pipeline; fifty-six persist and twenty-three do not. A fourth block follows them: the twenty-four 1.x properties v2 does not carry at all, which for a migration is the half that decides whether anything is being lost. Listing only the columns would record the survivors and lose every decision that produced them — a control flag replaced by a derivation, a URL narrowed to a URI, a client clock refused in favour of the server's. So this is one table, ordered by the stage that sets each value, with persistence as a column rather than as a separate section.

Read not stored as a deliberate outcome, never an oversight: each one is either an input that has been transformed, a control flag that has done its job, or a field v2 declines to keep. The In 1.x column separates what already exists from what v2 introduces — seven properties are genuinely new and seven more exist under a different name, so the collection surface is far closer to today's than the schema change suggests. Stage 0 at the foot of the table is the other direction: everything 1.x registers that v2 drops, grouped by why. Nothing there is lost by accident — the date parts and the dimension FKs alone account for twenty-one of the twenty-four, and both are the single table's entire point.

Part Five

The two events with no client half

Where the tracker column is empty for every row.

session_start and first_visit are server-materialized (§1.4): no beacon, zero wire cost. The server recognises new-session or fresh-fsts state on an incoming page_view and writes a second row beside it. So every one of their columns is server-set — copied from the triggering request, or derived from it.

Aspectsession_startfirst_visit
TriggerA page_view whose state says new session / prior_sessions = 0
idhash(site_id + session_id + event_type) — content-derived
yyyymmddFrom session_id, never from ts — the midnight rule
CarriesSession-scoped attributionUser-scoped acquisition
PhaseB — materializable at the drain, since every input is on the queued page_view

Racing tabs cost nothing. Because the id is content-derived, two tabs starting the same session produce the same row and the second insert is a duplicate-key no-op — no coordination, and it works across subdomains where the origin-scoped Web Locks API cannot reach. This is also why a negative breakdown remainder is a pure defect signal rather than an expected artefact: duplicates are structurally impossible, so the count can only go one way.

They are emitted for grain, never counted from. §1.4 is emphatic: session totals come from the rollup, so a lost marker degrades that session's attribution and erases nothing.

Part Six

What each topology can defer

The boundary is not one line. It moves with what the node can reach.

Splitting A from A* pays off here. The irreducible set is fixed; the policy set moves depending on what the receiving node has access to. Three topologies, in increasing order of how little the edge does:

Topology 1Inline

No queue. The request does everything, as 1.x does with queue_events off.

  • Every column resolved before the response. Simplest, and the slowest per beacon — measured at 79 events/s in 1.x against v2's 202 for the insert alone.
Topology 2Queued, application store reachable

The default deferred shape. The node can read config and goals.

  • Request does: A and nothing it does not have to. The three checks — bot refusal, IP exclusion, site validation — run here by preference, to keep junk out of the queue.
  • Drain does: everything else. UA parse, geolocation then IP masking (§7.1), attribution, page_uri, id, yyyymmdd, is_key_event, and materializes session_start / first_visit.
  • This is the shape the fan-out argument in §3.1 assumes: “an argument for the queue carrying the fan-out rather than the request doing it inline.”
Topology 3Logging node, no database

A file-queue collector. 1.x has this today as OWA_USE_STATIC_CONFIG_ONLY, which skips both boot queries.

  • Request does: A only. It cannot validate the site, cannot read the goal config, cannot consult a stored exclusion list.
  • So all three checks move to the drain. Geolocation is already there (§7.1), so this topology costs nothing extra for it — the incidental win of that decision. Nothing breaks: a bot refused at the drain still never becomes a row, since §1.9's ban is on reclassifying stored rows and a queued message is not one.
  • The real limit is further along. If the drain also lacks the application store, key events cannot be stamped at all and the site check never runs — so a database-less collector is fine, but a database-less pipeline is not. See §7.2.

Part Seven

What this exposes

Four questions the plan has not answered, found by asking when rather than what.

7.1Geolocation and anonymisation both happen at the drain Decided

§1.8 anonymises the IP by default; §1.10 derives country and city from it. This section used to ask which runs first, because the answer decides whether geolocation can be deferred at all. It is settled: both move to the drain, in that order, and the insert follows them.

#WhereStep
1A receiptRead the connection address through X-Forwarded-For. Irreducible — it is the request.
2—The full address travels on the queue message.
3B drainGeolocate from the full address → country, city.
4B drainMask it. Lib::anonymizeIp() is a bitwise AND: /24 for IPv4, /64 for IPv6.
5by INSERTWrite the row. The masked value is the one stored.

The guarantee this buys: the table never holds a full address, not even briefly, because masking happens before the insert rather than as a later UPDATE. And because masking is a bitwise AND it is idempotent, so a redelivered message that is masked twice produces the same value — the property every other deferred step in this spec already relies on.

The cost, stated plainly: the full address now sits in the queue. That is the one place it lives outside a request, and it is the place data waits longest. Three things follow and should be treated as part of this decision rather than discovered later: queue storage is sensitive storage and a file queue means plaintext addresses on disk; the erasure command (§1.8) has to reach queued messages as well as rows and payloads, or it misses the least protected copy; and queue retention becomes a privacy parameter, not just an operational one.

Worth knowing, since masking is truncation rather than a hash: a /24 is still geo-locatable — country essentially exactly, city usually — so anonymising at receipt and geolocating from the masked value afterwards is a real alternative, and the only one that keeps a full address out of the queue entirely. It costs some city precision. Recorded because the choice is now an ordering preference with a known trade, not a constraint.

7.2The drain needs the application store Open

§1.10 establishes that no reporting query ever joins an application table, and that key events are stamped so the goal config is never consulted at read time. Goals live in the application store; events live in the reporting store.

That constraint is about the reporting boundary, not about the request. The drain can stamp is_key_event perfectly well — it simply has to reach the goal config while it does. In Topology 2 it does. In Topology 3 the edge cannot, and if the drain is a different process with the same limitation, nothing can.

So the question is narrower than it first looked, and worth stating as a supported-configuration rule rather than leaving to be discovered: an installation that uses goals needs a drain with application-store access. A database-less collector is fine; a database-less pipeline is not, and the same holds for the site-existence check and any stored IP exclusion list.

7.3Sticky attribution needs no state — 1.x already shows how Resolved

This section used to ask how a deferred pipeline arrives at sticky attribution consistently, given that a drain sees arrival order and retries reorder freely. The answer was already in the 1.x code, and it is better than the options previously listed here.

The tracker keeps the referer that started the session in the session store and sends it on every event as session_referer — distinct from referer_url, which is the current page’s. The server’s derivation reads that, not the session's first row. The property registrations say so explicitly: source, medium and search_terms each carry a derive callback and each is preceded by the comment // must come after session_referer.

B Every event carries the same session-originating input, so the resolver is a pure function of one event. Two events of one session resolve to the same answer because they were handed the same input — not because the second consulted the first.

That makes deferred attribution stateless, order-independent and idempotent: no session state at the drain, no ordering requirement within a batch, no backfill pass, and a retry produces the same row. It is the same property the content-derived ids give the marker events, arrived at the same way — put the input on the message rather than in the processor.

What v2 must add. The rule only holds for inputs the client carries. Today session_referer is carried but the session’s originating campaign parameters are not — the tracker sends the current page's tags. Under §7.5's rename the tagged_* values must therefore be the ones the session STARTED with, held in the session store beside the referer, or a campaign-tagged session falls back to needing state after all. That is a tracker change, and it is the price of keeping the resolver pure.

7.4Two meanings on one search_terms column Open

§1.10 lists search_terms among the attribution columns (14–18): the terms someone searched before arriving, derived server-side from the referer. §1.4 also has view_search_results and search — site-internal search, supplied by the tracker, describing what someone looked for while here.

These are different facts with opposite provenance sharing one name. Storing both in column 18 makes “top search terms” silently blend acquisition with on-site behaviour. Either the internal-search term belongs in params, or it earns its own column — but the collision should be resolved before either is built, because separating them afterwards means rewriting rows.

7.5Attribution: name the claim apart from the answer Proposed

In 1.x the tracker parses the landing URL and puts source, medium, campaign and search_terms on the wire — registered regular, “set by clients”. The server also derives them, from the referer, when the tracker did not send them. So both halves already write the same five names, and which one you are looking at is not recorded anywhere.

That is the confusion to remove, and renaming the tracker's half removes it. The tracker is not answering “what is the source”; it is reporting what the landing URL was tagged with. Naming it for that makes the whole chain expressible:

StageNameSet byMeans

The precedence is the ordinary one — an explicit tag wins, else classify the referer, else direct, then stay sticky for the rest of the session. What today's schema loses is which of those fired, and that is a question people genuinely ask: how much traffic is attributed because it was tagged, versus because we guessed from a referer? Today it cannot be answered at all. attribution_basis is scalar and release-known, so it satisfies the column-admission rule in §1.10 rather than needing params.

Open within this: whether the tagged_* values are persisted as well as the answer. They are redundant whenever attribution_basis = tagged, which is the only case they exist for — so the cheap option is to keep the basis column and drop the claims after resolution, and the expensive one is five mostly-NULL columns that let you audit the resolver against its own inputs. The claims could also ride params only when the resolver overrode them, which is the case worth being able to see.

Two consequences of the move survive whatever is decided about storage. A server computing attribution from scratch has no sliding 60-day window until it has been collecting for sixty days, so a migration cannot switch this on and expect matching numbers on day one. And the tracker keeps sending campaign parameters as long as the snippet is deployed — under the rename that is fine, because tagged_source arriving is no longer indistinguishable from source having been decided.

7.5bAcquisition is carried, not reconstructed Decided

A visitor's first source, medium and campaign are now three columns of their own, written once into the visitor cookie at first session and stamped on every event thereafter — the same permanence visitor_id and fsts already have in the v store.

Today they are mutually exclusive with the current touch, and that is the problem. 1.x keeps a campaign array in the c store (registered for 60 days) and originalAttributionModel() returns campaignState[0] — the oldest entry — in place of the current campaign. So source, medium and campaign carry first-touch or last-touch depending on a configured model, never both, and the row does not record which. Choosing an attribution model is therefore a collection-time decision that destroys the alternative: switching it later cannot be applied to data already collected, which §1.9 rules out anyway.

Carrying acquisition separately makes it a reporting choice instead of a collection one. It also removes the migration warm-up §7.5 warns about for this half: a server deriving acquisition from a sliding window needs sixty days of history first, while a value the visitor cookie has been holding all along is available on the very first event after upgrade.

Stamped on every event rather than left on the first_visit row for the reason §1.4 gives for session-scoped values: it turns “revenue by acquisition source” into a group-by instead of a join to each visitor's first row — the same shape that measured 215 ms against 3.1 s for sessions by landing page.

7.5cThe campaign cookie goes away Decided

1.x keeps a third cookie, c, holding an array of prior campaigns under the key attribs. The tracker ships that array on the wire, the server stores it as latest_attributions on the session row, and it surfaces as the latestAttributions dimension behind the Attribution History report. v2 does not need it, and both of its jobs are better done elsewhere.

  • First touch moves into the visitor cookie as first_source / first_medium / first_campaign (§7.5b). It has to be carried rather than derived, because retention can delete the events that would otherwise be the only evidence of a visitor's first session.
  • The history in between is derivable, and this is where the single table pays. Every v2 event carries its own session's attribution, so a visitor's campaign sequence is a group-by over their own events. 1.x cannot do that — attribution lives only on the session row, so reconstructing a sequence means joining sessions, which is exactly why the client cached it in a cookie in the first place.

So c goes, and attribs goes with it: one fewer cookie, one fewer wire field, one fewer stored blob, and no maxPriorCampaigns cap silently truncating the history at the client.

The bound changes rather than disappearing. Today the history is bounded by maxPriorCampaigns and by the cookie surviving; in v2 it is bounded by event retention. Neither is unlimited, and the Attribution History report should say which bound it is showing rather than implying completeness.

7.6Billing address versus geolocation Open

The same shape as §7.4, found the same way. ecommerce.transaction sends city, country and state — the billing address, supplied by the site. Columns 23 and 24 are country and city derived from the IP. Two of those three names collide, and state has no column at all.

A purchase row would then carry either the buyer's billing city or the network's geolocated city depending on which writer ran last, and nothing in the schema records which one it is. The fix is the same as §7.4 — billing belongs in params with the rest of the commerce detail, or in columns of its own — and the reason to settle it now is also the same: separating them afterwards means rewriting rows.

7.7Named dimensions, not is_* columns Decided

1.x answers “new or returning?” with a boolean column. That is a chain of four problems, and each link was paid for separately:

  1. A boolean column holds three values — 1, 0 and NULL each group separately in SQL — so the dimension has three buckets, not two.
  2. Raw, those buckets read as 1, 0 and empty, so the type needs a formatter to render Yes/No.
  3. Yes/No is the wrong vocabulary for the question, so each report needs a valueLabels map to say New/Repeat.
  4. And a map that folds two values onto one name still leaves two rows, so the chart has to fold slices too — which it did not, and drew “New” twice on a live install.

v2 exposes newVsReturning instead, a derived dimension whose values are new and returning. Two values, named at the source, no NULL bucket, no formatter, no per-report relabelling, nothing for a renderer to fold. It groups and charts directly.

B newVsReturning = prior_sessions == 0 ? 'new' : 'returning', derived at query time from a stored column that rides every event type.

That last point is why the flag could never have done this job. is_new_visitor is sent on the page_request family and not on clicks, actions or transactions — so “was this purchase from a new visitor?” has no answer today. prior_sessions is on all seven event types, so the derived dimension answers everywhere the flag cannot. The plan already assumes this shape: §1.4 describes first_visit as materialized from “fresh fsts, prior_sessions=0”.

GA does the same thing, which is worth knowing before inventing: GA4 exposes newVsReturning with values new and returning (UA called it User Type, New/Returning Visitor). Its wire protocol carries one-shot markers — first-visit and session-start — and derives the every-event dimension server-side, rather than sending a per-event new-versus-returning flag.

The rule this generalises to

Prefer a derived dimension with named values over a stored boolean, wherever the question has a natural vocabulary. 1.x carries five is_* dimensions — is_repeat_visitor, is_new_visitor, is_browser, is_robot, is_entry_page — and every one pays the same tax. §1.12 keeps valueLabels for the cases where a boolean genuinely is the shape; this decision is about not reaching for that shape by default.

What the four new-ness flags become

7.8Two clock domains, and nothing crosses between them Decided

Six time values ride the wire or land in a column, which invites the question of how many are really needed. Asking “which of these are clocks?” turns out to be the wrong cut. The one that matters is where the subtraction happens.

SERVER Ordering and partitioning. ts, stamped at receipt, and yyyymmdd derived from it. Answers when did this happen and how fresh is this. CLIENT Elapsed time. Anchors (fsts, sts) and durations (engagement_msec). Answers how long since — and answers it entirely among themselves.

The rule: a value from one domain is never differenced against a value from the other. That is what makes the client's clock being wrong not matter. Days-since is computed from fsts against sts, both client, so skew cancels; engagement_msec is a difference between two readings of the same client clock taken before it is sent, so skew cancels there too. Only rate error survives either, and that is negligible.

stsclientanchorKept, same reasoning. Recoverable from session_id; sent explicitly instead.

So the rationalisation is two removals, not five. The client clocks are not clutter; they are a deliberate second domain that keeps offset arithmetic away from a clock the client cannot see. What was wrong was one value crossing between them, and one value existing only as a fallback for another.

Why this is worth a rule rather than a fix. 1.x got the domains right almost everywhere — deriveDaysSinceFirstSession() reads fsts against the session's own date, and sessionDateOf() falls back to the client's timestamp, keeping both sides client-side. That is careful work, and it is invisible: nothing in the schema says which column came from which clock, so the one place that crosses looks exactly like the places that do not. Stating the domains is what makes the next addition checkable.

7.9Actions and custom variables are not ported — they are replaced Decided

1.x has two separate mechanisms for “things the site wants to record that OWA does not know about in advance”, and both are fixed-shape:

  • Actions — track.action, carrying action_name, action_group, action_label and numeric_value. The UA event schema: category, action, label, value.
  • Custom variables — cv1, cv2, cv3 on the wire, landing in ten session columns (cv1_name…cv5_value) that implement exactly five slots.

v2 has one mechanism and no slots. A custom event is its name plus a parameter map — event_type carries the name, params carries whatever the site wants to say, under keys the site chooses. So neither 1.x mechanism is ported: each is replaced by something more general, and their wire fields have no v2 counterpart.

1.xv2
action_nameThe event’s own event_type. A custom event is its name; there is nothing separate to send.
action_group, action_label, numeric_valueOrdinary params keys, named by the site. Three fixed names become however many the site needs, called whatever it calls them.
cv1 – cv5Ordinary params keys. The numbers go away with the slots.

Why the slots existed is the point. §1.10 is explicit that five was never a design preference — it is what a fixed-width session row forces. Ten columns buy five name/value pairs, and a sixth would cost two more columns and a schema migration on every install. A JSON map removes the ceiling, which is what makes unregistered custom-variable segmentation possible at all.

The commerce fields are a different case and stay in the v2 pipeline: ct_order_id, ct_tax, ct_shipping and the rest map onto GA4’s recommended commerce parameter names. Those are fields being relocated into params, not a mechanism being retired — the distinction being whether the name is known at release time.

7.10A campaign change is a session boundary Decided

§7.5 puts the session’s originating campaign tags in the session store so the resolver stays stateless. That only works if the value never changes mid-session — which is the session-scope contract the tracker already states: identical on every event sharing a session_id, a divergence being a regression, enforced by SessionScopedInvariant.test.js.

So what happens when someone with an active session clicks a newsletter link and lands on ?utm_source=newsletter? Writing the new tag breaks the invariant. Ignoring it means the newsletter never gets credit for the visit it caused. Neither is acceptable, so the sessionization rule changes instead.

RULE A new session starts on timeout OR campaign change. 1.x sessionizes on timeout alone — isNewSession() is timestamp - last_req >= sessionLength and nothing else. Campaign parameters play no part in it today.

This is what GA does, and it preserves the invariant rather than carving an exception into it: session-scoped values may never change within a session, so when attribution must change, a new session is started to hold it. Each campaign owns the session it created.

What counts as a change

A tag that differs from the session’s stored one — not a tag that is merely present. The distinction is load-bearing, and 1.x gets it wrong for this purpose: getCampaignProperties() sets isNewCampaign the moment any campaign parameter appears on the URL — “anytime we see a campaign param on the URL its a new campaign”. That is fine for choosing an attribution model and wrong for deciding a session boundary, because the tag stays in the address bar: a refresh, a back-navigation, or any in-page link that preserves the query string would start a fresh session every time.

StoredIncomingResult
(none)utm_source=newsletterNew session. Direct traffic acquiring a campaign mid-visit.
newsletterutm_source=adsNew session. A different campaign.
newsletterutm_source=newsletterSame session. A refresh or re-navigation with the tag still in the URL.
newsletter(none)Same session. Attribution is sticky; an untagged page later in the visit does not un-attribute it.

Restarting gracefully

The rotation has an ordering trap, and it is the reason “gracefully” is the right word. Engagement accrued on the previous page belongs to the previous session. engagement_msec rides the next outgoing event, so if the session id rotates first, that residue is attributed to the new session and inflates it — while the session that actually earned the time loses it. The sequence has to be:

  1. Settle the outgoing session first. Flush or attribute the pending engagement residue and any pending one-shot flags against the old session_id.
  2. Close it. The old id becomes prior_session_id — 1.x already carries that, and already reports it for the life of the successor session.
  3. Mint the new session. New session_id, new sts, and the new tagged_* written into a fresh session store. Visitor-scoped state is untouched: visitor_id, fsts and the acquisition triple (§7.5b) all survive, and prior_sessions increments.
  4. Let the marker follow. is_new_session_start fires for the new session, materializing a session_start carrying the new attribution — which is exactly what that marker is for.

The state manager already has the machinery: a new-session decision discards the persisted session values and keeps what this page load set, which is precisely the swap needed here.

Expected parity difference

v2 will count more sessions than 1.x on identical traffic, because a mid-session campaign click now splits one session into two. The number is correct and the change is deliberate, but the parity harness (§3.3) compares v1 against v2 and will report it as a divergence. It has to be declared as an expected difference before cutover, or it will surface during the overlap looking exactly like a regression — and “sessions do not match” is the last thing anyone wants to be debugging from scratch on the day.

7.11Trend resolution needs no extra date columns Decided

A trend chart offers day, week and month resolution, which raises the obvious worry about dropping eleven derived date parts. It holds up, but for three different reasons depending on the part — and one of the three hides a timezone bug worth naming before anyone writes the query.

One conversion at write time, another at query time

yyyymmdd is derived from the timestamp — date("Ymd", $timestamp). There are not two timestamps and not two timezones on the row. There is one instant, and one conversion already applied to it: ts is the raw epoch, which has no zone; yyyymmdd is that instant rendered as a calendar date using the zone Settings hands to date_default_timezone_set().

Fine until the sub-day parts, because they need a second conversion, in a different place. HOUR( FROM_UNIXTIME( ts ) ) converts in MySQL's session timezone, and nothing makes that match the zone PHP used at write time. New York install, UTC database: an event at 22:00 on the 30th is stored yyyymmdd = 20260830 and reports as hour 2. Evening traffic reads as overnight traffic, daily totals stay correct, and nothing flags it.

1.x never meets this because it converts once — every part including hour is computed in PHP under the same default zone. Dropping the stored parts is what moves the sub-day conversion to query time.

The fix is at the connection, not in the column

The obvious move is to type the column, and on MySQL it makes things worse:

TypeWhy not
DATETIMEA wall-clock value carrying no zone. Keeps the ambiguity, loses cheap arithmetic, costs more bytes.

So ts BIGINT UNSIGNED stays, and it is the honest choice: an explicitly zone-less instant that does not pretend otherwise. Set the session timezone on connect instead, from the same base.timezone the application uses. There is already a place for it — OWA issues SET SESSION sql_mode=… on every connection in both Core/Db/Mysql.php and Core/Db/Pdo.php, with a dialect method choosing the value. One line beside it and FROM_UNIXTIME(ts), PHP's date() and yyyymmdd agree by construction, with no CONVERT_TZ discipline for query authors to remember.

Two things that come with it. The reporting store's timezone becomes part of its contract: anything querying it outside OWA's connection layer — a BI tool, a direct mysql session, the columnar engine — must set the same zone or get different answers. And a per-connection setting is powerful and easy to forget is there: OWA sent SET SESSION sql_mode='' for years, and that turned out to be hiding truncation bugs on every install. Worth a comment at the call site saying what depends on it.

On the columnar path the answer flips, which is why this is a per-store decision rather than a schema-wide one — consistent with the two-store split in §1.10. Those engines have real timezone-aware timestamp types, and an epoch converts into one cleanly. A column type that is wrong for MySQL can be right for the store beside it.

No hourly bucket, because nothing asks for one

The obvious counter-proposal to deriving is a stored yyyymmddhh — one sortable integer that makes every resolution arithmetic on a single column (DIV 100 for the day, DIV 10000 for the month) and carries the write-time zone with it, dodging both the GROUP BY and the timezone objections. It is the strongest version of the idea. It is also solving a problem the product does not have.

And v2's realtime tier does not change it. §1.6 describes realtime as a short window over raw events, which is a filter — yyyymmdd IN (D-1, D) AND ts > X — not a group-by. Both columns it needs already exist.

Which downgrades the timezone hazard above, and it is worth saying plainly. The second conversion only bites sub-day parts, and there are no sub-day dimensions — so the connect-time time_zone setting protects future work rather than fixing a bug anyone can hit today. Most trends never read an event

The cost question barely arises, because owa_rollup_day is grained (site_id, yyyymmdd) — 5,785 rows measured against 692,829 events. A month resolution trend over a year aggregates about 365 rollup rows; day resolution reads them directly. Only two cases touch raw events: realtime, which is a short window by definition, and sub-day resolution.

Which leaves one real gap to decide later, not now: an hour-of-day report over a long period cannot come from a day-grained rollup, so it scans events. That is exactly the trigger condition §1.4 describes for an optional materialization — a cache with a reason, added if breakdown latency outgrows the shape, rather than a column added to every row today on the chance someone wants it.

Deriving is also more robust than storing here. If an install changes its timezone, stored date parts written under the old zone disagree with a re-derived yyyymmdd — the row contradicts itself. Derived parts move with yyyymmdd, so the whole row stays internally consistent even when it is historically wrong. Neither is retroactively correct, and only one is self-consistent.

7.12Source / medium as one dimension Decided

Ranking traffic means grouping by source and medium together — google / organic as one value, not two columns a reader has to join in their head. GA ships it as a first-class dimension for exactly this reason, and v2 needs the same.

Two of them, because v2 now has two attribution scopes. §7.5 separates the session's answer from the visitor's acquisition, so the combined dimension separates the same way:

DimensionFromAnswers
sourceMediumsource + mediumHow this session arrived.
firstSourceMediumfirst_source + first_mediumHow this visitor was originally acquired (§7.5b).

Derived, not stored — the same call as newVsReturning in §7.7, for the same reasons. A concatenation of two columns on the same row cannot drift from its inputs, costs nothing to add, and needs no migration when the format changes. Storing it would be a third copy of facts already on the row.

The NULL trap, and where the sentinel belongs

CONCAT() with a NULL argument returns NULL, not a partial string. So a naive CONCAT(source, ' / ', medium) collapses every row missing either side into one bucket — direct traffic, unattributed traffic and genuine gaps all landing together, and the bucket labelled with nothing.

§1.9 retires sentinel strings from storage, and that is right: NULL means absent, which is what makes COUNT(column) meaningful. But it means the display value has to come from somewhere else, and the dimension layer is that somewhere. Store the truth, name it at the edge — the same split §7.7 draws for booleans, where the type supplies a default rendering and the report may override it.

Declare the kind, not the SQL

A derived dimension has to become SQL somewhere, and the tempting shortcut is to let each one carry its own: CONCAT(source, ' / ', medium) in the registration. That works until the reporting store is not MySQL — and §1.10 explicitly holds the door open for a columnar one behind a second DSN. Then a store move means auditing and rewriting every derived dimension by hand, with nothing to tell you which ones broke.

The existing dialect layer does not help. MysqlDialect covers DDL and introspection — partitioning, primary keys, indexes, session sql_mode, charset — and nothing about expressions. There is also no interface or abstract base, so “another dialect” is not yet a defined shape.

So a dimension declares its KIND, and the dialect renders it. The point that makes this cheap rather than a mini-language: the set of kinds is small and closed, because §1.10's column-admission rule keeps nearly everything a plain column. Everything v2 has proposed so far needs exactly three:

Which changes the shape of a migration from O(dimensions) to O(kinds). A new store implements three renderers; adding a fourth concat dimension afterwards costs nothing in portability. The alternative grows the migration bill every time someone adds a dimension, and does it invisibly.

This repo just did the same thing one level up. Reports-as-config moved reports from code to declarations precisely so the renderer could change without rewriting the reports — and the narrowing that made it safe was the same move: formatters chosen by name from a known list rather than carried as code, excludeColumns a list of names rather than a fragment of script (§1.7). Raw SQL in a dimension registration is the thing that narrowing exists to prevent, one layer down.

It also wants deciding now rather than later, because retrofitting runs the expensive way. Once dimensions carry SQL strings, converting them means recovering intent from expressions — which is exactly the position the report controllers were in before they became configuration.

What this asks of the registry

1.x cannot express either of these. registerDimension() maps a name to a column — the signature takes the column twice, once for display and once for SQL, and there is no expression anywhere in it. Every one of its 93 dimensions is one name over one column.

v2 now has three dimensions that are functions rather than columns — newVsReturning, sourceMedium, firstSourceMedium — which makes derived dimensions a first-class registry concept rather than a special case to be worked around. That is worth planning deliberately, because §1.2 already loads the registry with the other half of this: a single fact table has no entity boundaries, so the registry becomes the only thing preventing non-additive metric and dimension combinations. It is now both the guard and the home of derived values, and it should be designed as such rather than grown into it.
